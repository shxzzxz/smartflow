# 组件治理

本文档定义 SmartFlow 全仓组件的治理范围、抽取判据、生命周期和质量门禁。设计系统入口见 [05. 设计系统](../05.%20设计系统.md)，当前基线见 [组件清单](组件清单.md)。

## 目标与原则

组件治理同时解决两类问题：

- 减少同一语义被反复实现所造成的重复代码和视觉漂移。
- 防止因为外观相似而制造参数膨胀、业务耦合的过度抽象。

治理遵循以下原则：

- **全范围覆盖，分批执行**：规则适用于全仓 UI 组件，但不进行一次性的全量重构。
- **语义优先于外观**：先判断组件承担的业务角色和交互契约，再判断视觉是否相似。
- **复用不是指标**：不以公共组件数量或删除行数作为治理成果。
- **新增债务优先阻断**：存量代码触达即治理，新增同类重复应在评审阶段被阻止。
- **代码是事实来源**：清单用于导航、判断和追踪，不替代源码、测试和组件示例。

## 治理边界

“组件”指承担可命名 UI 职责、具有明确输入与输出边界的 widget。以下内容属于治理范围：

- `lib/design_system/widget/` 中的基础组件。
- `lib/widget/business/` 中的跨 feature 业务组件。
- `lib/feature/<feature>/widget/` 中的 feature 组件。
- 页面文件中的私有 widget 和重复 UI 结构，作为抽取候选。
- 组件直接消费的展示模型、tone、status 和展示映射。
- 组件的示例、测试、无障碍与响应式表现。

以下内容不单独作为组件治理对象：

- 只表达领域规则、且不被组件契约直接消费的实体和值对象。
- 页面级业务流程编排和查询逻辑。
- 与 UI 无关的工具函数。

页面私有组件可以只服务一个页面，不要求进入公共清单；当同一结构出现第二个真实消费场景，或已有组件出现明显分化时，应进入清单并做合并判断。

## 分层与归属

| 层级 | 目录 | 职责 | 约束 |
| --- | --- | --- | --- |
| 基础组件 | `lib/design_system/widget/` | 通用布局、表单、反馈、选择等能力 | 不包含财务业务判断 |
| 业务组件 | `lib/widget/business/` | 跨 feature 的稳定业务表达 | 只包含可渲染组件和其轻量展示契约 |
| Feature 组件 | `lib/feature/<feature>/widget/` | 单个 feature 内跨页面复用 | 不读取页面级 ViewModel 状态 |
| 页面私有组件 | 页面文件或同级私有实现 | 单页面组合与专用展示 | 默认不对外复用，出现重复时进入候选 |

组件通常按以下路径提升：

```text
页面私有 -> feature 组件 -> 业务组件 -> 基础组件
```

允许在语义明显通用时跳级，但跳级仍须满足相同的稳定性和质量条件。

展示模型属于组件契约的一部分，放在组件所属层附近。业务状态到文案、tone 和颜色的映射应由页面或业务 presentation 层完成，不下沉到基础组件。

## 重复分类

发现相似实现后，先分类，再决定是否合并：

- **精确重复**：语义、结构和样式基本相同，仅类型名或调用位置不同。
- **近重复**：结构相同，但存在少量尺寸、文案或交互差异。
- **语义同族**：视觉不同但承担相同业务角色，需要统一语义而非直接合并代码。
- **视觉巧合**：外观相似，但业务职责、交互或未来演化方向不同。

## 决策规则

组件治理只有四种决策：

| 决策 | 适用条件 | 处理方式 |
| --- | --- | --- |
| 合并 | 语义、交互、视觉和演化方向一致 | 保留一个实现，迁移全部消费方并删除旧实现 |
| 提升 | 已在多个独立场景稳定使用，模式可命名 | 提升到更高层，补齐契约、测试和示例 |
| 对齐 | 业务语义不同，但视觉基础相同 | 共用 token 或内部 primitive，不合并公开组件 |
| 保留 | 交互复杂、场景特殊，或未来明确会分化 | 保持独立，并记录保留理由 |

以下条件同时满足时，优先抽取：

- 至少有 2 个独立消费场景，且需求已经实际出现。
- 组件承担相同语义角色，而不只是外观相似。
- 差异可以通过有限变体或组合槽表达，不需要大量布尔参数。
- 各消费方的演化方向没有明显冲突。
- 抽取后的契约比调用方重复组合更易理解。

以下情况应保留独立或只对齐样式：

- 组件内包含不同的数据获取、命令提交或状态生命周期。
- 差异主要来自业务规则，而不是视觉表达。
- 预期很快会沿不同方向演化。
- 合并需要调用方传入大量开关、回调或特定业务类型。

## 组件契约

新增或重构组件必须遵守以下规则：

- 输入使用组件职责内的语义类型，例如 `tone`、`size`、`variant`。
- 基础组件不接收业务状态枚举，不按账户、账单、交易等业务字段切换样式。
- 优先使用命名组合槽表达结构差异，例如 `leading`、`trailing`、`headerAction`。
- 变体数量必须有限，且每个变体都有真实的视觉或交互差异。
- 组件不读取 Provider、不发起查询、不提交业务命令。
- 文案格式化、金额语义和业务状态映射由页面或业务 presentation 层负责。
- 交互组件至少覆盖适用状态，例如默认、禁用、加载、错误和空状态。

## 组件清单

组件清单至少记录以下字段：

| 字段 | 含义 |
| --- | --- |
| ID | 稳定标识，用于 Issue 和提交引用 |
| 名称 | 组件或组件族名称 |
| 层级 | 基础、业务、feature 或页面私有 |
| 源码 | 文件路径和主要类名 |
| 公开性 | public 或 private |
| 职责 | 组件解决的一个主要 UI 问题 |
| 消费方 | 真实页面、feature 或组件 |
| 契约 | 主要输入、输出和组合槽 |
| 变体 | 有限的尺寸、tone、状态等差异 |
| 依赖 | 是否依赖业务类型、Provider 或特定页面状态 |
| 测试 | 对应 widget test 或页面测试 |
| 示例 | 组件示例页中的入口 |
| 状态 | stable、watch、merge-candidate 或 deprecated |
| 重复候选 | 已发现的相关实现 |
| 决策 | 合并、提升、对齐或保留 |
| 最后核对 | 最近一次核对的日期或提交 |

清单维护规则：

- 所有稳定基础组件和业务组件必须登记。
- feature 组件在出现跨页面复用后登记。
- 页面私有组件不逐类登记，但重复候选必须进入清单。
- 新增、迁移或删除共享组件时同步更新清单。
- 同一组件族以清单条目追踪，不要求每个内部私有类单独建行。

## 优先级

治理优先级按影响判断，不按代码行数排序。优先处理：

- 同一语义存在多个实现，且已经出现视觉或交互漂移。
- 高频修改、跨多个 feature 使用或影响关键财务信息展示的组件。
- 无障碍、窄屏、大字号或输入状态处理不一致的组件。
- 改动范围可控、可以通过现有测试验证的精确重复。

低优先级项包括单页面专用、交互复杂、迁移成本明显高于风险收益，或已有证据表明未来会分化的组件。

## 执行方式

- 以组件族为单位创建子 Issue，一次治理一个语义边界。
- 先补齐或确认行为测试，再迁移消费方，最后删除旧实现。
- 不把视觉重构与业务规则变更混在同一提交中。
- 采用触达式迁移；高重复、高风险组件族可以集中治理。
- 每个共享组件至少验证正常状态、关键边界状态和窄屏布局。

## 防回归

- 新增组件前先检索设计系统、业务组件和组件清单。
- 新增基础组件或业务组件必须同步提供测试和组件示例。
- 新增同类实现时，必须在评审中说明为什么不能复用或不应该抽取。
- 组件清单中的 `watch` 和 `merge-candidate` 项应定期复核。
- 静态扫描优先约束明确的重复模式，例如原始状态色透明度、私有状态 badge 和重复列表分隔线；扫描规则稳定后再评估是否接入 CI。

## Issue 管理

#53 作为组件治理父 Epic，负责规则、清单、优先级和跨组件族协调。具体组件合并与迁移拆分为子 Issue。

父 Epic 的完成条件不是“仓库不再有任何重复”，而是治理机制能够持续运行：

- 组件分层和抽取/保留规则已经落地。
- 全仓共享组件和重复候选已有基线清单。
- 第一批高优先级组件族完成收口。
- 新组件具备测试和示例，新增重复能够被发现。
- 组件族有明确的责任人和后续复核机制。

组件族子 Issue 至少包含：目标族、源码与证据、真实消费方、拟采用的决策、契约与变体、迁移范围、测试计划、风险和明确不处理的内容。
