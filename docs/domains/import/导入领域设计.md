# 导入领域设计

## 1. 目标与边界

导入是独立业务域，负责解释外部来源、维护来源映射、识别重复、组织导入交易组、记录成功批次并编排撤销。账务核心继续只负责账户、交易、分录和过账规则，不感知导入批次、来源文件或来源映射。

导入域不直接创建或修改账务实体，而是通过账务 application 端口调用现有创建、删除和账户管理能力。解析器只产出导入域模型，不依赖数据库、来源映射或账务核心 API。

## 2. 导入流程

```text
选择导入来源与文件
→ 解析 ImportBundle
→ 提取来源账户、类别和导入交易组草稿
→ 应用可用的既有来源映射
→ 将唯一且角色兼容的名称匹配直接填入
→ 为仍未匹配的实体生成导入时创建计划
→ 用户确认映射配置
→ 处理错误、警告和重复提示
→ 原子创建所选账务交易组与导入批次
→ 可按批次撤销
```

解析、映射和审阅状态只保存在内存中。只有用户成功提交至少一个交易组后才创建导入批次。

## 3. 来源与资料包

### 3.1 导入来源

一个导入来源代表一种受支持的外部记账产品及其语义，例如一木记账。每个来源只有一个跨批次作用域，同时用于：

- 选择对应解析器；
- 归属账户和类别默认映射；
- 限定历史导入去重范围。

当前不支持为同一种来源建立多个来源实例或来源配置。

### 3.2 ImportBundle

`ImportBundle` 是一次解析消费的一组文件，单文件导入是只包含一个文件的特例。具体解析器根据文件名、表头和内容自动识别文件类型，并负责校验重复或冲突的文件。一个来源支持哪些文件组合、某个解析步骤需要哪些文件，由该来源的 ParseUnit 编排；通用导入流程不要求资料包包含来源的全部导出文件。

文件处理分成两个层次：

- `FileHandler` 处理一个物理或逻辑文件，产出该文件的 `SourceFileFact`；事实集合包含强类型来源记录、文件直接表达的来源实体，以及文件级或行级问题。
- `ParseUnit` 消费一个或多个 `SourceFileFact`，产出交易组、跨文件派生实体、过滤记录和语义问题。单文件规则与多文件联合规则使用同一种编排模型。

文件自身无法解码、表头不受支持等问题只使该文件不可用；只要资料包中仍有可用文件，其余文件的事实和交易组可以继续审阅。没有任何可用文件，以及重复文件类型等无法消解的资料包冲突，才构成资料包致命错误。

通用导入流程不提供手动指定文件角色的界面。文件内容、文件元数据和文件哈希均不持久化。

## 4. 解析结果

### 4.1 来源实体

解析器分别提取来源账户和来源类别。每个来源实体具有来源内稳定的 `sourceEntityKey`；来源没有原生稳定身份时，由解析器根据来源规则生成确定性键。

交易草稿只引用来源实体键，不引用 SmartFlow 账户 ID。来源明确表达“无账户”时不生成来源账户实体，也不进入来源映射。

### 4.2 导入交易组草稿

解析器产出多个导入交易组草稿，每组结构固定为：

```text
ImportTransactionGroupDraft
├─ topLevelDraft
└─ childDrafts[]             // 有序，允许为空
```

一个交易组草稿是整体校验、选择、跳过、去重和提交的最小单位。它可以由一条来源记录展开，也可以由多条、多个文件中的来源记录共同推导。

提交时先创建顶层交易并取得其 ID，再按解析器给出的顺序创建子交易。交易组之间不存在依赖关系，也不支持子交易引用其它交易组或历史批次中的顶层交易。

草稿的金额、时间、账户、类别、备注等账务参数可以在审阅阶段修正；来源身份、账务行为类型、顶层与子交易结构及子交易顺序不可编辑。

### 4.3 来源身份

来源记录 ID 和来源记录指纹只服务于当前解析中的追踪与推导，不持久化。不得用文件名或行号伪造来源记录 ID。

每个导入交易组草稿具有：

- 可选的 `sourceOperationKey`：来源内可靠、稳定的组级身份，用于精确去重；
- 必需的 `sourceOperationFingerprint`：根据规范化来源事实生成，用于提示疑似重复；
- `fingerprintVersion`：标识指纹算法版本，不同版本的指纹不直接比较。

子交易不单独拥有来源操作键或来源操作指纹。

### 4.4 过滤来源记录

解析器可以识别并过滤已被其它来源事实完整表达的冗余记录，例如一木账单中的报销差额结果行和还款利息结果行。过滤记录不生成候选交易组，不属于解析失败，也不计入批次的跳过交易组数。

过滤数量及原因只在当前解析结果中展示，不持久化。

## 5. 解析错误与审阅

解析问题分为三级：

- 资料包致命错误：没有任何可用文件、重复文件类型或其它无法消解的资料包冲突，停止解析；
- 文件问题：单个文件解码失败、表头不支持或文件内结构无效，不丢弃其它有效文件的结果；
- 交易组阻塞问题：该组必须修正或整体跳过；
- 警告：用户确认后可以提交该组。

所有被选择的交易组在提交前都必须有效。同一交易组中的顶层与子交易不能部分导入；不同交易组可以分别选择。

解析器必须是确定、无副作用的转换，同一资料包和同一解析器版本应产生相同解析结果。解析器不读取数据库，不查询来源映射，也不调用账务核心。

## 6. 来源映射

每个导入来源拥有一套可跨批次复用的默认映射集合。映射以 `(source, entityKind, sourceEntityKey)` 唯一，将来源账户或完整类别路径映射到 SmartFlow 账户 ID。

既有映射配置是导入时的默认事实：目标仍可用且角色兼容时直接采用，不再把它作为需要用户“应用”的建议。对没有可用既有映射的实体，只接受名称规范化后唯一且账务角色兼容的完全匹配，并直接填入当前导入；不进行模糊匹配。

仍未匹配的账户或类别形成导入时创建计划。来源分类以完整分类路径参与计划，提交时按父子顺序创建缺失节点、复用已存在节点，并把来源映射到叶子分类。审阅阶段只展示“导入时新建”的差异，不创建账务基础数据；用户可以在映射选择器中改为已有目标。计划中的账户或类别只在确认导入且存在可提交交易组时，在导入外层事务内创建。

来源列只表达账户、收入分类和支出分类；目标则按收入分类、支出分类、资金账户、报销账户、信用账户和贷款账户展示。来源实体可以携带不直接展示的账户画像约束，已有目标和新建目标都必须同时满足交易使用场景与该约束。

新建信用账户缺少 SmartFlow 必填的账单周期参数时，由导入目标创建策略补齐集中定义且满足领域校验的默认值。默认值不属于来源事实，也不参与来源键或指纹；用户导入后可在账户详情中编辑。信用账户和贷款账户均通过信贷 application 创建，导入不得创建没有信贷扩展记录的裸负债账户。

“保存映射配置”是本次导入的确认选项。选中后，映射配置在账务交易、创建目标和导入批次均成功时一并持久化；取消、提交失败或没有成功导入交易组时不写入新的默认配置。映射目标被归档后，原映射记录保留，但下次使用时必须重新映射；账务核心的账户归档操作不反向通知或清理导入域。

## 7. 无账户与幽灵账户

“来源明确无账户”和“账户缺失或未完成映射”在领域事实中仍然区分。导入页面不按技术占位键拆分缺失账户：同一资料包中的缺失结算账户统一展示为“缺失账户”，目标文案展示为“无账户”，并在兼容结算角色时使用幽灵账户映射。该映射只属于当前导入，不写入来源默认映射。

- 来源明确无账户：由具体来源规则决定改变交易语义或使用幽灵账户；
- 来源账户缺失、无法解析或尚未映射：只有兼容结算账户角色的缺失占位可以使用幽灵账户，其它角色仍然阻塞并要求处理。

幽灵账户保持为 `SystemKey.ghostAccount` 标识的系统权益账户，只按 [ADR-0011](../../adr/0011-幽灵账户作为未知结算占位.md) 的狭窄角色例外参与过账，不作为资金账户，也不进入资产或负债口径。

一木借入记录缺少到账账户时转换为债务期初余额，不使用幽灵账户。

## 8. 去重

去重只比较同一导入来源的历史成功导入交易组。手工交易、自动创建的交易和其它导入来源不参与匹配。

### 8.1 精确重复

满足以下条件时认定为精确重复：

- `sourceOperationKey` 相同；
- 历史批次仍处于 `imported`；
- 批次详情关联的顶层交易仍然存在。

精确重复的交易组不能强制导入，自动排除并计入跳过交易组数。

### 8.2 疑似重复

同版本 `sourceOperationFingerprint` 相同但没有可靠操作键命中时，只提示疑似重复，由用户决定导入或跳过。指纹不包含映射后的 SmartFlow 账户或类别 ID。

### 8.3 当前资料包冲突

同一导入计划内出现重复的非空 `sourceOperationKey` 属于解析冲突，阻止提交。仅指纹相同则按疑似重复处理。

批次已撤销或顶层交易已被手动删除后，其详情不再参与精确或疑似重复判断，允许整组重新导入。顶层交易仍存在时，即使子交易被修改或删除，整组仍视为已导入。

## 9. 提交

用户提交时，导入 application service 在一个外层数据库事务中：

1. 再次确认所有选中交易组有效且映射目标可用；
2. 按创建计划创建本次导入实际使用的账户和类别；
3. 逐组创建顶层交易和有序子交易；
4. 按用户选择写入来源映射配置；
5. 写入导入批次；
6. 为每个成功交易组写入一条批次详情。

任何账务创建、批次或详情写入失败时全部回滚，并将错误归到失败的交易组。第一版不新增账务 dry-run API，真实账务创建及现有领域校验是最终权威。

导入创建的顶层和子交易统一使用 `SourceKind.import`，创建时不附加业务归属。来源提供交易时间和入账时间时分别保留；未提供入账时间时默认等于交易时间。

只有至少成功创建一个交易组时才产生批次。全部交易组被过滤、阻塞或跳过时不创建成功、失败或空批次记录。

## 10. 持久化模型

导入域只使用三张表，坚决不使用数据库外键约束。

### 10.1 `import_entity_mappings`

```text
id
source
entityKind                 // account / category
sourceEntityKey
targetAccountId

UNIQUE(source, entityKind, sourceEntityKey)
```

映射只保存当前默认值，不保存历史版本和来源展示快照。账户与类别在账务核心中都使用账户身份，`entityKind` 用于区分来源键空间并校验目标类型。

### 10.2 `import_batches`

```text
id
source
status                     // imported / reverted
importedGroupCount
createdTransactionCount
skippedGroupCount
importedAt
revertedAt?
```

三个数量都是导入提交时的历史结果，不因后续手动修改或删除交易而变化。精确重复、用户放弃的疑似重复、阻塞组和主动取消选择的合法组统一计入 `skippedGroupCount`；解析器过滤记录不计入。

### 10.3 `import_batch_items`

```text
id
batchId
sourceOperationKey?
sourceOperationFingerprint
fingerprintVersion
topLevelTransactionId
```

每个成功导入交易组只保存一条详情。详情不保存交易类型、子交易 ID、来源记录关系、跳过原因或交易展示快照。

## 11. 撤销导入

撤销批次时，在一个数据库事务内：

1. 读取批次详情中的全部顶层交易 ID；
2. 忽略已经被用户手动删除的顶层交易；
3. 通过账务核心删除其余顶层交易，由账务核心删除交易组当前存在的全部子交易；
4. 将批次状态由 `imported` 改为 `reverted` 并记录撤销时间。

任何一个删除或状态更新失败时全部回滚。对已撤销批次再次执行撤销是幂等成功。

撤销允许删除导入后被修改的交易，也会删除导入后新增的子交易。批次和批次详情继续保留，但不再阻止重新导入。来源映射不随批次撤销。导入时创建的账户与类别属于同一个导入事务：提交成功后保留，提交失败时随事务回滚；批次撤销不删除已经成功创建的基础数据。

当前导入只创建无业务归属的交易。未来若允许其它业务域事后关联导入交易，必须重新设计撤销时的跨域清理规则。

## 12. 第一版支持范围

首批交易草稿覆盖：

- 普通支出；
- 普通收入；
- 转账；
- 退款；
- 报销垫付、报销到账和结束报销；
- 还款；
- 借入；
- 期初余额。

第一版不支持：

- 多币种或无法确定本位币金额的记录；
- 余额调整导入；
- 同一来源的多个来源实例或独立账本；
- 文件归档、原始记录归档、持久化解析会话或草稿恢复；
- 跨批次查找父交易或把子交易挂到历史交易组；
- 与手工交易或其它来源进行模糊去重；
- 运行时插件系统或通用文件角色配置界面。
