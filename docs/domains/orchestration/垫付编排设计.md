# 垫付编排

## 1. 域职责

`orchestration`（交易编排）域管理账务核心原语难以单独表达的复杂交易场景。它负责场景定义、跨交易关系、场景规则以及按功能需要维护的状态；账户、交易、分项、分录和余额仍由账务核心负责。

垫付编排使用账务核心的 `advance`、`advanceCollection`、`advanceSettlement` 原语。AA、报销和代付不构成新的账务行为。

## 2. 垫付编排实例

垫付编排实例（`AdvanceCase`）保存：

- 场景：`aa`、`reimbursement`、`onBehalf`；
- 跟踪方式：`itemized`（逐笔）或 `account`（账户）；
- 账户模式使用的应收账户；
- 逐笔 AA 场景的参与人数。

逐笔垫付为每个顶层垫付交易组建立一个实例。垫付、退款、垫付到账和垫付结清作为同一交易组关联到该实例。

账户垫付沿用“应收账户 + 场景”的汇总方式。垫付、到账和结清都是顶层交易，不与某笔垫付建立父子关系，也不校验到账或结清与账户汇总余额的金额关系。

账户模式的 AA 垫付可能包含不同参与人数，因此实例不保存固定人数；退款按该父交易的总额和垫付应收恢复人数。

实例不是垫付单、应收单或账务真相。分类、金额、应收和结算事实只保存在账务交易中。

## 3. 交易归属

垫付相关交易的 owner 使用 `orchestration.advance`，`owner_id` 指向垫付编排实例 ID。owner 不记录场景、跟踪方式或状态。

同一交易组的父交易与子交易使用相同 owner。逐笔垫付的父子关系仍由 `parent_transaction_id` 表达；账户垫付没有父子交易，通过 owner 归入同一编排实例。

## 4. 场景规则

- 报销和代付按交易总额形成垫付应收，没有自承担部分。
- AA 按参与人数以进一法计算每人应付金额；垫付应收为每人应付金额乘以“参与人数减一”，自承担金额为交易总额减去垫付应收。
- 自承担金额按分类总额占比拆分，每个分类向下取整到分，尾差计入最后一个分类。
- 普通垫付退款保持当前自承担与剩余交易总额的比例。AA 退款从交易总额和垫付应收恢复参与人数，并以退款后的总额重新计算自承担和垫付。
- 父交易修改导致既有退款分担变化时，由编排用例生成完整重写事实，账务核心只校验并重新过账。

## 5. 账务边界

账务核心负责：

- 校验分类、自承担、应收和结算分项；
- 按账户类型和子类型校验垫付应收与结算账户；
- 校验逐笔垫付待收回上限和结清锁；
- 生成垫付、退款、到账和结清分录；
- 维护账户余额。

账务核心不保存 AA 参与人数、垫付场景或逐笔／账户跟踪方式，也不从 owner 推导这些信息。

## 6. 状态

`orchestration` 允许各能力按需要建立独立状态机，但当前垫付不新增持久化状态字段：

- 逐笔垫付是否关闭由是否存在垫付结清子交易派生；
- 账户垫付没有全局关闭状态；
- 仅当未来出现无法由交易事实派生的审批、争议或更正流程时，再为对应场景增加状态。
