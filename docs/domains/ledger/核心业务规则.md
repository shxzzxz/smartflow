# 核心业务规则

本文描述当前状态交易模型下的创建、修改、删除、父子交易与统计规则。

## 1. 一笔交易的完整表达

一笔交易由 `transactions`、`transaction_lines` 和 `entries` 在同一数据库事务内提交。交易与交易分项表达完整交易信息；分录由过账规则从分项生成，必须借贷平衡。分项不参与余额计算，也不校验借贷平衡——它与分录不同构，二者合计不相等。

日常支出与日常收入都由彼此独立的分类分配和结算分配表达：

- 每个维度可包含一条或多条分项，并分别合计到交易主金额。
- 分类分配只表达收入和支出分类的金额构成；结算分配只表达收付款账户的金额构成，两个维度不建立逐项对应关系。
- 日常支出的分类分配产生费用借方，结算分配产生付款账户贷方；日常收入的分类分配产生收入贷方，结算分配产生收款账户借方。

## 2. 修改交易

- 修改保持 `transactions.id` 不变。
- `created_at` 保持不变，`updated_at` 随写入更新。
- 备注、对手方引用、交易时间和入账时间等基础信息可走轻量更新。轻量更新不得触碰交易分项，否则会绕过派生分项的重算。
- 对手方使用稳定词表 ID 引用，每笔交易最多一个；清空对手方只移除该交易的引用，不改变任何账务表达。
- 对手方名称可重命名，词表内名称保持唯一；历史交易名称随稳定 ID 更新，不复制旧名称。
- 删除对手方时，在同一应用用例事务内清空全部交易的当前引用并删除词表记录；该操作不删除交易，也不改变分录、余额或统计。
- 金额、账户、分类、用途或父派生分录变化时，必须加载完整交易组并生成 rewrite plan。
- 对受影响交易整体重建分项与分录；不保存修改前快照。分项按当前过账指令重建，不以自身或分录作为重建输入。

## 3. 父子交易

- 父交易 `parent_transaction_id IS NULL`。
- 子交易的 `parent_transaction_id` 指向稳定父交易 ID，且创建后不可修改。
- 创建子交易时继承父交易的统计与预算排除配置。
- 修改父交易时，只能重算子交易中由父事实派生的账务表达。
- 子交易自身金额、时间、到账账户、对手方、备注、用途和父 ID 不得被父交易修改隐式改变。

## 4. 支出与逐笔垫付互转

`DAILY_EXPENSE ↔ ADVANCE` 的可用条件、场景和跟踪方式由交易编排域决定；账务核心只执行已通过编排校验的当前事实重写。

- 转换必须保持交易 ID、标签以及统计/预算排除配置。
- 退款 ID 与自身事实保持不变；当父交易类别或应收账户变化时，账务核心重算其父派生抵减账户。
- 存在垫付到账或垫付结清等不兼容子交易时，拒绝改变交易组结构。
- 逐笔垫付下，退款先拆分为自承担退款和垫付退款；只有垫付退款与垫付到账减少应收。未结清时的待收回金额为：
  `垫付应收 - 累计垫付退款 - 累计到账`。
- 修改后的垫付应收不得小于累计垫付退款与累计到账金额之和。
- 垫付的分类总额分项合计等于交易总额，自承担分项合计等于交易总额减垫付应收；调用方必须提交已计算并守恒的显式分项。
- 分类总额与结算分配各自对交易总额守恒，两个维度之间不建立逐项归属。
- 一笔垫付可退款金额是父交易总额扣除累计退款后的余额，不限于尚未收回的垫付应收。退款的自承担构成冲减原支出分类，垫付构成减少应收，两者合计等于本次退款金额。
- 多分类退款中，分类退款分配表达本次退款分别冲减的分类；自承担退款按这些分类分配拆分，结算账户仍按退款到账分配独立表达。多账户收款不改变自承担与垫付构成。
- 退款的分类分配不得超过父交易各分类扣除既有退款后的剩余金额；退款到账可分配到任意可用结算账户。
- 逐笔垫付的到账和结清必须使用父垫付交易的应收账户，实际到账可分配到多个结算账户。
- 账户垫付的到账、结清都是 ownerless 顶层交易，可一次覆盖同一应收账户下的多笔垫付，不校验金额与账户汇总余额的关系。

AA 人数、场景分担规则、退款重新分担和逐笔／账户跟踪方式见[垫付编排设计](../orchestration/垫付编排设计.md)。

## 5. 垫付结清

逐笔垫付存在 `ADVANCE_SETTLEMENT` 时，禁止修改会改变结算金额的事实，包括父金额、垫付应收、更早退款和垫付到账，以及垫付转支出。

逐笔垫付结清少收时，自己承担部分由调用方显式提交差额分类分配，并计入所选任意有效普通支出分类，不要求属于原垫付分类；坏账部分使用垫付坏账角色计入系统内置坏账损失分类。多收部分计入垫付补偿。

仍允许修改基础信息、付款账户、分类总额事实和垫付应收账户；修改应收账户时同步重建相关子交易的父派生分录。删除结清子交易后交易组重新开放。账户垫付的结清不建立全局关闭状态。

## 6. 往来余额账户

- `asset + receivable` 承载垫付或普通应收余额；`liability + payable` 承载普通应付或信用欠款；`liability + loan` 承载借款本金。
- 借出增加应收并减少资金；收回减少应收并增加资金，利息单独进入利息收入；坏账以坏账损失减少应收。
- 借入增加 `payable` 或 `loan` 负债并增加资金；还款减少负债并减少资金；债务豁免以债务减免收入减少负债。
- 坏账和债务豁免不得超过可减少余额。编辑时先还原旧交易对目标账户的余额影响，再校验新金额。
- 收回和还款允许账户余额穿零，feature 在提交前提示确认，领域过账不阻断。
- 借出、收回、借入和还款本金只影响资产或负债，不进入收支与预算统计。利息收入、利息支出、手续费、坏账损失和债务减免收入按实际收入/支出分录参与统计，再应用交易组排除配置。
- 普通应收账户的“收回”只承接借出后的本金收回；“垫付收回”承接账户垫付到账，两者使用不同的账务行为。报销账户的“报销”承接账户垫付到账。
- 账户垫付的退款从属于对应垫付交易并继承 owner；到账和结清为 ownerless 独立顶层交易，不与该垫付交易建立父子或 owner 关系。

## 7. 删除

- 删除父交易：原子删除父交易、全部子交易及其分项与分录。
- 删除普通子交易：只删除目标子交易。
- 删除逐笔垫付结清子交易：交易组恢复为未结清状态。
- 删除时同步移除分录对账户余额的影响。
- 账务核心不检查 owner；跨域清理由所属 application service 负责。

### 分类迁移与删除

活跃分类树恒为二层，一级和二级分类均可直接记账。同一父分类下的活跃分类按 `sort_order` 稳定展示，用户可调整同级顺序；排序只影响展示，不改变账务、统计或预算口径。分类移动只改变活跃树中的层级关系，并追加到目标同级末尾。

- 分类迁移一次只处理一个源分类，不递归处理子树；源、目标必须是同类型活跃分类且不能相同。
- 迁移命中交易组内引用源分类的分录、垫付分类总额分项与自承担分项；每个命中的顶层交易组通过既有交易编辑与重写规则改到目标分类。
- 整批迁移由一个 application 用例事务包裹，任一交易组重写失败时全部回滚，不产生部分迁移。
- 迁移只改变交易的当前分类事实，不移动分类节点，也不自动删除源分类。
- 删除一次只处理单个分类。分类仍有子分类、分录引用或垫付分类引用时拒绝删除；满足条件时物理删除。
- 删除不再归档分类，也不保留用于统计归并的第三层挂载节点。迁移完成后，用户需要单独再次发起删除。

### 标签与对手方词表管理

- 标签与对手方词表均支持单条和批量删除、合并、迁移；批量操作先选择一个或多个源词表项，再选择一个不在源选择中的共同目标。
- 标签管理和对手方管理均可从词表项进入对应交易流水。标签流水按顶层交易所属交易组的标签匹配；对手方流水只返回自身引用该对手方的顶层交易，子交易引用不单独出现在结果中。
- 标签合并把选中标签在顶层交易上的全部引用改指向目标标签，去除已同时携带目标标签的重复关联，然后删除源标签；对手方合并把选中源对手方在交易上的单值引用改指向目标对手方，然后删除源对手方。
- 标签迁移把选中标签在顶层交易上的引用改指向目标标签并保留源标签；对手方迁移把选中源对手方的引用改指向目标对手方并保留源对手方。
- 合并与迁移都不删除交易，不改变交易分项、分录、余额、统计口径或预算。一次批量操作由一个 application 用例事务包裹，任一源项处理失败时整体回滚。
- 删除标签会解除其全部顶层交易引用；删除对手方会解除其全部交易引用。删除词表项同样不删除交易或改变账务表达。

### 账户归档与永久删除

- 账户停用默认使用归档；归档账户不再参与新交易，但保留余额、历史交易和跨域业务数据，并可恢复。
- 永久删除只允许从已归档账户详情发起，仅适用于用户账户；系统账户不得归档或删除。
- 账务核心在同一事务内重新加载账户并校验：账户已归档、余额为零、没有分录引用，也没有垫付分类事实引用。任一条件不满足时拒绝删除。
- 资金、垫付应收、应收和应付账户由账务 application service 直接删除。信用账户与贷款账户的生命周期归信贷域所有，必须由信贷 application service 完成跨域校验与清理后，再调用账务核心删除基础账户。

## 8. 余额维护

日常修改：

```text
remove(old entries impact)
apply(new entries impact)
save affected accounts
rewrite affected transaction rows/lines/entries
```

以上步骤必须位于同一 `TransactionRunner` 事务内。v20 → v21 数据迁移不重算余额，因为迁移只归并当前有效事实并移除旧版本链记录。

## 9. 统计与预算

- 默认流水直接查询当前 transactions，不再折叠版本。
- 顶层流水使用 `parent_transaction_id IS NULL`。
- 子交易按 `parent_transaction_id = parent.id` 加载并在详情中展示。
- 收支统计以分类账户上的 entries 借贷净额计算。
- 数据库按真实分类账户聚合金额；application 查询层加载活跃两层分类树，组装一级总额与二级分类自身金额。
- 一级分类总额等于一级自身直接金额与全部二级分类金额之和；一级自身金额以“未细分”项呈现，并使用一级分类的真实 ID。
- 统计区间内存在命中分录的物理分类生成统计项，借贷净额允许为零；一级分类只要自身或任一二级分类存在统计活动就返回，其总额允许为零。
- 一级自身“未细分”项与二级分类采用相同活动判断；完全没有命中分录的节点不生成统计项。前端只消费已组装的分类统计读模型，不沿 `parent_id` 自行拼树。
- 不计收支：当前交易组的收入、支出分录不进入收支统计。
- 不计预算：当前交易组的支出分录不进入预算已用金额；是否计入收支统计由不计收支独立决定。
- 两项配置适用于所有账务行为与业务归属，不按交易类型强制赋值。新交易组默认均为 `false`；修改金额、账户、用途或业务域数据时保留，除非用户明确修改配置。
- 配置属于交易组，仅允许从顶层交易修改并同步全部子交易。子交易详情只读展示所属交易组状态，不能独立修改；新增子交易继承配置。
- 转账本金、还款本金即使没有排除标记也不进入收支或预算，手续费、利息等收支分项按其实际分录参与。例如转账 100 元并支付手续费 5 元，两种统计最多计入手续费 5 元。
- 排除配置只影响对应统计查询，不改变分录、账户余额、信贷核销或还款计划状态。

退款在支出分类上产生 CREDIT 分录，因此会自然抵减支出；无需红字冲销记录。

## 10. 交易列表查询

- 对外分类筛选表达一个活跃分类选择：一级分类通常展开为自身与全部二级分类，二级分类只匹配自身，“未细分”只匹配一级自身。
- 结算账户筛选只接受活跃资产或负债用户账户；不存在、归档或系统账户按无匹配结果处理。
- 分类与结算账户是两个独立维度；事实查询匹配对应交易分项，影响查询匹配对应分录，两个维度同时存在时取交集。
- 分类树校验与展开属于 application 查询层，仓储只接收已展开的物理分类 ID。
- 事实查询的分类与结算账户通过交易分项匹配；账务影响查询的账户通过分录匹配。`topLevelOnly` 只控制返回顶层交易还是父子实际交易。首页返回顶层交易，账户详情与统计贡献流水返回实际命中的父交易或子交易。
- 列表主分类由用途决定：日常支出/收入解析唯一合法方向且金额等于主金额的分类分录，候选缺失或不唯一时返回空；垫付读取显式分类总额事实。读侧不依赖分录顺序，写侧不新增唯一性约束。
- 列表与详情统一消费 `TransactionReadModel`。角色事实只来自按录入顺序排列的交易分项；分录不对外暴露，只投影为 `impactsByAccountId`。顶层交易在列表与详情中都填充直接子交易；退款与垫付摘要由 `TransactionGroup` 基于交易分项计算后注入 read model。
- 列表订阅同时响应交易、分录、交易分项与账户快照变化；分类改名、换图标或调整父子关系后重新展开筛选并投影列表。
