# 账务核心业务设计

## 1. 设计目标

账务核心以复式记账保证余额正确，以当前状态交易模型表达用户看到的业务事实。修改和删除保持简单、原子且可验证，不在主交易表中承担审计历史职责。

## 2. 模块边界

```text
TransactionEditAppService
        ↓ application 编排与事务边界
TransactionGroupRewriteService
        ↓ 加载账户、生成候选、应用余额差量
TransactionGroupRewritePlanner
        ↓ 父子兼容性、累计金额、close 锁、用途互转
PostingEngine
        ↓ instruction → 完整当前 Transaction
TransactionLedgerWriter
        ↓
TransactionRepository / TransactionGroupRepository / AccountRepository
```

planner 只计算和校验，不写数据库。application service 在 `TransactionRunner` 内持久化 rewrite 或 deletion result。

## 3. 写路径

### 3.1 轻量修改

备注、对手方、交易时间、入账时间和业务归属等不影响父子账务关系的字段，可以只加载单笔交易并更新当前行。

### 3.2 交易组重写

以下操作必须加载完整交易组：

- 修改父金额、账户、分类或用途；
- 修改报销应收账户；
- 修改或删除子交易；
- 修改组级统计/预算标记；
- 删除父交易；
- 任何可能触发累计金额约束或 close 锁的操作。

`TransactionGroupRewritePlan` 保存每笔受影响交易的 before/after。写入时先计算账户差量，再整体替换受影响 details/entries。

## 4. Repository 语义

```text
TransactionRepository
- findById
- findCompleteById
- save / saveAll
- rewriteAll
- deleteAll

TransactionGroupRepository
- findByParentId
- findByTransactionId
```

数据库不建立外键。repository 与 domain 共同保证只存在一层父子关系、稳定父 ID 和原子写入。

## 5. 查询侧

- 列表查询顶层交易，不做版本折叠。
- 详情按稳定交易 ID 查询。
- 子交易按父 ID 查询。
- 统计直接连接当前 transactions、entries 和 accounts。
- 交易详情不展示修改链历史。

## 6. 迁移策略

schema v21 是一次性、不可逆切换：旧当前父版本内容归并到旧 root 的稳定 ID；当前子交易保留自身 ID 并重指向稳定父 ID；外部引用同步迁移；余额不重算。

迁移失败由数据库事务整体回滚，不保留双写和旧查询 fallback。
