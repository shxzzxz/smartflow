# 账务核心业务设计

## 1. 设计目标

账务核心以复式记账保证余额正确，以当前状态交易模型表达用户看到的业务事实。修改和删除保持简单、原子且可验证，不在主交易表中承担审计历史职责。

## 2. 模块边界

```text
TransactionEditAppService
        ↓ application 编排与事务边界
TransactionGroupRewriteService
        ↓ 加载账户、生成候选、应用余额差量
TransactionGroupRewritePlanner
        ↓ 父子兼容性、累计金额、close 锁、用途互转、派生分项计算
PostingEngine
        ↓ 阶段一：instruction → 交易分项
        ↓ 阶段二：(transaction, lines) → 分录
TransactionLedgerWriter
        ↓
TransactionRepository / TransactionGroupRepository / AccountRepository
```

过账分两阶段：构造分项需要交易组上下文（待核销、核销额、报销差额由父交易与兄弟交易决定），生成分录不需要——阶段二只依赖本交易自身的分项，以及账户与系统账户注册表。两条性质守住这个边界：`instruction → lines → instruction` 往返恒等保证交易层无损，`(transaction, lines) → entries` 可复现且幂等保证账务层确定。

planner 只计算和校验，不写数据库，也不直接构造分录。application service 在 `TransactionRunner` 内持久化 rewrite 或 deletion result。

分类迁移复用同一条重写链路：

```text
CategoryTransactionMigrationAppService
        ↓ 校验源/目标分类，查找命中的顶层交易组，控制整批事务
TransactionEditAppService
        ↓ 按支出、收入、报销垫付分派编辑命令
TransactionGroupRewriteService
        ↓ 保持退款/报销派生分录与余额同步
TransactionRepository / AccountRepository
```

## 3. 写路径

### 3.1 轻量修改

备注、对手方、交易时间、入账时间和业务归属等不影响父子账务关系的字段，可以只加载单笔交易并更新当前行。轻量修改不得触碰交易分项与分录，否则会绕过派生分项的重算。

### 3.2 交易组重写

以下操作必须加载完整交易组：

- 修改父金额、账户、分类或用途；
- 修改报销应收账户；
- 修改借出、收回、坏账、借入、还款或债务豁免的金额与账户；
- 修改或删除子交易；
- 修改组级统计/预算标记；
- 删除父交易；
- 任何可能触发累计金额约束或 close 锁的操作。

`TransactionGroupRewritePlan` 保存每笔受影响交易的 before/after。写入时先计算账户差量，再整体替换受影响分项与分录。分项按当前过账指令重建，不以既有分项或分录作为重建输入——派生分项每次重算，因此不会随编辑漂移。

### 3.3 分类迁移

分类迁移对外只接收源分类与目标分类，不暴露交易组和分录细节。application service 在一个外层 `TransactionRunner` 中依次重写命中的顶层交易组；内层交易编辑用例参与当前事务，任一组失败时整批回滚。

迁移一次只处理源分类自身。一级分类的二级分类需要分别迁移；分类迁移完成后也不会自动删除源分类。

## 4. Repository 语义

```text
TransactionRepository
- findById
- findCompleteById
- save / saveAll（完整持久化新交易）
- updateAll（只更新交易头，不触碰分项与分录）
- rewriteAll
- deleteAll

TransactionGroupRepository
- findByParentId
- findByTransactionId
```

数据库不建立外键。repository 与 domain 共同保证只存在一层父子关系、稳定父 ID 和原子写入。

## 5. 查询侧

- 列表查询顶层交易，不做版本折叠。
- 详情按稳定交易 ID 查询。
- 子交易按父 ID 查询。
- 统计在数据库按真实分类分录聚合，application 查询层再沿活跃两层分类树组装一级总额、二级自身金额与“未细分”项。
- 分类统计以聚合记录是否存在判断统计活动，不以净额是否非零判断；有分录活动的一级、二级和“未细分”项允许返回零金额。
- 语义分类选择由 feature 使用共享纯函数和响应式账户缓存解析为物理分类 ID 集合；application 查询层校验分类与结算账户 ID 集合，再交给仓储按两个独立维度分别匹配。
- 首页查询顶层交易；账户详情与统计贡献流水查询实际父子交易。`topLevelOnly` 只控制结果层级，不改变分类与结算账户通过实际分录匹配的语义。
- 交易角色（主分类、结算账户、转账两端、报销应收）由交易分项直接读取，不从分录的方向、账户类型与金额反推。
- `TransactionReadModel` 是列表与详情共用的唯一读模型：投影交易自有事实、交易分项、当前交易按账户聚合的借贷与净变化，以及子交易（同类型递归）。它不暴露领域 `Entry` 或完整 `Account`。
- 角色查找与交易组聚合（累计退款、报销到账、报销差额、待核销）以读模型方法提供，避免各调用方在多分项场景下各自实现。待核销公式与写路径共用同一 domain 纯函数。
- 一笔交易含多个分类分项时，列表按交易总额展示并标记为多类别，不选取单一主分类。
- 列表响应 transactions、transaction_lines、entries 与 accounts 变化；账户元数据由全局响应式账户缓存按 ID 解析，分类树变化后 feature 重新解析物理筛选集合。
- 交易详情不展示修改链历史。

## 6. 迁移策略

schema v21 是一次性、不可逆切换：旧当前父版本内容归并到旧 root 的稳定 ID；当前子交易保留自身 ID 并重指向稳定父 ID；外部引用同步迁移；余额不重算。

schema v25 清理旧分类归档归并模型：把旧归档分类的物化余额、分录引用、报销支出分类事实和导入分类映射迁移到原活跃归并目标，然后删除旧节点。

schema v28 标准化资产负债账户分类：报销子类型迁移为 `receivable`，信贷扩展与六种已知画像补齐兼容类型、子类型和画像，无其它信号的历史资产/负债分别默认为 `fund / payable`。冲突信号、未知画像或目标不变量失败时升级事务整体回滚；迁移不重算余额或改写既有分录。

交易分项重新定位为过账输入后的迁移（见 ADR-0016）：分项补齐角色与账户，报销支出分类由交易列下沉为分项。存量账户从分录回填，此时全部交易都是单腿的，「每个角色一条分录」的前提成立。验收门槛是过账复现——用回填后的交易与分项重新过账，必须逐条复现库中现存分录；不复现即回填错误或角色缺失。迁移不重算余额。

迁移失败由数据库事务整体回滚，不保留双写和旧查询 fallback。
