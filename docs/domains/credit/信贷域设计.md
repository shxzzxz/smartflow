# 信贷域设计

本文是信贷域的概览与导航，定义域的定位、边界、两类账户、核心概念与聚合关系。表结构、业务规则、场景示例拆分到同目录的子文档。

## 1. 定位与边界

信贷域在账务核心的**借入 / 还款**能力之上，管理负债履约：借款、分期、合同、还款计划、账单、还款。它不表达账务事实，也不改变分录借贷平衡或收支统计口径。

SmartFlow 定位为记账类应用，信贷能力以**记录与追踪真实产品已发生 / 将发生的事**为目标，不承担金融计算职责：

- **不**承诺与各家产品（花呗、银行）的还款金额完全一致。系统按标准方式生成初始数据，产品差异由**修正来源（交易、计划）和还款时据实填写**兜底。
- **不**自动计算逾期罚息、节假日顺延；产品实收的年费 / 罚息 / 取现费等记为该账户的交易，自然进入消费净额。
- 用户的还款行为发生在真实产品里，App 只是记录。真实产品保证了"不会超额、不会还未入账的钱"，App 的职责是**让记录向真实账单收敛**。

## 2. 与账务核心的关系

遵循 [ADR-0001](../../adr/0001-业务域划分与账务核心独立性.md)：信贷域消费账务核心能力，账务核心不感知信贷域。

- 沿用账务行为 `BORROWING`、`DEBT_REPAYMENT` 与 `REPAYMENT_PRINCIPAL / REPAYMENT_INTEREST / REPAYMENT_FEE / REPAYMENT_DISCOUNT` 分项。
- **业务归属标记**：放款交易（owner = 合同）、还款交易（owner = 还款记录）打 owner 标记；**消费交易不标记**——消费与账单的关系靠读时重算维系，记账写侧零负担。
- 通用交易 UI 对 owner 标记交易：日期、结算账户、备注**直接可改**（不触碰核销与状态）；**金额性修改与删除**路由到信贷域页面。
- 跨域写侧流程收口在信贷 application；application 只依赖信贷 domain port，`infrastructure/credit` adapter 调用 ledger application facade。**信贷账户的创建 / 编辑接口由信贷域提供**（编排账务核心建账 + 信贷扩展行）。

## 3. 两类账户与双轨账单

信贷域只面向负债账户（`account_type = LIABILITY`），按账户画像分两类，账单生成机制分轨：

| 账户类型 | 账户画像 | 典型 | 账单机制 | 账单内容 |
| :--- | :--- | :--- | :--- | :--- |
| 信用账户 | `credit.credit` | 信用卡、花呗 | **周期驱动**：出账日协调消费明细窗口 | 消费净额 + 挂载合同期次（账单分期、现金分期） |
| 贷款账户 | `credit.loan` | 借呗、房贷 | **合同驱动**：期次按月归集，无账户级周期参数 | 贷款分期期次（支持不规则、季供） |

两类账户共用同一套合同 / 计划 / 还款模型；**合同的期次节奏由合同阶段条款决定**。信用账户与贷款账户的差异在账单生成、放款交易和还款归集：信用账户按账单窗口投影合同期次，贷款账户按期次月份归集账单。

## 4. 核心概念与聚合

```text
借据侧（前瞻："未来打算怎么还"）           还款侧（本期："该还多少、已还多少"）
──────────────────────────────          ──────────────────────────────────
分期合同 installment_contracts            账单 bills（按 账户 × 周期 唯一）
   └─ 还款计划 installment_schedules           └─ 账单明细 bill_items（消费 / 分期）
          （N 期预期，可编辑可重算）
                                          还款记录 repayments（一次还款动作）
        提前还款 / 改计划                       └─ 还款明细 repayment_items
        作用在借据侧，重算未来计划                   （金额分项；账单级形态分摊到账单明细）
```

关键设计原则：

1. **账单是统一还款目标。** 用户永远对一张账单还款，不直接对计划期次还款；出账前对本期消费的偿还也是对当期 OPEN 账单的账单还款。
2. **账单是来源的只读投影，落库但不可编辑。** 每条明细记得来源（消费净额 / 某合同某期计划），账户详情展示或用户手动刷新时按来源重算。**修正一律作用于来源**：消费不对改交易，计划不对改计划行。
3. **类型下沉到明细，明细只分两类。** 消费 / 分期；贷款分期、账单分期、现金分期等细分标签由合同与挂载账户派生。
4. **还款记录持有还款时间，金额由明细派生。** 还款金额 = Σ 还款明细分项；所有还款自持还款时间，关联交易的交易时间由信贷用例在同一数据库事务内同步维护，还款账户从有效交易派生；明细已还 = Σ 指向它的还款明细；账单状态 = 明细状态投影；欠款分桶读侧派生。
5. **核销以本金为准，且是金额关系的纯函数。** `Σ 分摊本金 ≥ 应还本金 ⟺ 明细 PAID`。任何让两侧金额变化的操作之后重新执行该判定（**状态重判**）；利息 / 手续费据实记录、不阻塞核销；超额分摊允许。

**没有"信用合同"。** 合同 ⟺ 多期还款计划，只在放款分期（贷款分期 / 现金分期）、分期还款（账单分期）时存在。消费信贷在被分期之前没有合同，其偿还走账单还款（出账前挂当期 OPEN 账单）。

## 5. 账单生命周期总览

```text
信用账户：OPEN（周期开始打开，内容跟随来源）
            └─出账日─▶ BILLED（已出账待还，停止自动变化）
                          └─最后一条待还明细核销/跳过─▶ SETTLED
贷款账户：生成即 BILLED ──────────────────────────────▶ SETTLED
```

- 账单状态是明细状态的**事务内投影**，不变量 `SETTLED ⟺ 无 PENDING / PARTIALLY_PAID 明细`；还款更正可使其回退。
- 信用账户出账日是**双重职责日**：冻结上一周期 + 打开下一周期。
- **逾期判定下沉明细级**（按明细冻结的还款日期），账单级只做聚合展示；**逾期不滚动**，未还明细留在所属账单。
- 账单生成由时间驱动 Task 拉取执行（[ADR-0006](../../adr/0006-任务与调度分离的时间驱动生成.md)），幂等键 `(账户, 周期)`；信用账户冻结所有已过有效消费窗口的现存 OPEN，缺失账期不补建，当前 OPEN 被删除时遵从自动生成抑制；贷款账户只生成当期并同样遵从抑制。

## 6. 还款形态总览

| 形态 | 作用对象 | 还款明细 | 账务交易 | 对计划 / 合同的影响 |
| :--- | :--- | :--- | :--- | :--- |
| 账单还款 `BILL`（含本期提前还款） | 账单（OPEN / BILLED 均可） | 分摊到账单明细 | 可有可无 | 明细核销 → 期次 PAID |
| 分期还款 `INSTALLMENT`（账单分期） | OPEN / BILLED 账单 | 分摊到待还消费明细 | 无 | 创建账单分期合同 |
| 提前还款 `PREPAYMENT` | 合同 | 单条金额行 | 可有可无 | 以还款日期为锚点重算其后的待还期次，锚点前一律固定；不跳过计划，不关闭合同 |
| 未归属还款 `UNATTRIBUTED` | 账户 | 单条金额行 | 可有可无 | 无；偿还未归属欠款 |

- "本期提前还款"不是独立类型：对当前 BILLED 账单做账单还款即是，利息 / 手续费据实填写。
- **所有形态支持不生成账务交易**（导入 / 迁移核销；分期还款天然无交易）。
- 信用账户出账前还款 → 对当期 OPEN 账单的账单还款，按用户选择分摊到账单明细；还更远未出账期次 → 提前还款；未归属还款只偿还未归属欠款（期初欠款、余额调整等）。
- 合同指标由 application query 只加载合同与全部计划后调用领域计算；feature 只消费 read model。全部状态（含 `SKIPPED`）参与计划现金流，实际还款（含提前还款）不影响指标；计划本金守恒后再判断现金流充分性和利率解。

## 7. 还款计划模块

计划生成与变更统一由 `InstallmentPlanEngine` 计算。对外只提供 `generate(terms)` 和 `recalculate(context, change)`；还款方式计算器、浮动利率计算器与计息换算保留为内部计算实现。

`InstallmentPlanContext` 携带原合同条款（含已应用重定价事实）、本金、借款日期、当前计划快照和有效提前还款本金。`change` 明确区分按候选条款重算、应用某次重定价、提前还款变化后重算。调用方不再选择日期重建开关或组装跨调息本金快照。

引擎按原计划确定冻结范围，组织尾部期次结构和阶段条款，再计算尾部金额。按条款重算允许增减待还期次，冻结期次不得移除或移动；保留期次沿用原身份，新增期次在计算结果中不分配持久化 ID。`InstallmentPlanChangeSet` 返回最终计划、冻结范围及新增、移除、更新的期次。

`InstallmentPlanService` 属于 application，统一加载事实、生成预览、校验确认和保存。预览携带计算输入及变更请求的规范化指纹；确认在同一事务内重新加载事实、核对指纹、重新计算并保存，拒绝使用过期预览。名称和备注不影响计算，不参与指纹。自动重定价仅在受影响计划包含人工修改时要求确认；冻结期次和已出账账单作为预览提示，相关账单状态参与预览一致性检查，不作为人工确认条件。指纹不代替领域校验，也不作为持久化版本或审计记录。

`InstallmentContract.applyPlanChange` 应用计算结果、分配新增身份并维护合同状态；`reviseSchedules` 只表达手工编辑。自动计算不会新增人工调整标记；按条款重建的尾部清除原人工调整标记，冻结部分保持原样。

四条调用流程：

- 创建合同：创建用例 → `InstallmentOriginationService` → 引擎生成 → 原子保存合同和计划；贷款计算器直接消费同一引擎的结果。
- 按配置重算：`InstallmentAppService.previewContractRecalculation` 生成预览，`updateContract` 携带指纹确认 → 聚合应用 → 保存；合同编辑中的计划更新、条款修改、重定价候选清理与放款交易同步参与同一事务。编辑条款但不重算仍为独立行为。
- 重定价：`InstallmentRepricingService` 获取参考利率并维护候选 → 计划模块预览和确认 → 在外层事务内一并保存计划与应用状态；候选顺序、幂等和调度仍由重定价用例负责。
- 提前还款：还款用例在事务内修改还款事实 → 计划模块按最新有效本金重算 → 保存；删除后以被删记录的还款日期作为触发日期。失败时还款、账务交易和计划整体回滚。

`SettlementAppService` 只编排还款核销与状态同步，加载分摊事实并调用账单、期次和合同的领域行为。核销金额判断与状态投影属于 domain；还款计划重算不经过该模块。

`InstallmentStatusRepairAppService.validateAndRepair` 承载用户显式触发的状态校验与修复，由合同详情 ViewModel 直接调用。它在自己的事务中加载有效还款分摊、检查关联冲突、调用领域行为并保存计划与合同状态；保留人工跳过意图，不修改账单或交易。正常还款后的核销同步继续由 `SettlementAppService` 编排，两者复用领域状态规则。
