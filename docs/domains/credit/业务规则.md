# 信贷域业务规则

本文定义信贷域"账户与周期如何组织、账单如何生成与刷新、还款如何记录、状态如何联动"。表结构见《[数据模型](数据模型.md)》，端到端示例见《[业务场景流程示例](业务场景流程示例.md)》。

## 1. 信贷账户与周期

### 1.1 账户参数

- 信贷账户由信贷域接口创建 / 编辑（编排账务核心建账 + `credit_liability_accounts` 扩展行）。
- 信用账户必填出账日、还款日（1–28）；贷款账户无周期参数。
- 出账日 / 还款日**修改自下一张消费明细生效**：已生成消费明细保持其窗口和还款日期，每个 YYYYMM 最多一张账单。

### 1.2 周期归属

- 交易按**入账日期**（`posted_at` 日期部分）归属周期窗口；交易时间 `occurred_at` 不参与账单归属。出账日当天交易归本期 / 下期由 `billing_day_to_next` 决定（默认下期）。退款同规则（§8）。

### 1.3 账户归档与永久删除

- 信用账户与贷款账户可以归档；归档只停用账户，不清理账单、合同、还款或账务历史，并可从归档账户详情恢复。
- 永久删除入口只在已归档账户详情展示，并由信贷 application service 统一编排。通用账务入口不得直接删除信用账户或贷款账户。
- 存在分期合同、账户级还款、含明细的账单或账单级还款时，账户仍有业务数据，拒绝永久删除。
- 没有上述业务数据时，空账单、账单生成抑制和 `credit_liability_accounts` 扩展行属于可清理投影；信贷域清理这些数据后调用账务核心删除基础账户。
- 信贷侧校验、投影清理与账务基础账户删除必须位于同一数据库事务内，任一步失败时全部回滚。

## 2. 账单生成（双轨）

账单生成是[时间驱动生成（ADR-0006）](../../adr/0006-任务与调度分离的时间驱动生成.md)的一个 **Task**，幂等键为 `(账户, 周期)`，数据层唯一约束兜底并发。正常生成范围固定，不扫描全部历史周期。

### 2.1 信用账户：周期驱动

以出账日 5 号、还款日 25 号为例：

| 时段 | 账单状态 | 内容 |
| :--- | :--- | :--- |
| 上月 05 ~ 本月 04 | OPEN | 分期与消费明细落库；普通查看只刷新 OPEN 账单并跟随来源 |
| 本月 05 出账日 | OPEN → BILLED | 消费明细以当刻消费净额定格；同时打开下一周期账单 |
| 本月 05 ~ 25 | BILLED | 待还，25 到期 |

- 生成**不补建**：上一期账单不存在时不创建（新账户首个周期、或上一期被删除后都不重建）。用户删除账单会留下该 `(账户, 账期)` 的自动生成抑制，Task 不会恢复；只有显式补建该账期才清除抑制并恢复账单。
- Task 迟到执行时，冻结所有实际存在且已过有效消费窗口的 `OPEN` 账单；不会创建缺失账期。只要当前账期未被抑制，仍创建当前 `OPEN` 账单。
- 消费窗口只落在消费明细上。窗口仅在上一账期消费明细实际存在时衔接；中间存在缺失账期时，新的消费明细按账户参数重新起算，缺失窗口内的消费没有账单覆盖，落入未归属欠款。

### 2.2 贷款账户：合同驱动

- 只生成当期账单；该账户全部合同中，预期还款日落在当月的非 `SKIPPED` 期次合并进入账单。
- 期次日期完全按合同条款：末期对齐整年、季供、不规则日期均可。空账单也生成，不预生成下一期。

### 2.3 账单状态与了结

- 状态先看出账维度：任一消费明细 `billing_state = open` 时账单为 `OPEN`，即使金额为 0、已还清或溢缴；所有明细均为 `billed` 时，存在 `PENDING` / `PARTIALLY_PAID` 为 `BILLED`，否则为 `SETTLED`。存在应还金额且无还款引用为 `PENDING`；完全无应还金额的占位明细为 `PAID`；存在引用但本金未足额为 `PARTIALLY_PAID`；本金足额为 `PAID`。
- 了结性质按需派生：全部明细经现金核销 = 现金还清；含分期还款分摊 = 转过分期；混合场景看明细。
- **逾期判定明细级**（按明细 `repayment_date`），账单级聚合展示；**逾期不滚动**，未还明细留在所属账单，"总待还"用跨账单聚合视图。

## 3. 账单明细与刷新

### 3.1 消费净额口径

消费明细金额 = 窗口内**使该信用账户负债增加的交易**（普通支出、转账转出 = 取现、报销垫付）− 窗口内入账并命中该账户的退款。

排除：**借款**（已被合同期次覆盖，计入即与现金分期双算）、期初余额、余额调整（落未归属桶）、**还款**（任何形态的还款都不冲减消费净额——出账前对本期消费的偿还挂在当期 OPEN 账单上，作为分摊进入已还，见 §4）。净额为负按 0 出账，差额经余额自然落入未归属桶（溢缴）。

### 3.2 明细金额不可编辑，窗口调整有专用入口

1. **消费金额不对** → 改交易（补记 / 更正 / 改入账日期）。消费统计窗口可以通过账单明细编辑入口调整；金额仍由交易来源重算，不能直接改明细金额。
2. **分期明细不对** → 从账单明细进入合同详情，再由合同详情进入合同编辑页修改还款计划金额和日期，期次状态不阻止编辑或按配置重算。合同详情页可跳过或撤销跳过单个期次。
3. **利息 / 手续费与实际不同**（本期提前还款等） → 还款表单据实填写，核销以本金为准，不需要改账单。

不支持凭空增删明细或直接改写金额；导入缺口由未归属欠款 + 对应账单 / 合同的无交易还款承接（§7、§10）。

### 3.3 刷新规则与时机

| 时机 | 行为 |
| :--- | :--- |
| 交易或计划来源变化 | 不立即刷新账单 |
| 出账日 | 以当刻来源值定格，此后停止自动变化 |
| 查看账户详情 | 只刷新 `OPEN` 账单；`BILLED` / `SETTLED` 保持已落库投影 |
| 用户点"刷新" | 刷新指定账单，允许 `OPEN` / `BILLED` / `SETTLED` |

- 交易写入不调用信贷刷新，不存在 ledger hook；查看账户详情由 application 显式先刷新展示范围，再查询读模型。查看不会生成账单。
- 刷新后重建当前来源投影。同账单内来源持续存在时复用 `BillItem.id`。来源因移期或移除而消失时删除旧明细，同时将引用它的还款分项 `bill_item_id` 置空，保留分项金额、还款日期、关联交易和原账单归属；解除引用与刷新在同一事务中完成。新账单按当前计划完整生成应还金额，不扣减旧账单还款。移除计划期次时可先解除历史明细的计划引用，账单刷新时再按上述规则删除来源已消失的明细。
- 状态重判基于还款明细引用和累计本金，支持 `PENDING ↔ PARTIALLY_PAID ↔ PAID` 回退或推进。

### 3.4 账单删除与区间调整

- **删除**：仅允许没有任何还款记录（`repayments.target_type = BILL` 且 `target_id = 该账单`）的账单。账单明细是来源投影，删除不影响合同、还款计划或账务交易；删除会抑制该账期的自动生成，不会被 Task 自动重建。用户显式补建该账期才可恢复。
- **编辑区间**：编辑消费明细的 `start_inclusive` / `end_inclusive` 闭区间；账单不提供窗口编辑接口。
  - 校验：起始日不得晚于结束日，结束日必须仍在原账单月份。
  - 保存后立即按新窗口重算消费金额、明细状态和账单状态；账单归属仍由明细的 `bill_id` 表达。

## 4. 账单还款（`BILL`）

针对一张账单，一次可覆盖多条明细；一次还款针对一张账单。贷款账单生成即 `BILLED`；`OPEN` / `BILLED` 账单均可按用户选中的明细还款，账单状态不再限制明细类型。

1. 填**还款总额与优惠**（默认），展开可分别填本金 / 利息 / 手续费。
2. 分摊建议：**FIFO（默认）**——分项先手续费、再利息、后本金；明细间先分期、后消费。**均摊**备选。策略只是表单建议层，用户可在网格中任意调整，模型不感知。
3. **超额分摊允许**：建议永不主动超额；用户手动改超出应还时提示但不阻断（据实优先），多还部分经余额落入未归属桶（溢缴）。
4. 落库：1 笔 `DEBT_REPAYMENT` 交易（分项 = Σ 还款明细分项；无交易还款跳过）+ 1 条还款记录 + N 条还款明细。
5. 核销联动：存在分摊但本金不足 → `PARTIALLY_PAID`；本金够数 → `PAID`；账单无 `PENDING/PARTIALLY_PAID` → `SETTLED`。

**本期提前还款**：还款日前对当前 `BILLED` 账单做账单还款，不是独立类型；利息 / 手续费因提前而变少的据实填写，可偏离明细应还，不影响计划。

**部分还**：允许；未够数明细保持 `PENDING`，进度由明细派生。

**无交易还款**：`BILL` / `PREPAYMENT` 支持 `transaction_id` 为空——钱的流动已在别处发生（导入 / 迁移），只补信贷侧核销与状态推进。所有还款均由记录自身持有还款时间；有交易时与关联交易的交易时间一致，创建与修改由信贷用例在同一数据库事务内同步写入。`INSTALLMENT` 天然无交易；`UNATTRIBUTED` 不支持无交易还款。

## 5. 分期还款（`INSTALLMENT`，账单分期）

以分期合同代替现金完成核销的还款形态，债务总额不变、只改还款节奏：

1. 对 `OPEN` 或 `BILLED` 账单发起，**只能分摊到消费明细**（不支持分期的分期），且消费明细必须为 `PENDING` / `PARTIALLY_PAID`，可全额或部分。
2. 落库：1 条还款记录（无交易）+ 还款明细分摊到消费明细 + 1 个 `BILL_CONVERSION` 合同（本金 = Σ 分摊本金，`source_repayment_id` 回指还款记录）+ 还款计划（首期 = 下一个出账周期）。
3. 核销走统一规则：明细 400 = 现金还 200 + 分期还 200，两条还款明细合计够数即 `PAID`；"是否转过分期"从还款明细形态派生。
4. 新合同未来期次按计划日期进入对应账单，账单分期不额外改变合同计划生成规则。

## 6. 合同维度操作

### 6.1 合同创建

**放款类（`DISBURSEMENT`）**：输入放款入账资产账户、挂载负债账户、本金、期数、日期、还款方式、利率、计息方式、总手续费。**可选择不创建放款交易**（迁移，借款已实际发生于他处），放款双字段同空；创建交易时写 1 笔 `BORROWING` 并打 owner 标记。

- 挂贷款账户 = 贷款分期，挂信用账户 = **现金分期**；两者期次均按合同阶段条款生成。现金分期的借款交易不计入消费净额（§3.1），信用账户只影响后续账单投影和还款归集。

**账单转换类（`BILL_CONVERSION`）**：由分期还款触发（§5），不写账务交易。

### 6.2 参数、计划、还款与状态解耦

- 合同条款是计算输入，编辑条款不自动改写计划；结构或期数变化须先预览并确认。首次生成与重算共用完整计算入口，输入为合同条款、本金扣减、确定的重定价和利息调整。
- 普通还款、期次状态和合同状态不决定计算范围。已还、部分已还、跳过及已结清均不阻止计划计算或手工编辑；实际还款记录保持独立。
- 自动合同每次重新生成完整日期、本金、利息和手续费，覆盖人工修改。计划保存时维护账单和还款引用，并根据有效还款事实更新计划与合同状态。
- 本金舍入尾差按所在阶段的尾差处理策略分配，目前由阶段末期吸收；合同末阶段约定余额作为尾款只追加一次。自动计划满足 `计划本金合计 + 本金扣减合计 = 合同本金`。
- 计息周期为 `(上期还款日, 本期还款日]`，上期还款日不计入本期，本期还款日计入本期，实际天数取两次还款日之差。首期的左开边界由借款日、上一阶段结束日或明确约定的起息边界确定；例如 `(8/8, 9/8]` 覆盖 8/9 至 9/8，共 31 天。
- 自定义合同仅含一个或多个自定义阶段，不能混入自动阶段或免还期。计划完全手工维护；本金扣减、重定价与利息调整均不自动改写计划。显式调整阶段结构时保留可匹配行的手工金额和日期，并更新阶段归属。
- `PENDING` 期次可置 `SKIPPED`（用于迁移已还期次），也可撤销；跳过是独立状态意图，不改变计算输入。

### 6.3 提前还款（`PREPAYMENT`）

- 写合同级还款记录和单条金额明细，交易可选。有效本金转换为带实际发生日期的本金扣减；利息、手续费及优惠仍属于实际还款，不进入计划本金扣减。
- 新增、修改或删除本金后，重新加载全部有效操作计算完整计划。不含本金的提前还款不触发计划重算。
- 本金扣减以还款日次日定位首个受影响的计息周期，从该周期首个计息日作用于整期本金，不按实际发生日拆本金；借款日及免还期内的扣减归入随后首个计息周期。例如 8/20 的扣减作用于 `(8/8, 9/8]`，9/8 的扣减作用于 `(9/8, 10/8]`，此前周期不受影响。扣减只发生一次，减少后的本金传递至后续期次；本金扣减日期必须早于末期还款日。
- 本金扣减与重定价按计算生效位置交错处理。同一期的扣减先形成整期本金，利率仍按其实际生效日切分；未来扣减不能提前影响更早期次。
- 计划修改不自动刷新已落库账单，用户显式刷新账单后更新投影。状态按还款事实维护，提前还款不直接核销某一期。

#### 6.3.1 多阶段重算

各阶段按合同顺序传递日期和本金，利率由各自初始利率及本阶段重定价结果确定。当前位置可用本金为 `合同本金 − 截至当前位置已生效扣减 − 本次计算此前期次本金`，不使用普通还款金额或尚未计算的未来期次本金。

1. 每个阶段以当前位置本金为期初本金；阶段内扣减后重新求解剩余正常摊还。
2. 显式期末本金取原约定与当前可用本金的较小值，仅调整本次计算输入。可用本金不高于目标时，剩余正常摊还本金为零，余额传给下一阶段。
3. 未指定期末本金时，末阶段取零；非末先息后本阶段承接期初本金，其余方式须显式指定。免还期只推进时间，不产生期次或利息，期间操作计入后续阶段。
4. 手续费按阶段约定完整分配，正常本金尾差按所在阶段的尾差处理策略分配；最后阶段约定保留本金作为尾款追加一次。

借款 10 万元，阶段一期末约定 5 万、阶段二期末约定 2 万，扣减前已生成计划本金 1 万：扣减 5 万后阶段一剩余正常本金为零，阶段二期初 4 万、正常摊还 2 万、末期尾款 2 万；扣减 8 万后阶段二期初及尾款均为 1 万，正常摊还为零。同一笔扣减只处理一次，合同原约定保持不变。

### 6.4 提前还更远期次

要还的不是当前 `BILLED` 账单、而是更远未出账期次时，走**提前还款**；边界：当前 `BILLED` 账单 → `BILL`，更远期次 / 直接砍本金 → `PREPAYMENT`。

### 6.5 合同删除

- 统一条件：不存在合同级提前还款，且全部计划状态均为 `PENDING` 或 `SKIPPED`。
- 账单分期删除时同时删除来源分期还款及还款明细，并重判原消费明细和账单状态。
- 现金分期、贷款分期删除时同时通过账务领域删除借款交易。
- 最后清理合同关联的账单明细投影、计划和合同；整个流程由 application 在同一事务内编排。

### 6.6 状态校验

- 状态校验根据有效还款事实，在同一事务中校验并修复合同及期次状态；计划金额、日期、账单和交易保持不变。用户可以从合同详情显式触发状态校验。
- 非 `SKIPPED` 计划按关联账单明细上的**有效还款分摊**重判：无分摊 → `PENDING`；累计本金不足 → `PARTIALLY_PAID`；累计本金达到计划本金 → `PAID`。计划本金为 0 时仍要求存在有效分摊才可判 `PAID`。
- 同一期计划曾投影到多个账单明细时合并全部有效分摊。合同级提前还款与未归属还款不直接核销某一期计划。
- `SKIPPED` 是人工意图，校验永不自动修改；若其存在还款分摊，仅报告冲突。
- 已解除计划引用的历史账单明细不阻止当前计划状态修复。`bill_item_id` 为空的历史还款分项不参与期次核销，也不作为引用缺失冲突；非空 ID 指向缺失明细、孤儿还款分摊、零金额分摊、账单目标不匹配、指向缺失计划或合同无计划均报告冲突。存在阻断性冲突时不修改合同状态。
- 无阻断性冲突时，计划修复后由合同聚合统一重算：存在 `PENDING` / `PARTIALLY_PAID` → `ACTIVE`；全部 `PAID` / `SKIPPED` → `SETTLED`。

### 6.7 浮动利率与重定价

- 合同各计息阶段直接填写合同约定的初始利率及单位，不选择利率类型或填写基点，也不按公共报价自动回填。初始利率不得为负，留空按零利率处理。后续利率变化通过独立的重定价配置或重定价记录表达。
- 创建合同不自动创建重定价配置。用户在合同创建后独立添加配置，配置只供任务生成重定价结果；删除配置保留已有结果及其应用状态，也不重算计划。
- 自动重定价配置属于合同内的特定阶段历史，以稳定阶段标识关联：配置生效日、利率类型、加减基点、3 / 6 / 12 个月周期、首次重定价日和首次生效日。首次日期为永久日历锚点，月末截断后不逐月漂移。每条配置只生成重定价日在 `[本配置生效日, 同阶段下一配置生效日)` 内且不晚于今日的结果；重定价生效日可以早于所属阶段的首个计息日，但不得晚于阶段末期还款日；可以晚于今日或跨过下一配置生效日。各配置从自己的已处理进度继续生成。
- 每条配置独立记录上次成功处理的重定价日及生成状态（待生成 / 已完成），任务只处理待生成配置在该日期之后的候选；同阶段同生效日已有记录时跳过并视为成功。记录插入与进度推进在同一事务内提交；同一配置较早周期缺少参考利率时不越过它，其他配置可以继续。应用计划失败时保留未应用结果，即使配置已完成，后续仍直接重试应用，不重新生成。
- 配置的下一未处理周期若生效日晚于阶段末期还款日，或重定价日达到同阶段下一配置的生效日，则生成已完成，后续自动任务跳过该配置。下一周期尚未到期或缺少报价时仍为待生成。新增、删除配置后重新判断受影响的配置区间；阶段末日变化后重新检查该阶段配置。生成进度保持不变，手动删除结果不恢复已处理周期。
- 手动重定价独立于配置，用户指定所属阶段、利率类型、基点、重定价日和生效日；无需有适用配置，手动增删不改变配置或自动进度。生效日不得早于重定价日或借款日，且不得晚于所属阶段末期还款日。自动与手动共用 `(合同, 阶段, 生效日)` 唯一性，同阶段同日重复创建被阻断，不同阶段分别保存。
- 已被任务处理的日期，即使对应记录被删除也不自动补回，因为配置进度不回退；任务尚未处理的手动记录被删除后，该配置周期仍然可生成。用户主动重建已删除日期只检查同日唯一性及输入有效性。
- 类型支持 LPR 一年期 / 五年期以上及短期 / 中长期贷款基准利率，1 BP = 100 ppm = 0.01 个百分点。基点可负，执行利率不得负。一般参考利率查询包含查询日已发布的记录；重定价引用严格早于重定价日的最近可信参考利率，迟到执行仍使用约定的重定价日。已确定的结果保留其引用快照。
- 重定价不创建阶段或期次，所有结果按重定价生效日排列。生效日归新利率；周期首个计息日生效时，整期按新利率计算，不属于期中重定价。是否发生利率变化，按阶段计息方式将新旧利率换算为日、月或年利率后精确比较，换算遵循合同的标准天数约定。换算后相等仍保存记录，但不触发还款安排重算或改变正常计息口径。周期内部发生真实变化时拆分利息，各片段使用实际生效的利率，按实际天数及合同标准天数合计后舍入；月计息期内发生真实利率变化时改用日计息。
- 每年 6/20 还款，下一周期为 `(6/20, 次年6/20]`。配置一从 5/1 生效、6/20 重定价、6/21 利率生效，配置二从 6/21 生效时，配置一仍生成 6/20 的重定价记录；6/21 开始整期使用新利率，不触发期中策略。
- 等额本息按阶段约定的期中重定价还款策略处理周期内部生效的重定价。“保留当期本金”保留本次计算中调息前预测的当期本金，只重算分段利息，从下一期重算固定额；“动态期利率重算”以当期分段合计的混合期利率求解包含当期的剩余还款安排。固定额使用完整剩余期限，未来未确定利率沿用最近已确定利率，不提前把后续重定价用于历史期次。
- 自动任务补齐当前时点前尚未处理的重定价周期，重复执行不产生重复结果；参考利率缺失或单个合同失败不阻塞其他合同。
- 结果状态为未应用、已应用、用户已确认。计划保存与应用状态原子提交；确认只消除已加载记录的提示，不重算、不改变利率事实。每次完整计算消费全部有效记录，不能省略已经应用的历史事实。
- 删除合同清理其配置、重定价及利息调整，保留公共参考利率历史。各阶段初始利率可独立编辑，已确定重定价通过专用记录入口增删。
- 重定价结果只作用于所属阶段，不覆盖后续阶段的利率；阶段首个计息日及之前已生效的本阶段结果，按生效日取最新一条作为阶段起始利率，不按重定价日选择。没有适用结果时使用合同初始利率。例如首个计息日为 2025/09/01，生效日为 08/30、09/01 时取 09/01，为 08/20、08/25 时取 08/25。删除阶段在同一事务内删除其配置与结果，保留其他阶段和公共参考利率历史。

### 6.8 利息调整

- 用户填写开始日、结束日和调整后占原利息的比例：0% 免息，50% 减半，100% 不变，120% 增加 20%。区间为 `(开始日, 结束日]`，不包含开始日、包含结束日，比例非负。开始日填上期还款日、结束日填本期还款日，即调整本期完整利息。
- 同一合同区间禁止重叠，端点相接可以共存。新增或修改时校验实际计息单位：日计息按日，月 / 年计息必须覆盖完整单位；跨不同口径分别校验，不因为调整请求额外切换为日计息。
- 完整月 / 年单位以合同实际时间安排为边界，包含首期偏移和末期截断，并与计息片段保持一致。月供配按年计息时，基础利息按年利率乘间隔月数 / 12 计算。
- 调整区间可超出计息范围，但必须完整覆盖每个相交的月 / 年单位。例如月计息周期为 `(1/8, 2/20]`、`(2/20, 3/20]` 时，调整 `(1/1, 2/20]` 可以免除首期利息，调整 `(1/1, 2/26]` 因部分覆盖后一期而拒绝保存；日计息按实际覆盖天数处理。
- 先完成本金扣减和重定价，再基于最终计息片段调整精确利息，按期汇总后统一舍入到分。本金分配保持不变，等额本息的最终应还金额可因调整而变化。
- `(8/8, 9/8]` 按日计息、10 万元本金、360 天标准年，8/20 年利率从 3.6% 降至 1.8%，基础利息为 210 元；`(8/15, 8/25]` 按 50% 调整后为 175 元。
- 删除调整后按剩余操作完整重算。记录与计划在同一事务内保存，区间或粒度校验失败时整体回滚。

## 7. 未归属还款（`UNATTRIBUTED`）与未归属欠款

```text
未归属欠款 = 账户负债余额 − Σ 合同 PENDING 计划行剩余本金 − Σ 账单消费明细剩余本金
```

- 剩余本金 = `max(0, expected_principal - Σ allocated_principal)`。账单侧**只算消费明细**，分期账单明细由合同计划侧覆盖以避免双算。本桶承接期初欠款、余额调整及刷新前的来源差额；刷新后差额迁入账单应还。
- 未归属还款：写 1 笔 `DEBT_REPAYMENT` 交易 + 还款记录（目标 = 账户）+ 单条还款明细，不支持无交易模式，不碰任何账单 / 合同。**偿还上限 = 未归属欠款桶**；想还本期消费应走对 OPEN 账单的账单还款。

## 8. 退款

退款是账务核心 `REFUND` 交易：

- **退入资产账户**（花呗退支付宝余额等）：不影响信用账户与账单，天然支持。
- **退回信用账户**：按入账日期归属周期窗口，冲减该窗口消费净额；"冲抵下期" = 退款入账日期设到下期窗口，无需特殊机制。
- 入账日期落入已出账窗口（补记 / 改日期）：已出账账单查询只读，用户可在账单详情页显式刷新。

## 9. 还款的修改与删除

- 还款记录存稳定的 `transaction_id`。交易修改保持 ID 不变；金额变更经信贷域接口重写还款明细并重新判定状态。
- 历史空关联还款分项完整读取并显示为“无明细”，其金额计入还款合计。用户新增或编辑保存的还款不得含有无明细分项，须显式移除无效分项并纠正分摊；保存和分摊计算不得静默丢弃这些行。仅编辑日期、账户或备注也不能绕过这项要求；删除原还款仍沿用既有流程。
- **通用交易 UI 权限**（owner 标记的还款 / 放款交易）：日期、结算账户、备注直接可改（不触碰核销与状态）；金额性修改与删除显示横幅并路由信贷页。
- **删除联动**（有交易先按账务核心规则物理删除并回退余额影响）：
  - `BILL`：删还款明细 → 状态重判（明细 / 期次回 `PENDING`，账单 `SETTLED` 回退）。
  - `INSTALLMENT`：删还款明细与记录，级联其创建的合同——合同无其他关联还款时连同计划删除；有则**阻止删除并引导先处理合同侧**。
  - `PREPAYMENT`：删除后按剩余有效操作完整重算计划；历史账单通过既有显式刷新入口更新，还款归属保持。
  - `UNATTRIBUTED`：先删除对应账务交易，再删记录与明细。
  - 无交易还款（仅 `BILL` / `PREPAYMENT` / `INSTALLMENT`）：直接删记录与明细并执行同样联动；入口在账单或合同详情的还款记录列表（§11）。
- 合同状态联动：被撤销还款若曾使合同 `SETTLED`，回退 `ACTIVE`。

## 10. 导入与迁移

立场：**导入带来账务事实（交易、余额），信贷侧从切点开始管**。

| 场景 | 处理 |
| :--- | :--- |
| 补出历史账单 | 使用幂等的单账期生成接口；拒绝未来账期 |
| 导入数据里的还款 | 作普通交易入账；未归属部分随负债余额下降自然冲减未归属欠款，不再另建无交易 `UNATTRIBUTED` 记录。需要补账单 / 合同核销时，仍可用无交易 `BILL` / `PREPAYMENT` 还款补齐 |
| 进行中的分期合同 | 建合同不建放款交易；已还期次可置 `SKIPPED`，中间提前还款用无交易 `PREPAYMENT` 表达 |
| 期初欠款 | 账务核心期初余额承载，落未归属桶 |

## 11. 读侧派生与展示

- **可用额度** = 授信额度 − 账户负债余额。**欠款分桶**：账单欠款 / 合同未来欠款 / 未归属欠款。
- **XIRR（合同维度）**：application query 只加载合同与全部计划，不加载还款记录。领域计算精确判断 `Σ 全部计划 expectedPrincipal == 合同本金`；`PENDING / PARTIALLY_PAID / PAID / SKIPPED` 全部参与计划现金流。普通还款、提前还款、优惠和无交易核销都不改变合同约定现金流指标。
- **状态协调**：还款创建、删除与更正通过 application settlement coordinator 推进或回退计划状态，并由合同聚合统一刷新合同状态；显式跳过或恢复由合同聚合直接处理；用户可在合同详情显式校验并按还款事实修复异常状态。账单生成与刷新只维护 `Bill` / `BillItem` 投影，不把账单明细状态写回计划或合同。
- **账单查询**：按月账单概要查询；日历页按明细 `repayment_date` 展示；**不做主动提醒**，查询不执行写入或差异检测。
- **待还金额**：只统计未核销明细，按本息费各自剩余相加再扣减优惠，逐条下限为 0。账单概要、按月账单概要与日历页月度汇总共用这一口径；待还本金是它的分量，不单独作为「待还」对外展示。
- **还款记录管理**：账单详情列该账单全部还款记录（含无交易、分期还款），合同详情列提前还款；还款时间统一读取还款记录。交易详情页修改还款交易时间、账单还款编辑页修改时间都经过信贷用例，同步维护关联交易；单独修改备注、还款账户或入账时间不改变还款时间。未归属还款必有账务交易，统一通过账户交易查看与管理，账户信贷详情不另列还款记录。
