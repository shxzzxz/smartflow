# 交易编排域与交易业务归属

SmartFlow 新增 `orchestration`（交易编排）域，负责在账务核心原语之上组织复杂交易场景、场景规则和可选状态。垫付的会计表达仍属于账务核心，但 AA 垫付、报销垫付、代付垫付及其跟踪方式属于 `orchestration`。[ADR-0019](0019-垫付作为统一账务原语.md) 中把垫付场景写入 owner 的规则由本决策替代。

账户垫付收款的顶层账务行为由 [ADR-0022](0022-账户垫付收款统一为应收收回.md) 收敛为应收收回；本决策中其余交易归属边界继续有效。

## Decision

- `orchestration` 管理复杂交易场景及其跨交易关系，使用账务核心的账户、交易、分项和过账能力。后续摊销也按同样方式进入该域，不为每个场景扩展 `BusinessPurpose`。
- 账务核心继续拥有 `advance`、`advanceCollection`、`advanceSettlement` 及对应的分项、分录、金额守恒、待收回、结清锁和余额规则。场景名称、AA 人数、逐笔或账户跟踪方式不进入账务核心。
- 交易业务归属只由 `owner_type` 与 `owner_id` 表达，指向至多一个上层业务实体。owner 可空；存在时两个字段必须同时存在。`owner_role` 不再属于 owner 契约，不能保存垫付场景、还款类型或其他业务状态。
- `owner_type` 使用 `<领域>.<聚合>` 形式的稳定值，例如 `credit.installment_contract`、`credit.repayment`、`orchestration.advance`。账务核心只存储和透传，不校验上层实体是否存在，也不根据 owner 改变过账。
- 垫付由 `orchestration` 的 `AdvanceCase` 表示。每笔逐笔或账户垫付都建立独立实例，场景、跟踪方式以及 AA 参与人数保存在该实例中，owner 指向其实例 ID。账户模式的收款使用普通应收收回，可一次覆盖同一应收账户下的多笔垫付。
- `orchestration` 允许按功能需要设置状态机，但不要求所有场景都有持久化状态。当前垫付的逐笔关闭状态可从账务事实派生，账户模式不建立全局关闭状态。
- 跨域写入仍由消费域 application 控制事务，通过本域 domain port 和 infrastructure adapter 调用账务核心 facade。账务核心不得依赖 `orchestration`。

## Considered Options

- 继续使用 `owner_role` 保存垫付场景和信贷还款类型：拒绝。该字段跨域承载了互不相关的语义，是重复状态，也会让用户修正场景时同时改变业务归属。
- 为 AA、报销、代付分别新增 `BusinessPurpose`：拒绝。它们使用相同的会计表达，不应改变分录结构或账务行为。
- 建立通用工作流引擎承载所有复杂交易：拒绝。当前只有具体场景规则和实例，没有足够证据支持通用流程抽象；共享范围和跨域调用方式已足够复用。
- 用独立表表达一笔交易多个 owner：拒绝。当前明确最多一个 owner，保留交易行上的单一引用更简单。

## Consequences

- 一笔交易可在没有 owner 的情况下直接记账；复杂场景通过所属业务域创建和校验 owner。
- `owner_type + owner_id` 不是交易组边界，不能替代 `parent_transaction_id`。同一交易组的子交易继承顶层交易的 owner。
- 场景信息修改不改变 owner；例如 AA 修正为报销时只更新 `AdvanceCase` 和相应金额事实。
- 交易详情的编辑、删除和路由由 owner 所属域的查询结果决定，不从 owner 字段推断场景。
- 账户模式的收款由账务核心按账户级应收收回事实维护，不持有 `AdvanceCase` owner；它不代表单笔垫付结清，也不建立全局关闭状态。该边界由 ADR-0022 确定。
- 旧 `owner_role` 数据迁移后删除。`advance.itemized`、`advance.account` 迁移为垫付实例归属；信贷角色由合同、还款记录和交易用途恢复。
