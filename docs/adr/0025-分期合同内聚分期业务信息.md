# 分期合同内聚分期业务信息

用户实际办理的是一笔分期业务，而不是在创建合同。但“分期”和“分期合同”不需要成为两个持久化主体：每笔分期由一份分期合同表达，分期合同同时承载该笔分期的业务类型、来源关系和合同配置。保留 `InstallmentContract` 作为聚合根，并把用户行为与接口命名对齐为具体分期场景。

## Decision

- `InstallmentContract` 继续作为信贷域聚合根，表示一笔分期业务及其合同安排。合同与分期一一对应、共用一个身份和生命周期，不新增独立 `Installment` 实体或表。
- `InstallmentContract.id` 继续作为分期、合同、账单明细、还款目标和账务业务归属使用的稳定身份；数据库继续使用 `installment_contracts` 和 `contract_id`。
- 用户可见语言和 application 用例按业务行为表达为“办理放款分期”“办理账单分期”“办理消费分期”，不再以“创建合同”作为用户入口。
- 分期类型只有三种：放款分期、账单分期、消费分期。删除 `InstallmentSourceType` 和 `sourceType`，由 `InstallmentType` 表达分期类型。
- 放款分期统一覆盖此前的贷款分期与现金分期。挂载贷款账户或信用账户只影响账单生成，不产生新的分期类型，也不再区分贷款分期与现金分期展示。
- 来源不作为独立维度。`installmentType` 决定来源事实的语义：
  - 放款分期指向借入交易；记录型放款允许没有来源引用。
  - 账单分期指向创建该分期的分期还款记录。
  - 消费分期指向购买交易。
- 合同保存一个可空 `sourceRefId`，来源事实同时保存合同引用，形成双向链接。来源事实一侧是权威关系，合同上的 `sourceRefId` 是聚合索引；两者必须在同一 application 事务中维护。
- 一项来源事实最多对应一份合同。账单分期和消费分期的 `sourceRefId` 必须非空；只有放款分期允许为空。账单还款记录上的 `generatedContractId` 与来源身份具有唯一约束。
- 删除 `disbursementAccountId`。放款入账账户属于借入交易，不属于合同；`liabilityAccountId` 才是合同挂载的负债账户。
- 合同整体状态 `ACTIVE / SETTLED` 继续属于 `InstallmentContract`；期次自身的 `PENDING / PARTIALLY_PAID / PAID / SKIPPED` 继续属于还款计划。整体状态由计划和实际还款事实投影得到。
- 放款交易和购买交易继续通过账务 `owner_type = credit.installment_contract`、`owner_id = installmentContract.id` 归属合同。
- 合同聚合拥有自己的还款计划集合。application 仍然负责跨聚合事实加载和事务边界，但不需要反复向合同行为传入外部计划列表。
- application 按用户实际行为和还款目标划分：
  - 放款分期与消费分期分别组织自己的交易、合同和计划创建；消费分期退款属于消费分期行为。
  - 账单分期是一种账单还款 implementation，与普通账单还款共同位于账单还款 module，共享账单分配、核销和状态刷新。
  - 分期提前还款以合同为目标，账户还款以信用账户为目标并创建统一还款记录；三者共享 settlement implementation。
- 普通应付账户还款属于账务能力，直接使用账务的交易创建与编辑 interface。信贷域删除 `createLiabilityRepayment`、`editLiabilityRepayment` 和 `loadLiabilityRepaymentEditView`，不再提供绕过信贷还款事实、只修改负债余额的旁路。

## Considered Options

- **把聚合根和主表全局改名为 `Installment`**：拒绝。该改名涉及大量领域、application、infrastructure、备份、迁移和测试文件，但不会改变合同与分期的生命周期，也不会减少核心业务规则；收益不足以抵消机械迁移风险。
- **新增一个分期实体，与合同一对一关联**：拒绝。合同与分期始终一一对应、同生共死，没有独立创建、删除或替换合同的业务需求。拆成两个主体只会增加同步与不一致风险。
- **继续由合同同时表达能力类型、来源和合同配置，但保留现有表达**：拒绝。保留合同聚合是合理的，但“类型 + 多个互斥可空引用”的隐式联合类型会产生大量非法状态，必须收口。
- **保留贷款分期和现金分期两个类型**：拒绝。两者共享借入来源与合同计划规则，账户类型已经决定账单生成差异，没有独立生命周期或业务不变量。
- **建立通用来源实体或通用来源类型**：拒绝。分期类型已经决定来源结构；新增来源类型会形成第二个一一对应维度，并重新引入与分期类型不一致的可能。
- **将账单分期作为独立顶层 module**：拒绝。账单分期的目标是核销账单，与普通账单还款共享分配和状态投影；创建合同只是该还款行为的内部实现。
- **把普通负债还款包装在信贷还款 module 中**：拒绝。它不创建信贷还款记录，也不参与账单、分期或未归属欠款，属于账务交易能力。

## Consequences

- 不重命名 `installment_contracts`、`InstallmentContract`、`contractId` 或 `contract_id`；本轮变更集中在来源表示和 application seam。
- 来源映射从原有 `source_type` 与四个引用字段迁移为 `installment_type` 与单个 `source_ref_id`，并为来源关系补齐唯一约束和一致性校验。
- `bill_items.contract_id`、计划和其他子表继续使用既有合同身份；账单明细和还款目标无需全局改名。
- `RepaymentType.installment` 的语义应明确为账单分期，避免与用户业务语言“分期”混淆；是否重命名 enum 由对应实施 issue 决定。
- 计划引擎与利率计算不感知分期类型；类型只决定来源事实、账单归集和 application 编排。
- 查询模型和备份恢复继续使用合同身份，但用户可见文案使用“分期”；新增 `installmentType` 与 `sourceRefId` 后需要同步更新快照和校验。
- 本决策保留 [ADR-0005](0005-账单为中心的信贷还款模型.md) 的账单中心还款模型，并保留 [ADR-0024](0024-消费分期作为购买与融资一体的信贷场景.md) 的消费分期业务边界；仅调整合同的业务信息表达和 application seam。
