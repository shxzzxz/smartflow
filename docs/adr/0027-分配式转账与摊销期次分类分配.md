# 分配式转账与摊销期次分类分配

> 期次分类分项继续有效；计划级退款、净额重算和终止退还的边界见 [ADR-0028](0028-摊销退款与终止作为计划级编排事实.md)。

组合支付需要一笔转账由多个账户共同出资，摊销也需要把同一笔预付费用或预收收入分配给多个收入或支出分类。现有账务核心已经用交易分项表达多个分类和多条结算腿，但转账指令仍被压成单一转出、单一转入，摊销计划也只保存一个分类。继续禁止摊销分项会丢失业务事实。

## Decision

- 普通转账仍使用 `BusinessPurpose.transfer`，不新增预付、预收或摊销业务用途。
- 转账指令分别保存转出账户分配和转入账户分配；每个维度合计必须等于转账金额，两个维度的账户集合不得重叠。
- 保留单一账户对单一账户转账的便捷构造方式。手续费只允许在单一转出账户时随转账记录；多账户出资的手续费归属尚未成立时不得静默选择某一账户。
- 摊销计划创建命令保存资金账户分配和确认分类分配。预付费用的资金分配位于转出侧，预收收入的资金分配位于转入侧；递延账户仍为单一账户。
- 计划创建时把确认分类分配物化为每个摊销期次的分类分项，并随期次持久化。后续生成不再根据可变算法重新推导分类构成。
- 每个期次的分类分配合计等于该期金额；全部期次的同一分类合计等于计划创建时该分类的分配金额。
- 正常表单和分项表单都可以创建摊销。普通模式形成单元素分配，分项模式形成多元素分配。
- 提前终止时，默认按尚未确认的分类总额和实际退款比例确认剩余金额；调用方明确指定终止确认分类时，可以把本次终止确认归入单一分类。

## Considered Options

- 新增预付、预收或摊销账务行为：拒绝。正常转账、支出和收入已经完整表达借贷结构，新增用途会把场景差异扩散到分项、编辑、导入和查询规则。
- 把多账户初始付款拆成多笔转账：拒绝。一笔实际收付是一个业务事件；拆分会制造多笔顶层交易，并让编辑、删除和详情展示失去单一事实。
- 只在计划上保存分类比例并在生成时实时拆分：拒绝。算法调整会改变历史计划的未来交易，无法保证计划语义稳定。
- 为每期保存独立可编辑分类配置：暂不采用。当前需求是整份计划确定分类构成；期次已经保存分配事实，未来需要逐期差异时可以在同一模型上开放编辑。

## Consequences

- 转账创建、编辑、读取和指令往返都必须保留多条转出、转入分项。
- 摊销期次需要单独的分类分配记录；单一分类计划迁移后为每个期次生成一条分配。
- 计划和备份结构发生持久化变化，需要新增相邻 schema 迁移与逻辑备份迁移。
- 多账户手续费仍要求记录为单独事实；在出现明确的费用归属规则前，转账原语拒绝隐式选择账户承担手续费。
