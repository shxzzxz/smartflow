# 垫付作为统一账务原语

AA 垫付、代付垫付与报销垫付共享同一套账务表达。原先只服务于报销的“垫付、到账、结束报销”改为通用的 `advance`、`advanceCollection`、`advanceSettlement`，具体业务场景通过交易组的稳定归属区分。业务场景不是新的账务行为，也不能改变分录结构。

## Decision

- 逐笔垫付使用 `ownerType = advance.itemized`，`ownerId` 为顶层垫付交易 ID，`ownerRole` 为 `aa`、`onBehalf` 或 `reimbursement`。垫付到账、垫付结清与退款作为其子交易，并继承同一 owner；到账与结清还必须使用父交易的应收账户。
- 账户垫付使用 `ownerType = advance.account`，`ownerId` 为应收账户 ID，`ownerRole` 仍为上述封闭场景。垫付、到账、结清都是顶层交易，不建立父子关系，也不追踪到某笔垫付。
- 账务原语泛化不改变账户画像：报销账户继续使用 `ledger.reimbursement`，普通应收账户继续使用 `ledger.receivable`，两者底层均为 `asset / receivable`。借出、收回和垫付等应收能力由账户类型与子类型判断，不绑定具体画像。
- 同一笔垫付不能同时使用逐笔和账户两种管理方式。owner 只作为业务聚合索引；账务核心保存并透传 owner，不根据 owner 改变过账规则。
- 垫付交易同时保存分类总额分项和自承担分项。分类总额按分类分配，合计等于 `primaryAmount`；自承担分项合计等于交易总额减垫付应收。账务核心通过统一分担策略计算创建与退款所需的 AA、自承担和垫付构成，并作为显式分项持久化；页面不复制分担规则。
- 垫付金额由 `receivable` 分项汇总。过账只使用自承担分项、垫付应收分项和结算分项；分类总额分项保留业务分类信息，不直接产生分录。
- 退款先计算本次退款中的自承担与垫付构成，自承担部分冲减原支出分类，只有垫付构成减少应收；垫付到账继续减少应收。逐笔垫付按垫付构成与到账金额校验剩余应收。账户垫付的到账和结清只按账户与场景记录独立交易，不校验与账户汇总余额的金额关系。
- 逐笔结清少收时，自己承担部分落入调用方选择的任意有效普通支出分类，不要求属于原垫付分类；坏账部分使用 `advanceBadDebtExpense` 角色计入系统内置坏账损失分类；两者保留语义差异。多收时计入“垫付补偿”。
- 不新增垫付单表，不给交易分项增加 owner，也不增加分摊表。账户级汇总状态是按 `(应收账户, 场景)` 对顶层交易事实的派生查询。

## Consequences

- AA、代付和报销共享过账、编辑、删除、导入与统计能力，产品层只负责场景交互并调用账务核心提供的分担结果。
- 账户垫付允许先记录到账或结清事实而不被账户汇总余额阻断，代价是账户级待收余额可能暂时为负，读侧需要如实展示。
- 旧 `reimbursementAdvance`、`reimbursementReceipt`、`reimbursementClose` 分别迁移为 `advance`、`advanceCollection`、`advanceSettlement`；历史交易迁为逐笔垫付并标记 `reimbursement`。
