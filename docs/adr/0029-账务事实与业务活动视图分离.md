# 账务事实与业务活动视图分离

SmartFlow 的用户列表同时需要精确的账户影响，以及按分期、摊销等业务组织活动。交易组、`BusinessPurpose` 和 owner 都无法单独表达用户可见业务活动的稳定边界，因此业务活动由读侧 application 按场景组合，而不是成为新的持久化交易模型。

## Decision

- 账务核心继续以交易、交易分项和分录作为余额、统计与预算的唯一事实来源。顶层交易、交易组和现有 owner 语义保持不变。
- 用户视角的“业务活动”是只存在于读侧的查询投影。它可以关联一笔或多笔账务交易，但不持久化金额、状态或业务字段。
- 不新增继承式交易模型，不给 `transactions` 增加业务活动锚点字段，也不建立通用锚点表。锚点由每个业务活动来源根据所属业务事实确定，`anchorAt` 等于锚点交易业务时间。
- 新增 `application/transaction_view` 作为跨域读侧能力。每个业务活动来源负责自己的锚点规则、筛选口径、时间范围和分页；公共查询层选择来源、归并排序结果并为最终读模型批量加载锚点交易。需要账务摘要的 source adapter 通过通用账务查询获取所需事实，再映射统一摘要。
- `BusinessActivitySource` 是 `transaction_view` 内部的编排 seam。各业务域不实现或依赖该接口，也不定义 transaction view 专用的摘要 DTO；它们提供可独立复用的 application query。consumer-side source adapter 位于 `application/transaction_view/business_activity/source/`，负责把业务域 read model 与账务核心已有事实映射为统一业务活动摘要。
- 业务域锚点查询必须提供有界分页和作用域变更流。摘要批量加载复用锚点交易及所属业务域的通用查询结果，不重复构造账务聚合链路；来源监听只覆盖自身锚点与摘要依赖，不假设账务交易表变化能够代表业务事实变化。
- 交易详情先通过 `BusinessActivityItem` 获取当前交易的业务含义和局部事实；只有当前交易是活动入口时才加载活动摘要。Feature 侧通过私有业务场景 seam 组合业务模块、权限和动作，不把跨域查询散落在 ViewModel。
- 交易明细视图和业务活动视图是两种独立用户语义。交易明细视图复用现有交易查询，按实际分录命中并展示父交易和子交易；业务活动视图从锚点交易进入并组合少量业务摘要。
- 每个业务活动来源必须先完成全部筛选和游标条件，再执行 `LIMIT`。公共层不得对已分页结果补做业务过滤。
- 记录型分期和无交易还款不进入以交易为锚点的业务活动视图。

## Considered Options

- 使用通用交易字段承载所有业务扩展信息：拒绝。不同业务聚合的状态、计划和进度不属于账务交易。
- 建立交易基类和按业务类型派生的持久化子类：拒绝。这会形成多态数据模型并把业务生命周期重新耦合进账务核心。
- 在交易表增加锚点标记：拒绝。业务视图语义会透传到账务写入和交易重写路径。
- 建立通用锚点表：拒绝。查询更快，但会产生需要跨所有业务写路径同步的第二份关系事实。
- 从全部账务交易查询后再在应用层合并和筛选：拒绝。无法保证过滤后的页大小、游标和 `hasMore` 正确。

## Consequences

- `domain/ledger` 不依赖信贷、交易编排或其他业务域；场景联查只出现在各自业务活动来源的读侧实现中。
- 业务域 application query 拥有本域锚点、筛选、业务事实和变更来源；`transaction_view` 只编排、映射和组合账务核心已有摘要，不直接解释兄弟业务域规则。
- 新增业务活动需要增加来源、锚点规则和摘要，不修改公共分页归并，也不修改账务过账规则。
- 业务活动分页需要对各来源做有界查询和归并，来源数量成为读侧需要观测的性能维度；当性能证据充分时，只能在来源接口之后优化查询形态。
- 列表展示使用统一视觉基线，业务差异通过有限的摘要事实表达，完整计划、合同和还款页面保持独立。
- 交易详情页面以具体交易 ID 为用户入口；业务活动锚点只用于列表进入交易详情，完整业务聚合使用自身页面和身份。
- 交易明细视图监听账务事实，并只为当前页出现的业务活动补充所属业务域的 scoped watch；业务活动视图也按当前来源组合 scoped watch，不监听全部数据库表。
