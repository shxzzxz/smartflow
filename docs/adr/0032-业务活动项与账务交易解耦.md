# 业务活动项与账务交易解耦

业务活动与账务核心处于不同语义层级。用户交互和业务追踪以 `BusinessActivity` 为维度，账务交易是同一业务事实在账务核心中的投影；把业务活动项限定为一笔交易，会把展示入口当成业务身份，也无法表达一个可由多笔交易承载的业务事实。

## Decision

- `BusinessActivity` 由活动身份、一个 `origin` 业务活动项、零到多个 `followUp` 业务活动项及一份活动摘要组成。业务活动是读侧组合，不要求持久化通用活动实体。
- `BusinessActivityItem` 表示活动内可独立识别的业务事实，是名称、图标及编辑、删除等业务操作的作用边界。它持有 `activityKey`、活动项身份和 `origin / followUp` 角色，可以关联零到多条账务交易投影。
- `BusinessActivityItemRole` 固定为 `origin` 和 `followUp`。`origin` 定义活动身份并唯一存在；`followUp` 推进已有活动，可以有多项。
- 一项业务活动项可以聚合多条账务交易投影。摊销终止是一条 `followUp` 活动项，可以同时包含终止退还和终止确认两条交易；交易明细仍分别展示两条交易的局部业务含义，但编辑、删除等整体操作作用于该活动项。
- 业务活动视图以 `BusinessActivity` 为单位返回结果。普通支出等没有额外业务身份的交易由 `transaction_view` 直接基于账务交易构造活动读模型，活动标识和 `origin` 活动项标识均使用交易身份，不增加持久化结构。
- 有额外稳定业务身份的场景使用自身身份作为活动标识，例如垫付使用 `AdvanceCase.id`，分期使用合同 ID，摊销使用计划 ID。账务交易不是业务活动的默认身份来源。
- 业务活动项角色和所属活动由业务域提供；`transaction_view` 只负责映射与组合，不从交易业务用途、领域枚举或 UI 展示状态自行推导角色。普通账务交易所形成的隐式活动由 `transaction_view` 自己构造。
- 账单还款和未归属还款是各自活动的 `origin`，业务目标分别为账单和账户；提前还款是合同活动的 `followUp`。无交易的分期还款是否形成独立业务活动另行讨论。
- 账务核心仍可被统计、预算钻取等关注实际账务影响的场景直接访问。业务活动视图不成为账务事实的唯一读取入口。

## Considered Options

- 使用活动入口布尔值或由前端根据业务活动项 kind 推导角色：拒绝。入口描述页面导航，kind 描述业务事实，无法稳定表达活动身份关系。
- 保持一个 `BusinessActivityItem` 对应一笔账务交易：拒绝。摊销终止等业务事实可以由多笔交易共同承载。
- 用交易作为业务活动或业务活动项的默认身份：拒绝。普通场景可以共享交易身份，但分期、摊销和垫付等业务活动拥有独立稳定身份。
- 为普通支出强制建立持久化业务活动结构：拒绝。其业务属性和交易一一对应，读取时构造活动模型即可。
- 要求所有业务活动都通过业务活动视图访问：拒绝。统计等场景需要直接读取实际账务交易与分录。

## Consequences

- `BusinessActivityItem` 不再以 `transactionId` 作为公共必填字段；交易投影成为活动项上的零到多条关联事实。
- 交易明细查询需要同时得到活动项身份、所属活动和当前交易对应的局部投影，以区分“显示哪条交易”和“操作哪个业务活动项”。
- 业务活动视图与交易明细视图采用不同的查询方向：前者从活动项聚合交易投影，后者从交易反查活动项及其局部投影。
- 业务活动项和交易投影的读模型仍只存在于应用读侧，不新增通用业务活动表、锚点字段或数据库外键。
- 已有以交易为活动锚点的接口需要逐步迁移；迁移期间可以保留交易展示字段，但不得再由交易关系定义业务活动项角色。
