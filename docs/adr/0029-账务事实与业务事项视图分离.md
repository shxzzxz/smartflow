# 账务事实与业务事项视图分离

SmartFlow 的用户列表同时需要精确的账户影响，以及按分期、摊销等业务对象组织的事项。交易组、`BusinessPurpose` 和 owner 都无法单独表达用户可见事项的稳定边界，因此业务事项由读侧 application 按场景组合，而不是成为新的持久化交易模型。

## Decision

- 账务核心继续以交易、交易分项和分录作为余额、统计与预算的唯一事实来源。顶层交易、交易组和现有 owner 语义保持不变。
- 用户视角的“业务事项”是只存在于读侧的查询投影。它可以关联一笔或多笔账务交易，但不持久化金额、状态或业务字段。
- 不新增继承式交易模型，不给 `transactions` 增加业务事项锚点字段，也不建立通用锚点表。锚点由每个业务事项来源根据所属业务事实确定，`anchorAt` 等于锚点交易业务时间。
- 新增 `application/transaction_view` 作为跨域读侧能力。每个业务事项来源负责自己的锚点规则、筛选口径、时间范围和分页；公共查询层只选择来源、归并排序结果并批量加载摘要。
- `BusinessItemSource` 是 `transaction_view` 内部的编排 seam。各业务域不实现或依赖该接口，而是提供独立的交易视图 application query；consumer-side source adapter 位于 `application/transaction_view/business_item/source/`，负责把业务域 read model 映射为统一业务事项页。
- 业务域交易视图查询必须同时提供有界锚点分页、最终页摘要批量加载和作用域变更流。来源监听只覆盖自身锚点与摘要依赖，不假设账务交易表变化能够代表业务事实变化。
- 交易详情的 owner 事实通过独立 owner query seam 获取；feature 侧再通过私有 owner UI/action seam 组合业务模块、权限和动作，不把跨域查询散落在 ViewModel。
- 账务影响流和业务事项流是两种独立用户语义。账务影响流复用现有交易查询，按实际分录展示父交易和子交易；业务事项流从锚点交易进入并组合少量业务摘要。
- 每个业务事项来源必须先完成全部筛选和游标条件，再执行 `LIMIT`。公共层不得对已分页结果补做业务过滤。
- 记录型分期和无交易还款不进入以交易为锚点的业务事项流。

## Considered Options

- 使用通用交易字段承载所有业务扩展信息：拒绝。不同业务聚合的状态、计划和进度不属于账务交易。
- 建立交易基类和按业务类型派生的持久化子类：拒绝。这会形成多态数据模型并把业务生命周期重新耦合进账务核心。
- 在交易表增加锚点标记：拒绝。业务视图语义会透传到账务写入和交易重写路径。
- 建立通用锚点表：拒绝。查询更快，但会产生需要跨所有业务写路径同步的第二份关系事实。
- 从全部账务交易查询后再在应用层合并和筛选：拒绝。无法保证过滤后的页大小、游标和 `hasMore` 正确。

## Consequences

- `domain/ledger` 不依赖信贷、交易编排或其他业务域；场景联查只出现在各自业务事项来源的读侧实现中。
- 业务域 application query 拥有本域锚点、筛选、摘要和变更来源；`transaction_view` 只编排和映射，不直接解释兄弟业务域规则。
- 新增业务事项需要增加来源、锚点规则和摘要，不修改公共分页归并，也不修改账务过账规则。
- 业务事项分页需要对各来源做有界查询和归并，来源数量成为读侧需要观测的性能维度；当性能证据充分时，只能在来源接口之后优化查询形态。
- 列表展示使用统一视觉基线，业务差异通过有限的摘要事实表达，完整计划、合同和还款页面保持独立。
- 交易详情页面以具体交易 ID 为用户入口；业务事项锚点只用于列表进入交易详情，完整业务聚合使用自身页面和身份。
- 账务影响流只监听账务事实；业务事项和交易详情在交易事实之外，按当前来源或 owner 组合各自的 scoped watch，不监听全部数据库表。
