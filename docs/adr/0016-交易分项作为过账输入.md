# 交易分项作为过账输入

账务核心此前只把账户事实保存在分录上，交易分项仅记录分项类型与金额。读写两侧都必须从分录反推业务事实，而这类推断依赖「每个角色只有一条分录」的前提，组合支付与多品类支出会直接打破它。本决策把交易分项重新定位为过账输入的完整快照，由此在账务核心内部确立交易层与账务层的边界。

## Decision

- 交易分项是交易在业务语言中的完整表达，携带分项角色、金额与相关账户。`transactions` 与交易分项共同表达完整交易信息；分录只保证账务正确，服务余额、统计与预算。
- 过账方向为 `用户命令 → 指令解析 → 交易分项 → 分录`。系统账户由指令解析在写入时填入分项，不由命令携带；分项是解析后、过账前的完整输入快照，不是用户原话。
- 分项角色决定该角色是否携带账户，账户期望性按角色固定、不逐行可变。用户账户角色必填，规则账户角色恒空并由 `system_key` 解析。「无账户」属于用户账户角色，按既有语义填幽灵账户。
- 分项角色按语义划分，不按账务行为划分。账务行为已由交易持有，角色与账务行为的合法组合由过账规则约束。
- 凡是不能由本交易自身推出的事实，必须成为分项。报销差额、报销应收核销额、退款冲销科目据此落库；期初余额与余额调整的分项金额带符号存储。
- 交易分项与分录不同构，二者合计不相等。过账规则会补出命令中不存在的腿（报销差额、手续费支出、利息支出、期初权益），也会合并同账户的腿。不得对分项施加借贷平衡校验。
- 报销支出分类由交易列下沉为分项。账户引用集中在交易分项与分录两处。
- 分项由过账链路整体重建，不逐行 diff，也不作为自身重建的输入。只修改备注、交易时间、入账时间、对手方等不影响账务表达的字段时，不得触碰分项。

## Considered Options

曾考虑取消交易分项表，改为在分录上增加角色列并逐腿展开。该方案被否决：带手续费的转账中，业务语言是「转出 100、转入 100、手续费 5」，账务语言是「转出账户 credit 105」，两者互相翻译不出；组合支付时手续费属于哪个付款账户的事实并不存在，逐腿展开会迫使系统虚构归属。转账、还款、应收收回与结束报销四处均存在同类合并。

## Consequences

角色成为可读取的事实而非推断结果，读写两侧的分录反推随之取消，其中写路径依赖分录顺序的反推是本决策的首要收益。组合支付与多品类支出不再需要结构变更，只需增加分项行。

分类分配与结算分配是两个彼此独立的守恒维度：各自合计等于交易金额，但不记录“哪个账户支付了哪个分类”。支出与报销垫付都可同时包含多条分类分配和多条付款分配。

退款同样持有独立的分类退款分配与到账分配。每个分类的累计退款不得超过父交易在该分类上的原始金额；到账账户不受原付款账户及其金额限制。普通支出退款直接冲减对应支出分类，报销垫付退款在业务语言中保留分类退款分配，但账务上减少报销应收。

结束报销少收时，差额支出必须由用户在退款后的剩余分类范围内明确分配，不按比例静默推断；报销到账和结束报销的实际到账金额可以分配到多个结算账户。

代价是存量分项需要一次性回填账户，回填仍依赖推断——但存量全部是单腿交易，「每个角色一条分录」的前提当下成立，且可用过账复现全量校验。两条性质长期守住边界：`指令 → 分项 → 指令` 往返恒等保证交易层无损，`(交易, 分项) → 分录` 可复现且幂等保证账务层确定。
