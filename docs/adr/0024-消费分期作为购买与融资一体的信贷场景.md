# 消费分期作为购买与融资一体的信贷场景

SmartFlow 将用户购买商品或服务时同时形成购买交易和分期合同的行为定义为消费分期。采用该模型，是为了按普通组合支付表达消费支出和退款，同时复用现有分期产品、还款计划与信贷账单追踪融资本金。

## Decision

- 消费分期从新建交易页的支出场景进入，场景名称为“消费分期”。该名称属于 feature 层业务场景，不是新的账务行为；购买交易仍使用 `dailyExpense`。
- 消费分期由信贷 application 统一编排购买交易、合同与退款还本，账务核心只负责交易、分录、余额与过账规则。整个创建或退款用例共享一个顶层事务，任一步失败均整体回滚。
- 一笔购买交易最多对应一个消费分期合同，合同只挂载信用账户。购买金额可按普通支出方式分配到多个支付账户，再从分配中的信用账户指定分期账户；该信用账户的分配额是融资本金且必须大于零。系统不为单笔购买自动创建信用账户，也不支持把一笔购买拆成多个合同。
- 购买交易确认全额消费支出，并以合同为业务归属。融资本金由合同还款计划进入信用账户账单，购买交易本身不计入消费净额，避免购买金额与合同期次双算。
- 消费分期复用现有分期产品与阶段配置。购买时把产品规则复制为本笔合同条款，融资本金由成交价与首付款派生，并配置期数、利率、手续费和日期等本笔参数；后续修改产品不影响既有合同。
- 合同借款日仅在创建时确定：草稿未填写时，进入分期配置以当时交易时间预填；用户可独立修改草稿值，但不回写交易时间。合同提交后借款日不可修改，后续交易时间变化也不影响借款日。
- 利息和手续费只存在于合同计划，实际还款时才按实际发生金额确认费用。购买交易只包含成交价。
- 消费分期退款复用普通组合支付退款。退向分期负债的金额形成“退款还本”，不修改合同原始本金，并与 `PREPAYMENT` 保持独立业务身份；提前还款和退款还本共同作为本金扣减输入现有计划计算。
- 退款还本以退款业务日之后、即计划还款日严格晚于退款日的未还本金为上限，末期还款日当天及之后均不形成退款还本。系统不自动拆分超额退款；分期账户分配超限时应拒绝提交，超出部分由用户明确分配到资产账户。
- 退款还本使合同剩余本金归零时，合同进入 `SETTLED`。正常还清与退款终止共用合同状态，终止原因由退款还本事实派生，不增加 `REFUNDED` 状态。
- 成交价、分期账户及各支付账户分配不能通过普通交易编辑修改。尚无还款和退款时，可删除整个交易与合同后重建；已有历史时禁止通用删除，后续若需要更正，必须使用专用用例。
- 不新增商品明细实体。商品或服务通过分类、对手方、标签、交易备注和合同名称表达。

## Considered Options

- 将消费分期建模为普通信用消费，事后再转换为账单分期：拒绝。消费分期在购买时即存在合同，事后转换会丢失真实融资来源并造成账单口径错位。
- 复用放款类分期合同：拒绝。放款会形成资产流入，而消费分期确认商品支出并直接形成负债，没有等额现金流入。
- 为“消费分期”增加新的 `BusinessPurpose`：拒绝。账务行为仍是普通支出，业务场景应由交易页 ViewModel 分发到信贷用例。
- 把退款还本记录成 `PREPAYMENT`：拒绝。退款不是用户支付还款，两者的来源、费用结算、编辑删除和审计语义不同。
- 为退款另建一套还款计划算法：拒绝。业务事实应分离，但本金扣减、计息和期末本金处理应复用现有计划引擎。

## Consequences

- 账单消费净额必须排除消费分期购买交易；合同计划是该融资本金在账单中的唯一来源。
- 合同来源需要区分消费购买，合同需要引用购买交易；退款还本需要以退款交易和合同为逻辑引用保存，不使用数据库外键。
- 计划计算需要同时消费提前还款与退款还本产生的本金扣减，并继续保证计划本金与合同本金守恒。
- 测试至少覆盖交易与合同原子回滚、购买交易不进入消费净额、退款还本日期边界与表单限额、退款编辑删除后的计划重算，以及退款清零后的合同状态。
