# 摊销退款与终止作为计划级编排事实

现有摊销只能把未确认余额通过转账退回，无法表达用户按净额重新分摊全部期次的退款，也把终止退款与普通退款混为一体。摊销退款因此由交易编排域作为计划级事实管理：正常退款携带分类和结算分配，减少净摊销金额并重算期次；终止独立携带分类退还和结算退还分配，并将未退还的剩余分类立即确认。

## Decision

- 摊销计划保存原始金额、分类分配、资金账户分配、递延账户、节奏和期次。计划不再保存对手方、备注、不计收支或不计预算配置，也不提供计划级批量修改这些交易字段的能力。
- 摊销退款保存分类分配和结算分配，两者合计相等。分类分配用于减少摊销基数，不产生重复冲减分类的退款分录，也不包含退款手续费。
- 净摊销金额等于原始金额减累计摊销退款。每次退款重新计算全部期次；已生成确认交易保持 ID 并改写当前事实，零金额期次不生成交易。
- 摊销终止与摊销退款分离。终止分别接收分类退还和结算退还，二者合计等于实际退还金额；未被退还的分类余额生成终止确认支出或收入。
- 初始收付、正常退款和终止退还继续使用转账原语；期次确认和终止确认继续使用日常支出或收入原语。账务核心不新增摊销退款账务行为，也不把退款扩展为任意转账的子交易。
- 所有摊销交易保持独立顶层，通过 `owner_type = orchestration.amortization` 关联计划。摊销业务通过读取投影覆盖普通转账的业务名称和分类展示。
- 摊销计划、期次、退款和终止共用一张摊销分项表，使用 `subject_type / subject_id / dimension` 表达归属和分配维度，避免与账务核心的 `owner_*` 和 `parent_*` 语义混淆。

## Considered Options

- 扩展通用退款使其接受转账父交易：拒绝。退款会变成任意反向资金流，父交易分类推导、退款子交易和计划重算会混在同一原语中。
- 只保存退款结算分配，期次分类按比例实时推导：拒绝。退款用户需要显式填写分类分配，且期次分类和舍入结果必须作为稳定当前事实保存。
- 把终止当作一次较大的摊销退款：拒绝。终止同时包含剩余分类退还、实际资金退还和未退还分类的立即确认，与正常退款后继续摊销的结果不同。
- 为计划、期次、退款和终止分别建立结构相同的分项表：暂不采用。所有分项共享账户金额结构，统一表配合显式分配维度即可保持简单，同时由应用规则校验各对象自己的守恒条件。

## Consequences

- 摊销退款、终止、期次和分项需要新的持久化结构，并迁移现有单次终止退款和期次分类分项。
- 已生成确认交易需要支持由摊销用例原子改写或删除；普通交易详情仍可逐笔维护交易时间、入账时间、备注、对手方、标签和统计/预算配置。交易业务时间独立于期次应摊销日期，修改交易时间不重算计划。
- 交易列表和分类筛选需要识别计划所属转账，并从摊销业务分项投影分类和业务名称，不能退回普通转账展示。
- 计划删除、退款修改、退款删除和终止删除必须由摊销 application 协调全部 owner 关联交易，账务核心不承担跨域级联。删除终止时，终止日之后已经到期的期次立即恢复并补齐；删除退款只撤销该笔退款；计划删除同时删除全部 owner 关联交易。
