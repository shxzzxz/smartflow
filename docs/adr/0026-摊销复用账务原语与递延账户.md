# 摊销复用账务原语与递延账户

预付费用和预收收入都需要把实际收付、逐期确认与提前退款分开表达。它们可以由现有转账、支出和收入原语完整过账，不需要为“预付”“预收”“摊销”分别增加账务行为。

## Decision

- 新增 `asset / prepaidExpense` 预付费用账户和 `liability / deferredIncome` 预收收入账户，分别使用 `ledger.prepaidExpense`、`ledger.deferredIncome` 账户画像。
- 初始预付或预收使用普通转账原语：预付从资金账户转入预付账户，预收从预收账户转入资金账户。
- 每期确认继续使用普通支出或收入：预付账户作为支出账户，预收账户作为收入账户。
- 提前退款使用普通转账，不把未确认的递延余额当作已确认收支退款。
- 摊销场景由 `orchestration` 管理。交易使用 `owner_type = orchestration.amortization`，`owner_id` 指向摊销计划；账务核心不新增 `BusinessPurpose` 或 `TransactionRole`。
- 每期按用户选择的日、月或年间隔等额确认；最后一期承担最小货币单位尾差。日期以首期日期为锚点计算，避免月末日期漂移。
- 计划保存整组默认的 `isExcludedFromStats`、`isExcludedFromBudget`。初始转账、确认和退款交易生成时复制该默认值，之后每笔交易自身字段是生效口径；计划可以显式批量覆盖现有交易。
- 提前终止以终止自然日为界。终止日之后的自动确认交易删除，之后尚未生成的期次取消；终止日当天保留。终止时确认金额为终止时计划剩余递延余额减实际退款，再用转账退回实际退款。
- 自动生成由 `AppTask` 幂等补齐，不保证后台准时执行。数据库继续不使用外键，计划、期次、账户和交易引用由 domain/application 校验。

## Considered Options

- 新增预付、预收、摊销三个账务行为：拒绝。它们的借贷结构已由转账、支出和收入完整覆盖，新增行为会把场景扩散到分项、编辑、导入和查询规则。
- 将预付费用复用为应收、预收收入复用为应付：拒绝。预付和预收不是往来债权债务，复用会暴露错误的收回、还款等账户能力。
- 为每笔计划建立父子交易组：拒绝。初始收付、逐期确认和退款是独立业务事实；计划使用 owner 关联，不改变账务核心的一层父子语义。

## Consequences

- 普通支出、收入、转账仍是账务行为；账户子类型与账户画像表达递延余额性质。
- 转账创建和编辑接口需要携带收支、预算两个交易配置，手续费按该笔转账自身配置参与统计和预算。
- 转账创建接口的两个配置默认 `false`；编辑接口使用可空参数，`null` 表示保留当前配置，避免未传字段时意外重置。
- 摊销计划拥有持久化期次和生成交易引用，任务、重复执行和终止清理可以保持幂等。
- 交易详情根据 owner 路由到摊销计划；计划生成的交易不能绕过计划修改金额、账户或日期。
