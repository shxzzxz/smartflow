# 页面动态渲染与业务行为分发

SmartFlow 的复杂页面通过路由参数获得最小身份信息，例如 `transactionId`、`accountId` 或初始化模式。页面动态渲染由页面级 ViewModel 产出的 view state 控制；页面上的保存、删除、改字段、切换口径等用户事件也由页面级 ViewModel 接收。

当页面事件需要根据业务类型、账务行为或业务归属调用不同 application service 时，分发逻辑默认作为对应 ViewModel 的私有实现细节存在。只有当多个页面已经稳定复用同一套页面无关动作协议时，才考虑提升为共享 handler 或策略对象。

交易相关页面中，`BusinessPurpose` 用于驱动退款、报销等账务流图原语相关入口；`transactions.owner_*` 只表达业务归属，用于 ViewModel 在必要时把页面事件转换为具体业务域 command，例如分期放款转为合同更新、分期还款转为还款编辑。

## Considered Options

- 仅靠路由传参控制页面：拒绝。路由只应提供身份信息或初始化信号，不应承载复杂渲染或业务分发逻辑。
- 让页面 widget 直接维护具体业务域分支：拒绝。页面会同时承担渲染判断、业务归属解析和 command 转换，难以测试和演进。
- 继续保留公开 `TransactionActionPolicy`：拒绝。现有 policy 同时混合了详情页字段、横幅、路由控制，以及交易动作到业务域接口的转换，边界容易再次膨胀。
- 引入公开策略模式处理所有渲染和行为差异：暂不采用。当前差异还没有大到需要公开策略契约；过早抽象会增加类层级并预支未来需求。
- 用组件工厂处理业务行为分发：拒绝。组件拆分适合 UI 结构差异，不适合作为跨业务域 command 分发机制。

## Consequences

- View 渲染页面级 view state，并把用户事件转发给页面级 ViewModel。
- 页面上的 banner、字段可编辑状态、编辑入口、按钮显示、局部禁用原因等属于 view state，不进入公开策略对象。
- 页面事件到 application command 的转换属于 ViewModel 职责；其中依赖业务归属或类型的分发逻辑默认保持私有。
- `feature/` 可以 import 相关业务域 application service；domain 不感知 feature、ViewModel 或其私有分发逻辑。
- 业务域 service 继续负责写入与一致性，ViewModel 只负责页面事件到应用服务入口的转换。
- 组件工厂只用于拆分差异明显的 UI 结构，不作为业务行为分发机制。
