# 发布前持久化基线契约

> 版本演进说明：本 ADR 确定 v49 / `backupSchemaVersion` 1 为首个正式基线；当前 schema 与备份版本以[持久化与版本演进契约](../engineering/persistence-contract.md)为准。

SmartFlow 尚未发布正式版本，也没有需要兼容的用户数据。开发早期的领域模型和数据库接口仍在快速变化，继续维护 v19 至 v48 的迁移与恢复兼容链，会把不稳定时期的实现固化为长期维护成本。

因此，当前数据库结构、逻辑备份格式和交易导入接口以本次约定为第一个稳定契约，历史版本统一停止支持。

## Decision

- 数据库 schema v49 是第一个受支持的数据库基线。`drift_schemas/drift_schema_v49.json` 是该基线的结构快照。
- v49 以下数据库不再迁移或重建，打开时明确拒绝。新安装直接从 v49 创建完整 schema。
- 从后续版本开始，每个数据库变化只能新增固定的 `vN -> vN+1` 步骤。旧步骤不得引用当前 `AppDatabase` 表定义、当前领域实体或当前枚举，也不得在发布后修改。
- 数据库迁移使用 Drift schema snapshot 和 `stepByStep`。每个相邻版本验证结构和关键数据，完整链路只覆盖基线到最新版及少数高风险路径。
- 逻辑备份使用独立的 `backupSchemaVersion = 1` 作为当前数据契约；数据库 `schemaVersion = 49` 只记录导出时的数据库结构，不参与恢复兼容判断。
- 数据库 schema 变化不会自动使备份失效。只有导出的表、字段或 wire code 变化时，才增加 `backupSchemaVersion`。
- 未来备份数据契约变化时，从 v1 开始新增固定的 `vN -> vN+1` 备份迁移；最新解析器只负责当前契约，历史步骤负责把旧逻辑数据逐级升级到当前版本。
- `formatVersion`、`backupSchemaVersion` 和数据库 `schemaVersion` 分别表达包结构、备份逻辑数据和来源数据库结构，不得混用。
- 交易导入的账户目标只使用 `ImportTargetDescriptor`。不得再引入 `asset`、`liability` 等粗粒度兼容类型或静默回退映射。
- 一木等外部来源的格式解析规则和去重指纹版本属于来源契约，不属于 SmartFlow 历史版本兼容，按来源本身继续维护。
- 已持久化的枚举文本和备份 wire code 从 v49 起视为稳定值。领域枚举重命名不得隐式改变这些值；需要改变值时，必须通过显式数据库或备份迁移完成。

## Considered Options

- 保留全部历史迁移，并从现有代码反向补齐所有 schema 快照：拒绝。没有正式用户，投入收益低，且旧迁移仍包含当前模型耦合。
- 只删除迁移测试但保留迁移实现：拒绝。实现仍会限制当前领域演进，并制造“看似支持、实际未验证”的兼容承诺。
- 把所有旧数据自动清空并恢复为当前 schema：拒绝。旧版本没有兼容承诺，但静默删除数据会掩盖版本不匹配；当前选择明确失败。
- 让备份版本直接等于数据库版本：拒绝。索引或内部表变化会无意义地使备份失效，也会阻止升级前备份在新版本中恢复。
- 恢复时要求备份数据库版本与当前版本完全相等：拒绝。升级前备份无法用于升级后的数据回滚，违背备份的安全目标。
- 保留交易导入的粗粒度 `kind` 作为 UI 兼容层：拒绝。当前尚无正式用户，直接使用描述符能避免新增账户画像时重复维护映射。

## Consequences

- 升级测试装置、开发机或测试安装包时，如数据库低于 v49，需要清除应用数据后重新创建。
- v49 之前的历史迁移代码、迁移夹具和旧备份转换测试不再保留。
- 后续 schema 变化的上限成本固定为一次 `vN -> vN+1` 迁移，而不是回改整条历史链。
- 备份当前只支持 `backupSchemaVersion = 1`；未来增加版本时，必须保留从 v1 开始的固定备份迁移链和对应测试。
- v49 数据库备份在 v50 中可以直接恢复，前提是两者仍使用相同的 `backupSchemaVersion`。若 v50 改变备份逻辑结构，则先完成备份迁移再进入当前快照校验和恢复。
- 交易导入界面、应用服务和 ledger port 只传递精确目标描述符，新增目标类型时修改一个枚举和相关策略即可。
