# 微信支付解析规则

> 样例文件：[微信支付账单流水文件(20250101-20251231)_20260101090000.xlsx](<../../demo/data/微信/微信支付账单流水文件(20250101-20251231)_20260101090000.xlsx>)
>
> CSV 浏览版：[微信支付账单流水文件(20250101-20251231)_20260101090000.csv](<../../demo/data/微信/微信支付账单流水文件(20250101-20251231)_20260101090000.csv>)
>
> 分类推断词表：[category_lexicon.json](../../assets/import/wechat/category_lexicon.json)
>
> 本规则依据该脱敏样例和微信支付导出的账单 XLSX 确定。样例保留原文件的前导说明区、分隔线、表头位置、11 列列顺序和空行结构，只抽取覆盖不同解析场景的代表记录，并替换昵称、时间、交易对方、商品、金额、支付方式尾号、交易单号、商户单号和备注等敏感值。

CSV 浏览版与 XLSX 样例逐行对应，使用 UTF-8 BOM 和 CRLF 换行。日期显示为 `yyyy-MM-dd HH:mm:ss`，金额固定两位小数，长交易单号加引号保存，便于直接用表格工具或文本编辑器查看。

本次规则范围是单个微信支付账单 XLSX 文件。首版只按 `收/支` 导入普通支出和普通收入，不把微信内部转账、退款、充值或提现解释为 SmartFlow 的转账、退款、还款或其它业务活动。分类可以从 `交易类型`、`交易对方`、`商品` 推断，但推断结果只作为可审阅建议，不改变普通收入或普通支出的业务类型。微信可与其他导入来源并存，但仍遵循“一个来源一个跨批次作用域”的导入域规则。

## 1. 文件模板

### 1.1 结构与识别

- 文件是一个 `.xlsx` 工作簿，样例中的交易表名为 `Sheet1`。
- 前导说明区位于交易明细之前。样例中说明区为第 1 至 16 行，其中第 6、16 行为空行；第 17 行为分隔线；第 18 行为交易表头；第 19 行起为交易记录。
- 解析时通过表头定位交易区，不能假设表头固定在第 18 行。首个同时包含全部必需表头的行是交易表头。
- 交易明细固定使用 11 列。表头结束后是连续数据行；前导说明区的空白行和分隔线不进入数据行。
- 文件名只作辅助识别。前导说明区中的昵称、导出时间和汇总统计不参与交易解析、去重或映射。
- 一次资料包只接受一个微信支付账单文件；资料包中出现多个微信账单文件时按资料包冲突处理。

### 1.2 核心字段

| 字段 | 必填 | 用途 |
| --- | --- | --- |
| `交易时间` | 是 | 交易发生时间；微信未提供独立入账时间，入账时间等于交易时间 |
| `交易类型` | 否 | 作为分类推断关键词来源；不写入交易备注 |
| `交易对方` | 否 | 作为分类推断关键词来源；不写入交易备注 |
| `商品` | 否 | 写入交易备注；同时作为分类推断关键词来源 |
| `收/支` | 是 | 判断普通收入、普通支出或过滤 |
| `金额(元)` | 是 | 人民币金额；方向由 `收/支` 决定，不读取金额正负 |
| `支付方式` | 否 | 结算账户来源；`/` 表示无账户 |
| `当前状态` | 否 | 识别退款收入，并在特定条件下补全收入到账账户；不写入交易备注，也不覆盖 `收/支` 的方向判断 |
| `交易单号` | 否 | 来源操作键；必须按文本保存 |
| `商户单号` | 否 | 忽略，不写入备注、映射或去重身份 |
| `备注` | 否 | 忽略，不写入交易备注 |

### 1.3 忽略内容

- 前导说明区中的微信昵称和导出信息不进入解析结果，也不写入交易或映射。
- 前导说明区的收入、支出、中性交易数量及合计不参与交易判定；它们只描述导出文件，可能与解析后的可导入候选数不同。
- `交易类型`、`交易对方`、`当前状态` 和来源 `备注` 不写入交易备注，只按规则用于方向、账户或分类判断。
- `商户单号` 可以是数字、字母数字组合、`/` 或空值。它不进入交易备注，也不用于 `sourceOperationKey`。
- 商品为 `/` 或空值时，交易备注为空。

## 2. 导入判定

### 2.1 方向

业务方向只读取 `收/支`：

- `支出`：生成普通支出候选；
- `收入`：生成普通收入候选；
- `/`：中性交易，过滤且不生成交易组；
- 空值或其它未知值：过滤并记录行级警告，不猜方向。

`交易类型` 和 `当前状态` 不能覆盖这张判定表。微信账单中的 `转账`、`群收款`、`二维码收款`、`零钱充值`、`零钱提现`、零钱通存取和商户退款只描述微信侧的资金场景，不会自动转换成 SmartFlow 的转账、退款、还款或信贷交易。

`当前状态` 不用于过滤方向为 `收入` 或 `支出` 的记录。样例中的 `支付成功`、`已转账`、`已存入零钱`、`对方已收钱`、`已全额退款`、`已到账`、`已收钱`、`提现已到账`、`充值完成` 不写入交易备注；其中 `已存入零钱` 可补全收入到账账户，`已全额退款` 可把收入行识别为退款收入。`已全额退款` 的原支出行和退款收入行都按各自方向保留；系统不自动建立退款父子关系。

在首版简化规则下，退款收入按普通收入导入，不会自动冲减原支出或预算。若需要“退款冲减原支出”的统计口径，应另行确定退款关联与导入模型，不能从本规则中的商户名称或金额相同关系自动推断。

### 2.2 金额与时间

- `金额(元)` 按人民币元解析为两位小数，再转换为 SmartFlow `Money` 最小货币单位。
- 样例中的金额单元格是正数数值。方向始终来自 `收/支`，金额本身不携带方向语义。
- 样例中的金额全部为正数，未覆盖零值和负值。解析器将金额为零的记录过滤并记录原因码 `wechat_amount_zero`；金额为负数或无法解析时使该交易组阻塞。
- `交易时间` 可能是 Excel 日期数值或日期时间值。解析后使用 `yyyy-MM-dd HH:mm:ss` 对应的本地时间语义，`occurredAt` 与 `postedAt` 相同。
- 来源没有币种列，不能据此表达多币种交易。

### 2.3 备注

交易备注只取 `商品` 字段。`交易类型`、`交易对方`、`当前状态` 和来源 `备注` 都不写入交易备注。

- `商品` 有非空值且不是 `/` 时，原值去除首尾空白后作为交易备注；
- `商品` 为 `/` 或空值时，交易备注为空；
- 备注不包含交易单号、商户单号或前导说明区内容。

商品值仍参与分类词表匹配，但写入备注与分类推断是两个独立结果。用户可在导入审阅中修改交易备注。

## 3. 名称映射

### 3.1 分类推断

微信支付账单不提供原生收入分类或支出分类。`交易类型`、`交易对方` 和 `商品` 是分类推断的输入字段，而不是直接的分类名。

分类推断使用 [category_lexicon.json](../../assets/import/wechat/category_lexicon.json) 的版本化规则快照。该 JSON 资源后续由 Dart 原生解码，包含方向、字段、关键词、优先级、分类路径和冲突策略。解析器不读取数据库，但可以使用随解析器版本提供的内置词表；用户自定义规则在进入解析前固化为规则快照。

处理顺序：

1. 按 `收/支` 确定候选方向，只使用同方向的词表规则；
2. 应用来源明确规则：退款收入固定为收入分类 `其他`；
3. 规范化并匹配 `商品`、`交易对方`、`交易类型` 中的关键词；
4. 选择优先级最高的唯一分类路径；
5. 没有命中或最高优先级出现不同分类冲突时，应用同方向的低置信度兜底规则 `其他`。

退款收入指满足下列任一条件的 `收入` 行：

- `交易类型` 包含 `退款`；
- `当前状态` 为 `已全额退款`。

退款收入必须预填收入一级分类 `其他`。该规则只适用于收入方向，不把 `已全额退款` 的原支出行改成收入，也不自动关联原支出。

词表命中后，导入草稿使用建议分类路径，不为该行添加 `category_missing`。命中来源、关键词和优先级应作为审阅提示展示，用户仍可按交易组覆盖分类。

未命中或同优先级冲突时，按 JSON 中的 `fallbackRules` 预填同方向的 `其他`，并添加警告 `category_fallback`。兜底结果允许导入，但必须与普通词表命中区分展示，让用户能筛选并批量改到更具体的分类。冲突候选仍应显示在审阅提示中。

缺失分类只在以下情况继续作为阻塞问题 `category_missing`：

- 当前规则配置关闭了对应方向的兜底；
- 兜底分类路径在导入目标中无法映射或创建；
- 来源方向本身无效。

审阅页应允许用户为每行选择已有分类、在导入时新建分类，或将当前建议批量应用到相同商户、相同商品关键词的多行。

词表推断只影响当前导入的分类引用，不进入来源操作指纹。默认词表升级不应改变同一笔来源交易的去重身份。

### 3.2 结算账户

`支付方式` 的规范化结果作为来源账户：

| 来源值特征 | 目标约束 | 新建默认 |
| --- | --- | --- |
| `收入` 且 `/` 或空值，`当前状态=已存入零钱` | 来源账户补全为 `零钱`；资金账户 | 资金账户 |
| 其它 `/` 或空值 | 明确无账户；当前导入使用幽灵账户 | 不新建来源账户 |
| `零钱` | 资金账户 | 资金账户 |
| `零钱通` | 资金账户 | 资金账户 |
| 包含 `银行` 的卡名称 | 资金账户；保留卡名称中的脱敏尾号以区分同名卡 | 资金账户 |
| 其它非空支付方式 | 资金账户或信用账户 | 资金账户 |

`收/支=收入`、`支付方式=/`、`当前状态=已存入零钱` 表明这笔钱实际进入微信零钱，收款账户应补全为来源账户 `零钱`，并使用资金账户约束。该补全只依据这三个字段的明确组合，不从商品、交易对方、金额或交易类型猜测。

其它 `支付方式=/` 的候选仍按无账户处理，当前导入使用幽灵账户。支出去向不能据此反推为零钱。

支付方式中的银行卡尾号属于来源账户身份，不能移除或只按银行名称合并。

### 3.3 来源身份与去重

- `交易单号` 非空时，去除首尾空白后作为 `sourceOperationKey`。
- 交易单号必须按文本保存，不能转换成数字，避免长数字被截断或改变。
- `交易单号` 为空时不使用商户单号、文件名或行号伪造操作键；保留缺失操作键并记录警告，仅使用交易组指纹发现疑似重复。
- 交易组指纹至少包含方向、金额、交易时间、交易类型、结算账户来源键、状态和规范化备注，并带独立指纹版本。指纹不包含映射后的 SmartFlow 分类或账户 ID。
- `商户单号` 只是微信侧商户单号；其数字、字母数字、`/` 或空值形态不影响去重。
- 同一文件内重复的非空交易单号由导入计划装配阶段判定为冲突，不能静默合并。

## 4. 文件解析

以下示例均来自脱敏样例，不代表真实交易。

### 4.1 普通支出

示例：

```text
交易类型=商户消费
收/支=支出
金额(元)=1.01
支付方式=零钱
当前状态=支付成功
```

解析结果：生成一条普通支出 `1.01`，付款账户为 `零钱` 来源实体并受资金账户约束。示例中的通用交易对方和商品未命中分类词表，因此预填支出分类 `其他`，并附加低置信度分类警告。

### 4.2 二维码付款

示例：

```text
交易类型=扫二维码付款
收/支=支出
金额(元)=3.01
支付方式=零钱
当前状态=已转账
```

解析结果：生成普通支出。`已转账` 不改变 `支出` 方向，也不转换成 SmartFlow 转账；分类继续按交易对方和商品词表推断，未命中时预填支出 `其他`。

### 4.3 微信转账

示例：

```text
交易类型=转账
收/支=支出
金额(元)=4.01
支付方式=/
当前状态=对方已收钱
```

```text
交易类型=转账
收/支=收入
金额(元)=5.01
支付方式=/
当前状态=已存入零钱
```

解析结果：分别生成普通支出和普通收入，都不转换成 SmartFlow 转账。

- 支出行的 `支付方式=/`、`当前状态=对方已收钱` 不足以识别付款账户，当前导入使用幽灵账户；
- 收入行的 `支付方式=/`、`当前状态=已存入零钱` 将收款账户补全为 `零钱`；
- 收入 `转账` 没有更具体的商品或交易对方关键词时，按词表回落为收入分类 `其他`；
- 支出 `转账` 没有具体关键词时使用低置信度支出分类 `其他`。

### 4.4 商户退款

示例：

```text
交易类型=示例商户甲-退款
收/支=收入
金额(元)=6.01
支付方式=示例银行储蓄卡(0003)
当前状态=已全额退款
商户单号=
```

解析结果：生成普通收入，收款账户为示例银行卡来源实体，分类直接使用收入 `其他`，商户单号保持缺失。交易类型中的“退款”只用于分类识别，不写入交易备注；系统不自动建立退款父子关系，也不自动归入原支出分类。

### 4.5 原支出已被全额退款

示例：

```text
交易类型=商户消费
收/支=支出
金额(元)=8.01
支付方式=示例银行储蓄卡(0001)
当前状态=已全额退款
```

解析结果：仍生成普通支出。方向为 `支出`，因此不因 `当前状态=已全额退款` 过滤，也不会套用退款收入分类规则。支出行按普通支出词表推断，未命中时预填支出 `其他`；退款收入行固定为收入 `其他`。系统不能猜测退款父子关系。

### 4.6 群收款和二维码收款

```text
交易类型=群收款
收/支=支出
当前状态=支付成功
```

```text
交易类型=二维码收款
收/支=收入
当前状态=已收钱
```

解析结果：分别生成普通支出和普通收入，不映射为转账或应收。收入 `二维码收款` 在无更具体关键词时按词表回落为收入 `其他`；支出 `群收款` 先按交易对方和商品推断，未命中时预填支出 `其他`。

### 4.7 中性转账与零钱通存取

```text
交易类型=零钱通转出（银行卡）
收/支=/
当前状态=支付成功
```

```text
交易类型=转入零钱通（银行卡）
收/支=/
当前状态=支付成功
```

解析结果：两条均过滤，不生成交易组。`/` 是中性交易的唯一方向判定依据；即使金额非零，也不能从交易类型推断为收入或支出。

### 4.8 充值和提现

```text
交易类型=零钱充值
收/支=/
当前状态=充值完成
```

```text
交易类型=零钱提现
收/支=/
当前状态=提现已到账
```

解析结果：均过滤。充值和提现属于微信内部资金搬运，可能不造成外部资金变化，不对应普通收入或支出。

### 4.9 分类推断、冲突与补全

分类词表命中的交易使用建议分类：

```text
分类：<词表分类路径>
审阅提示：分类由关键词推断，可修改
```

没有命中或同优先级冲突时：

```text
分类：其他
审阅警告：category_fallback（低置信度分类）
```

相同优先级命中不同分类时，不按字段顺序或行顺序任意选择，也不把冲突候选中的一个当作结果；系统使用低置信度 `其他` 兜底，并保留冲突候选供用户修正。用户可接受建议或批量改为更具体的分类。解析阶段不创建分类。

## 5. 校验与处理原则

- 找不到完整交易表头、工作簿不可读或没有任何数据行属于文件问题。
- `交易时间`、`金额(元)`、`收/支` 缺失或无法解析时，若该行本应成为候选，则交易组阻塞。
- `收/支=/` 的记录是过滤记录，不是解析失败，也不计入用户主动跳过数。
- `收/支` 为空或未知时过滤并记录警告，不根据交易类型、状态或金额反推方向。
- `收入` 候选的 `支付方式=/` 且 `当前状态=已存入零钱` 时，收款账户补全为 `零钱`；其它 `支付方式=/` 使用幽灵账户。
- 退款收入固定使用收入分类 `其他`；其它候选按分类词表推断，命中多个同优先级冲突或未命中时预填同方向 `其他` 并添加 `category_fallback` 警告。
- 分类建议或兜底目标无法映射、创建时仍产生阻塞；用户可继续审阅修改其它分类建议。
- 所有过滤后没有候选交易组时不创建空批次。
- 解析器只解释来源事实，不读取数据库、来源映射或账务历史，也不直接构造账务命令。

## 6. 脱敏样例覆盖
