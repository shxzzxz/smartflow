# 支付宝解析规则

> 样例文件：[支付宝交易明细(20250101-20251231).csv](<../../demo/data/支付宝/支付宝交易明细(20250101-20251231).csv>)
>
> 本规则依据该脱敏样例和支付宝导出的交易明细 CSV 确定。样例保留原文件的前导说明区、分隔线、表头位置、列顺序和末尾空列，仅将姓名、账号、商户、订单号、金额、商品说明等敏感值替换为虚构数据。

本次规则范围是单个支付宝交易明细 CSV 文件。XLSX 导出尚无样例，不在本次规则范围内。支付宝可与其他导入来源并存，但仍遵循“一个来源一个跨批次作用域”的导入域规则。

## 1. 文件模板

### 1.1 编码与结构

- 支付宝 CSV 可能使用 UTF-8，也可能使用 GB18030/CP936；仓库中的脱敏样例统一保存为 UTF-8 BOM，便于直接查看和跨平台比对。
- 文件带有前导说明区，真正表头不是第一行。解析时应在文件中定位首个同时包含全部必需列名的行，不能按固定行号截取。
- 文件使用逗号分隔并遵循 CSV 引号规则。表头末尾可能带一个空列，数据行也相应多一个空字段。
- 一个导入资料包只接受一个支付宝交易明细文件。文件角色由表头和内容识别，文件名只作辅助。

### 1.2 核心字段

| 字段 | 必填 | 用途 |
| --- | --- | --- |
| `交易时间` | 是 | 交易发生时间；支付宝未提供独立入账时间，入账时间等于交易时间 |
| `交易分类` | 是 | 收入或支出的来源分类 |
| `交易对方` | 否 | 写入交易备注 |
| `对方账号` | 否 | 忽略，不持久化 |
| `商品说明` | 否 | 写入交易备注 |
| `收/支` | 是 | 判断收入、支出或主动忽略 |
| `金额` | 是 | 正数金额，单位为人民币元 |
| `收/付款方式` | 否 | 结算账户；空值时使用幽灵账户 |
| `交易状态` | 是 | 判断交易是否实际完成 |
| `交易订单号` | 否 | 来源操作键 |
| `商家订单号` | 否 | 忽略，不参与去重或分类 |
| `备注` | 否 | 追加到交易备注 |

### 1.3 忽略内容

- 前导说明区中的姓名、支付宝账户、导出时间和统计摘要不进入解析结果，也不写入交易或映射。
- `对方账号`、`商家订单号` 不进入交易备注，避免无必要地复制外部主体标识。
- 表头末尾空列和无法识别的附加列忽略；缺少必需列时该文件不可用。

## 2. 导入判定

### 2.1 方向与状态

业务方向只读取 `收/支`：

- `支出`：生成普通支出候选；
- `收入`：生成普通收入候选；
- `不计收支`：过滤，不生成交易组。

方向成立后还必须确认交易实际完成。当前只接收 `交易状态=交易成功`：

- `交易关闭`、`冻结成功`、`放款成功`、`芝麻免押下单成功` 等状态不是普通已完成的收支事实，过滤；
- `退款成功`、`还款成功` 即使包含金额，也不在本来源中解释为普通收入或支出，过滤；
- `收/支` 为空或出现未知值时跳过该行并记录行级警告，不猜方向。

这条规则的含义是：`收/支` 是唯一的业务方向来源，`交易状态` 只用于排除未成立或不属于普通收支来源语义的记录。不能从交易分类、金额正负、账户类型或商品说明反推方向。

按此规则，账单中的转账、红包转账、投资理财、信用借还、退款、冻结和免押记录不会自动变成 SmartFlow 的转账、还款或信贷交易。

### 2.2 金额与时间

- `金额` 按人民币元解析为两位小数，转换为 `Money` 最小货币单位。
- `金额` 恰好为零时过滤该记录，不生成候选交易组，也不视为解析失败。
- `金额` 为负数或无法解析时使该交易组阻塞。`支出` 和 `收入` 的方向由 `收/支` 决定，不读取金额负号。
- `交易时间` 使用 `yyyy-MM-dd HH:mm:ss` 本地时间语义，`occurredAt` 与 `postedAt` 相同。
- 来源没有币种列；不能据此表达多币种交易。

### 2.3 备注

交易备注按 `交易对方`、`商品说明`、`备注` 的非空顺序组合，并使用字段名区分来源值，例如：

```text
交易对方：示例早餐店；商品说明：虚构早餐套餐
```

三个字段都为空时不生成备注。备注只是来源摘要，可由用户在导入审阅中修改。

## 3. 名称映射

### 3.1 分类

- `收/支=支出` 时，将 `交易分类` 提取为支出分类路径；
- `收/支=收入` 时，将 `交易分类` 提取为收入分类路径；
- 支付宝明细只提供单层交易分类，因此路径只有一级，不根据商品说明继续拆分子类；
- 分类为空或无法规范化时，该交易组阻塞并生成缺失分类审阅项。

同一个名称作为收入分类和支出分类时，来源键必须带分类方向，不能互相复用。

### 3.2 结算账户

支持的收支记录使用 `收/付款方式` 作为来源账户：

| 来源值特征 | 可映射的 SmartFlow 账户 | 新建默认 |
| --- | --- | --- |
| 包含 `花呗` 或 `信用卡` | 信用账户 | 信用账户 |
| 包含 `储蓄卡`、`账户余额`、`余额宝` 或 `骑行卡` | 资金账户 | 资金账户 |
| 其它非空银行或支付方式 | 结算账户，可为资金账户或信用账户 | 资金账户 |
| 空值 | 缺失结算账户，当前导入使用幽灵账户 | 不新建来源账户 |

`收/付款方式` 为空时不创建持久化的来源账户实体或默认映射。交易组按缺失结算账户处理，并在当前导入中使用幽灵账户；不能根据交易对方、商品说明或前导区中的真实支付宝账号猜测账户。

`收/付款方式` 可能在账户名称后用 `&` 追加优惠、红包等说明。账户识别和来源键只使用第一个 `&` 之前的非空片段，后续片段忽略：

- `花呗&网上消费红包` 和 `花呗&晚餐到店红包` 都识别为 `花呗`；
- `中国银行储蓄卡(2485)&优惠&网上消费红包` 识别为 `中国银行储蓄卡(2485)`。

账户名称片段会去除首尾空白。不同说明拼接到同一账户时归并为同一个来源账户实体。

来源账户键使用规范化后的非空 `收/付款方式` 文本。银行卡名称中的尾号必须保留在来源键中，否则不同的同名卡会被错误合并。账户映射、建户和兼容性校验仍由通用导入流程处理。

### 3.3 来源身份与去重

- `交易订单号` 非空时，去除首尾空白后作为 `sourceOperationKey`。样例中订单号稳定且文件内唯一。
- `交易订单号` 为空时不伪造订单号，也不使用行号；保留缺失操作键并记录警告，仅使用交易组指纹发现疑似重复。
- 交易组指纹至少包含方向、金额、交易时间、结算账户来源键、分类来源键和规范化备注，并带独立的指纹版本；不包含映射后的 SmartFlow 账户或分类 ID。
- 同一文件内重复的非空订单号由导入计划装配阶段判定为冲突，不能静默合并。

支付宝账单本身可能同时包含支付宝交易和对应的银行卡交易。SmartFlow 的跨来源去重边界不变：支付宝来源只与历史支付宝导入比较，不与同名的银行导入、手工交易或其他来源模糊匹配。

## 4. 文件解析

以下示例均来自脱敏样例，不代表真实交易。

### 4.1 普通支出

示例：

```text
交易分类=餐饮美食
收/支=支出
金额=1.00
收/付款方式=花呗
交易状态=交易成功
```

解析结果：生成一条普通支出 `1.00`，支出分类路径为 `餐饮美食`，付款账户为 `花呗` 来源实体，账户画像首选信用账户。

### 4.2 普通收入

示例：

```text
交易分类=转账红包
收/支=收入
金额=23.22
收/付款方式=
交易状态=交易成功
```

解析结果：生成一条普通收入 `23.22`，收入分类路径为 `转账红包`。由于 `收/付款方式` 为空，收款账户按缺失结算账户处理并使用幽灵账户。该行不会解释为转账或应收收回。

### 4.3 关闭的支出

示例：

```text
交易分类=交通出行
收/支=支出
金额=28.27
收/付款方式=花呗
交易状态=交易关闭
```

解析结果：过滤，不生成候选交易组。虽然方向列为 `支出`，但订单没有形成实际支出。

### 4.4 不计收支

示例：

```text
交易分类=投资理财
收/支=不计收支
金额=2.01
收/付款方式=余额宝
交易状态=交易成功
```

解析结果：过滤，不生成候选交易组。该记录可能是余额转出、理财申购、还款或其它资金活动，但本来源不根据分类自动赋予转账或信贷语义。

### 4.5 退款和信用借还

示例：

```text
交易分类=退款
收/支=不计收支
金额=24.23
收/付款方式=花呗
交易状态=退款成功
```

```text
交易分类=信用借还
收/支=不计收支
金额=9.08
收/付款方式=示例银行储蓄卡(0001)
交易状态=还款成功
```

解析结果：均过滤。支付宝来源首版只导入普通收入和普通支出，不把退款、还款、放款或冻结记录转换为账务核心的其它交易类型。

### 4.6 零金额

示例：

```text
交易分类=餐饮美食
收/支=支出
金额=0.00
收/付款方式=花呗&网上消费红包
交易状态=交易成功
```

解析结果：过滤，不生成候选交易组；原因码为 `alipay_amount_zero`。

## 5. 校验与处理原则

- 解码失败、找不到完整表头或没有任何数据行属于文件问题；不能把整个支付宝文件的第一行当表头。
- `交易时间`、`交易分类`、`金额`、`收/支`、`交易状态` 缺失或无法解析时，若该行本应成为候选交易，则该交易组阻塞。
- 成功 `支出`/`收入` 记录的金额为零时作为过滤记录处理，不生成阻塞问题。
- `支出`/`收入` 记录的 `收/付款方式` 为空时，交易组按缺失结算账户处理并使用幽灵账户，不按商户、商品说明或前导区账号猜测账户。
- 过滤记录不生成交易组，不是解析失败，也不计入导入批次的用户跳过数量；审阅页展示过滤数量和原因。
- 所有过滤后没有候选交易组时不创建空批次。
- 解析器只解释来源事实，不读取数据库或来源映射，不直接构造账务命令。

## 6. 脱敏样例覆盖

[支付宝交易明细(20250101-20251231).csv](<../../demo/data/支付宝/支付宝交易明细(20250101-20251231).csv>) 不是重新设计的模拟文件。它保留原文件的前 23 行说明区、第 24 行表头、13 列顺序、末尾空列和法律提示，只在数据行中替换敏感值。

数据行按 `交易分类 + 收/支 + 交易状态 + 付款方式类型` 分组，每组抽取一条原记录作为场景代表，共 33 条虚构记录。按本规则应得到 20 个候选交易组（19 条支出、1 条收入）和 13 条过滤记录（11 条不计收支、2 条关闭支出）。

| 规则 | 对应样例场景 |
| --- | --- |
| 方向与状态判定 | 19 条成功普通支出、1 条成功普通收入、2 条关闭支出 |
| 分类提取 | 覆盖样例中的全部 16 个交易分类 |
| 结算账户映射 | 覆盖花呗、储蓄卡、骑行卡、余额宝、账户余额、其它银行方式和空付款方式 |
| 账户缺失处理 | 覆盖收入方向且 `收/付款方式` 为空，确认使用幽灵账户 |
| 过滤规则 | 覆盖不计收支投资理财、退款、信用借还、冻结、放款、免押和关闭交易 |
| 来源身份 | 覆盖 20 位纯数字订单号及带字母、下划线的较长订单号 |
| 文件结构 | 保留原文件前 23 行说明区、第 24 行表头、13 列及末尾空列，并保存为 UTF-8 BOM |

样例还覆盖全部 7 种状态值：`交易成功`、`交易关闭`、`退款成功`、`还款成功`、`冻结成功`、`放款成功`、`芝麻免押下单成功`。样例中的备注均为空。

样例用于保护解析判定和字段映射行为，不保留完整真实账单，也不包含真实个人或交易信息。
