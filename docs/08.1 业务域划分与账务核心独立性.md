# 08.1 业务域划分与账务核心独立性

## 适用范围

本决策约束 SmartFlow 的业务域划分与边界：

- 哪些功能应归入**账务核心**（账务流图原语），哪些应作为**独立业务域**；
- 业务域如何在 `lib/domain/` 与 `lib/data/` 中组织；
- 业务域之间的依赖方向与 import 边界。

不约束：任一业务域内部的实体 / 服务 / 仓储细分；`app/`、`core/`、`design_system/`、`widgets/`、`features/` 的组织；UI 与业务域的接入协议（见《08.2 通用 UI 与业务域接入协议》）。

## 背景

账务核心承担过账、平账、更正、删除、统计口径等基础职责。在其之上扩展业务时，会出现两类形态——

### A. 账务流图原语（Accounting Flow Primitives）

引入**新的 entry / details 拆分模式**——业务含义与过账规则绑定，离开账务核心无法表达。当前已落地的有：转账（含手续费）、退款、报销三段式（垫付 / 收款 / 结案 + 缺口拆分）、借入 / 还款（本金 + 利息 + 手续费 + 优惠）、余额初始化 / 调整。

流图原语理应进核心，它们是会计模型的一部分。本决策不要求剥离任何一个。

### B. 独立业务域（Independent Business Domain）

**不引入**新的 entry 模式，只是在已有原语之上挂载独立的状态机 / 计划表 / 关联实体，把"哪些交易归我管、按什么节奏发生、什么时候算结束"组织起来。典型形态：

- 一个**主体实体**（合同 / 订阅 / 目标 / 凭证…），描述长期协议或承诺；
- 可能附带**计划表**（多期未来期望）；
- 实际发生时，**关联表**把账务交易绑定到主体；
- 主体有自己的**状态机**（active / settled / closed / expired …）。

落地候选包括：分期合同、信用卡账单分期、订阅扣款、保险缴费、定投计划、储蓄目标、租金合同。

当独立业务域需要"撤销 / 修改受管交易"的能力时，会出现两种诱惑：在 `BusinessPurpose` 中追加业务域专属枚举；或在账务核心动作里检测交易归属、反向调用业务域 service。两条路都会把"该业务域的存在"写进账务核心，造成跨域耦合，且让"新增一种业务"变成"改一次核心层"。

### 与 DDD 术语的对应

本决策采用 DDD 的战略设计框架：

| 本文用语 | DDD 标准术语 |
| :--- | :--- |
| 业务域（总称） | Bounded Context |
| 账务核心（也称账务域） | Shared Kernel |
| 其它业务域（信贷 / 预设 / 预算 / 分析 / ...） | 单向依赖共享内核的 Bounded Context |
| 业务域之间的依赖规则 | Context Map（Customer-Supplier） |

行文优先使用中文术语；附注 DDD 原词只为术语锚定。

## 决策

### 1. 业务域分类与边界

**账务核心独立。其它业务域单向依赖账务核心，账务核心不感知其它业务域的存在。**

具体表现为：

- 其它业务域的实现 / 枚举 / 表不进入账务核心；账务核心**不** `import` 任何其它业务域的模块。
- `BusinessPurpose` 不为其它业务域做"模块身份"特化（不存在为业务域识别而生的枚举）。
- `transactions.owner_type / owner_id / owner_role` 是开放字符串形式的业务归属索引，只保存"这笔交易归哪个业务域 / 主体 / 角色"，不进入过账规则，也不让账务核心解释具体含义。
- 其它业务域负责自身（主体 / 计划 / 关联表 / 状态机）与账务核心（交易表）之间的一致性。

### 2. 业务域清单与角色

`lib/domain/` 与 `lib/data/` 的第一层目录就是业务域。当前清单：

| 业务域 | 角色 | 说明 |
| :--- | :--- | :--- |
| `accounting`（账务核心） | **Shared Kernel** | 账户、交易、分录、过账规则、所有流图原语、查询投影。其它业务域消费它，它不知道其它业务域存在 |
| `credit`（信贷） | 独立业务域 | 分期合同 / 计划 / 还款；后续承接信贷账户辅助查询、普通借入 / 还款的额度约束等扩展能力 |
| `budgeting`（预算） | 独立业务域 | 预算实体与服务（允许暂时薄，预留位置） |
| `preset`（预设记账） | 独立业务域 | 周期记账、模板记账，共享"交易模板"实体；模板 = 立即触发，周期 = 调度触发 |
| `analytics`（分析） | 独立业务域 | 趋势 / 洞察 / 预测等分析能力，未来承接自定义仪表盘配置、报告快照等持久化实体；分析页消费此处 |

加新业务域按"演进规则"流程，并在本表追加一行。

### 3. 调用方向与 import 边界

**调用方向**：

```text
features / UI ─→ 其它业务域 service
                       │
                       ↓
                 账务核心（通过 accounting_api facade）
```

- 其它业务域**单向依赖**账务核心，不反向。
- 账务核心**不知道**其它业务域的存在。
- 兄弟业务域之间**不互相依赖**（假设当前一笔交易只有一个 owner）。

**import 边界**：账务核心以**单一 facade 文件**对外——`domain/accounting/accounting_api.dart`，统一 re-export 实体 / 枚举 / 服务 / commands / queries / views 等对外契约。

- 其它业务域、`features/`、`widgets/`、测试代码：**一律只 import `accounting_api.dart`**，不允许 import `domain/accounting/<子目录>/...`。
- 账务核心内部的 `repositories/` 与 `ledger/` 是实现细节，facade 不导出，外部不可访问。
- 例外：`app/providers.dart`（DI composition root）与 `data/accounting/`（账务核心自己的持久化实现）允许直 import 内部子目录，这是 facade 模式本来就保留的口子。

> `TransactionActionPolicy` 不在此约束内——它是 UI 接入业务域的集成层契约，整套位于 `features/transactions/action_policy/`，不属于任何业务域。详见 08.2。

兄弟业务域之间不互相 import；若未来出现真实交叉需求，通过共享 ID + 账务核心串联，不直接 import。

import 规则应由 lint（custom_lint / dart_code_metrics）强制，违反即 CI 失败。

### 4. 账务引擎心智模型

`domain/accounting/` 是"账务引擎"的当前形态。"引擎"指它对外只暴露一组明确的能力（facade 中 re-export 的契约），内部规则（ledger、posting 细节、内部数据结构）对外不可见。

**当前形式**：以 **facade 文件** `accounting_api.dart` 而非 `engine/` 子目录的方式呈现引擎对外面。这样做的好处：不引入额外目录层级，目录形态保持稳定；对外契约集中在一个文件，演化可见；内部实现可在子目录里自由重组，不影响外部 import。

**长期方向**：当 `accounting/` 稳定且其它业务域足够多，可整体提炼为独立 pub 包（`packages/smartflow_accounting_engine/`）。届时迁移成本主要是 pubspec 与少量 import 路径，目录形态不变，facade 文件成为 package 的 public API。**当前不做此提炼**。

## 归类判断

新功能接入前，按以下三问判断它属于 A（账务流图原语）还是 B（独立业务域）：

1. 它是否引入了现有 entry / details 拆分之外的新模式？
   - 是 → 流图原语，**应当**进核心枚举与账务服务，并补充对应 detail 类型 / 系统科目键。
   - 否 → 继续问 2。
2. 它是否有独立于交易的状态机 / 关联实体（合同、订阅、目标、计划等）？
   - 是 → 独立业务域，独立目录，遵守本决策。
   - 否 → 继续问 3。
3. 把它从代码中删掉，账务核心能否独立完成过账？
   - 不能 → 流图原语。
   - 能 → 独立业务域。

任何让账务核心 `import` 其它业务域的方案 → 拒绝。任何让 `BusinessPurpose` 增长以服务业务域身份识别的方案 → 拒绝。任何让 `owner_*` 参与核心过账分支的方案 → 拒绝。任何让外部模块绕过 `accounting_api.dart` 直 import 账务核心子目录的方案 → 拒绝。

## 反例

以下方案违反本决策，遇到类似诱惑时**不**采用。

### 反例一：把业务域身份编码进 `BusinessPurpose`

- **形式**：在核心枚举中追加 `<module>Specific` 项（如 `installmentBorrowing` / `subscriptionCharge` / `insurancePremium`），仅为让调用方"知道这笔交易归 X 业务域"。
- **为什么不取**：账务过账规则不依赖业务域身份；核心枚举会变成业务域注册表，每加一个业务域都要改核心；历史数据迁移代价高，且未来废弃业务域时枚举无法回收。
- **替代方案**：使用 `owner_type / owner_id / owner_role` 表达业务归属；`BusinessPurpose` 继续只表达账务行为。
- **与流图原语的区别**：`reimbursementAdvance` 等枚举之所以合理在核心，是因为它们改变了 detail 拆分模式（缺口拆分、三段式过账规则）；独立业务域不改 detail 拆分。

### 反例二：账务核心做"业务感知级联"

- **形式**：在账务核心的删除 / 更正动作中检查交易是否被某业务域持有，命中则反向调用业务域 service 做收尾。
- **为什么不取**：账务核心反向依赖业务域，无法独立编译 / 测试；每加一个业务域都要改核心 API 实现，违背开闭原则；"删交易"是核心原语，被业务感知盖住后语义不再纯粹。

### 反例三：在通用入口绕过约束做"智能联动"

- **形式**：检测到交易归某业务域管，仍然让通用层直接编辑 / 删除，背后再隐式调用业务域 service 同步状态。
- **为什么不取**：跨域协同藏在隐式回调里难以审计；调用方对动作影响范围没有清晰预期；业务规则更新时同步逻辑容易漂移。
- **替代方案**：通用 UI 通过 `TransactionActionPolicy` 路由到业务域 service（见 08.2）。

### 反例四：业务域代码组织形态错误

合并两种常见误区：

- **形式 1（扁平 domain/）**：把所有 service 平铺在 `domain/services/`，靠文件名前缀（`installment_*` / `budget_*`）区分业务域。
- **形式 2（feature 自带 domain）**：在 `features/credit/` 下重建 `domain/`、`data/`、`usecases/`，把业务域所有代码收进 feature。
- **为什么不取**：形式 1 让"账务核心独立"无法用目录表达，违反靠 review 抓，顶层目录文件会膨胀；形式 2 让 `features/` 承担领域代码不再是 UI 单元，跨 feature 共享的领域规则也没有合适位置。

### 反例五：为账务核心引入额外结构层级

合并三种"过度结构化"形态：

- **形式 1**：给账务核心起特殊目录名（`domain/core/` / `domain/kernel/` / `domain/shared/`），与兄弟业务域形成"一等公民 + 二等公民"关系。
- **形式 2**：在 `accounting/` 内部按流图原语（转账 / 报销 / 借还）再分子目录。
- **形式 3**：在 `accounting/` 下建 `engine/` 子目录承载对外面。
- **为什么不取**：核心的特殊性来自**依赖方向**（被所有人依赖、不依赖任何人），不是目录名；流图原语共享大量过账规则与实体，强行拆分会重复或交叉 import；"引擎对外面"已经以 `accounting_api.dart` 这个文件呈现，再加目录层级是过度抽象。
- **替代**：用领域词 `accounting`，靠 facade + lint 规则维持其"被依赖、不依赖"的实际地位。

## 演进规则

- **加新业务域**：在 `domain/` 与 `data/` 新建 `<域>/` 目录；在"业务域清单与角色"追加一行；如需接入通用 UI 动作槽位，按 08.2 在 `features/transactions/action_policy/` 新增实现并在 provider 注册 owner_type 映射；lint 规则按 import 边界自动覆盖新业务域。
- **现有流图原语不剥离**：`transfer / refund / reimbursement / borrowing / opening` 等不剥离；它们的核心耦合是合理的，归 `domain/accounting/`。
- **流图原语演化出独立状态机时**：例如报销引入审批流。可在其上**追加**一个独立业务域（新建 `domain/approval/` 等），但原有 detail 拆分仍留在核心。
- **何时把业务域提炼为 pub 包**：业务域代码量超过约 30 个文件且对外 API 稳定数月；出现明确复用诉求（另一个 app / package 需要该业务域）；团队规模扩大、需要并行开发隔离。未达条件前，单仓多目录足够。
- **不回归扁平结构**：集中扁平的成本随业务域数量超线性增长；分业务域组织的成本是固定的（一次性）。
