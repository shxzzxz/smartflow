# 08.1 业务域划分与账务核心独立性

## 适用范围

本决策约束 SmartFlow 的业务域划分与边界：

- 哪些功能应归入**账务核心**（账务流图原语），哪些应作为**独立业务域**；
- 业务域之间的依赖方向；
- application 用例如何编排多个领域；
- 账务核心如何保持独立，不感知其它业务域。

目录分层规则见《06. 项目结构说明》；读路径规则见《08.4 仓储层与读路径分层》；UI 与业务域接入协议见《08.2 通用 UI 与业务域接入协议》。

## 背景

账务核心承担复式记账、过账、平账、更正、删除、统计口径等基础职责。在其之上扩展业务时，会出现两类形态。

### A. 账务流图原语

引入新的 entry / details 拆分模式，业务含义与过账规则绑定，离开账务核心无法表达。

当前已落地的有：

- 普通支出 / 普通收入
- 转账（含手续费）
- 退款
- 报销三段式（垫付 / 收款 / 结案 + 缺口拆分）
- 借入 / 还款（本金 + 利息 + 手续费 + 优惠）
- 期初余额 / 余额调整

这些原语属于账务核心。它们是会计模型的一部分，不应剥离到其它业务域。

### B. 独立业务域

不引入新的 entry 模式，只是在已有账务原语之上挂载独立状态机、计划表或关联实体，组织“哪些交易归我管、按什么节奏发生、什么时候算结束”。

典型形态：

- 主体实体：合同 / 订阅 / 目标 / 凭证等。
- 计划表：多期未来期望。
- 关联表：把账务交易绑定到主体。
- 独立状态机：active / settled / closed / expired 等。

分期合同、订阅扣款、保险缴费、定投计划、储蓄目标、租金合同都属于这一类候选。

## 决策

### 1. 账务核心独立

**账务核心独立。其它业务域可以依赖账务核心的领域能力，但账务核心不感知其它业务域。**

具体表现：

- `domain/accounting` 不 import `domain/credit`、`domain/budgeting` 等兄弟业务域。
- 其它业务域的实现、枚举、表结构不进入账务核心。
- `BusinessPurpose` 不为其它业务域做“模块身份”特化。
- `transactions.owner_type / owner_id / owner_role` 只表达业务归属索引，不参与账务过账分支。
- 账务核心不根据 owner 反向调用其它业务域。

### 2. application 负责跨域用例编排

跨域用例属于 application 层，不属于某个 domain 的内部实现细节。

例如分期还款：

```text
application/credit/createScheduledRepayment
  - 控制事务
  - 调 credit domain 判断合同 / 期次状态
  - 调 accounting domain service 生成还款入账结果
  - 调 accounting ports 保存账务结果
  - 调 credit ports 保存 repayment / schedule 变化
```

这不是 accounting 为 credit 提供特殊入口，也不是 credit 绕过 accounting 规则。application 用例可以组合多个领域服务和 ports，但不应把另一个完整 application use case 当成可复用领域能力。

### 3. domain 可以通过本领域 ports 获取领域事实

账务规则需要哪些事实，本身是账务领域知识。例如退款需要父交易和已退款额，还款需要账户角色和系统科目事实。

因此：

- `domain/accounting` 可以定义 ports 来获取账务事实。
- `infrastructure/accounting` 实现这些 ports。
- `application/credit` 等调用方不应复制 accounting 的事实加载规则。
- domain 不依赖 Drift / RPC / infrastructure 实现。

### 4. 业务域清单与角色

| 业务域 | 角色 | 说明 |
| :--- | :--- | :--- |
| `accounting`（账务核心） | Shared Kernel | 账户、交易、分录、过账规则、所有账务流图原语。其它业务域可消费它，它不知道其它业务域存在 |
| `credit`（信贷） | 独立业务域 | 分期合同 / 计划 / 还款状态机；通过 application 用例调用账务核心完成入账 |
| `budgeting`（预算） | 薄业务域 | 预算配置与预算查询，当前不强制完整战术 DDD |
| `preset`（预设记账） | 独立业务域候选 | 周期记账、模板记账，待业务复杂度明确后落地 |
| `analytics`（分析） | 查询 / 分析域 | 趋势、洞察、预测、报告投影 |

### 5. 调用方向

写侧调用方向：

```text
features / UI
  -> application use case
      -> domain service / aggregate / ports
          <- infrastructure implements ports
```

纯 UI / 报表查询可以绕过 domain：

```text
features / UI
  -> application query / read model
      -> infrastructure query implementation
          -> database
```

如果查询结果会参与领域规则判定，则不是纯读侧投影，应由对应 domain port 加载领域上下文。

跨域组合发生在 application：

```text
application/credit
  -> domain/credit
  -> domain/accounting
  -> domain/credit/ports
  -> domain/accounting/ports
```

禁止：

- `domain/accounting -> domain/credit`
- `domain/* -> application/*`
- `domain/* -> infrastructure/*`
- `features/* -> domain/*` 或 `features/* -> infrastructure/*`

## 归类判断

新功能接入前，按以下三问判断它属于账务流图原语还是独立业务域。

1. 它是否引入现有 entry / details 拆分之外的新模式？
   - 是：流图原语，进 `domain/accounting` 的账务规则，并补充对应 detail 类型 / 系统科目键。
   - 否：继续问 2。
2. 它是否有独立于交易的状态机 / 关联实体（合同、订阅、目标、计划等）？
   - 是：独立业务域，由 application 用例调用账务核心。
   - 否：继续问 3。
3. 把它从代码中删掉，账务核心能否独立完成过账？
   - 不能：流图原语。
   - 能：独立业务域或 application 编排能力。

任何让账务核心 import 其它业务域的方案都拒绝。任何让 `BusinessPurpose` 增长以服务业务域身份识别的方案都拒绝。任何让 `owner_*` 参与核心过账分支的方案都拒绝。

## 反例

### 反例一：把业务域身份编码进 `BusinessPurpose`

- 形式：追加 `installmentBorrowing` / `subscriptionCharge` 等仅表示模块身份的枚举。
- 为什么不取：账务过账规则不依赖业务域身份；核心枚举会变成业务域注册表。
- 替代：使用 `owner_type / owner_id / owner_role` 表达归属；`BusinessPurpose` 只表达账务行为。

### 反例二：账务核心做业务感知级联

- 形式：账务删除 / 更正时检查 owner，命中某业务域后反向调用该业务域 service。
- 为什么不取：账务核心反向依赖业务域，每加一个业务域都要改核心。
- 替代：由 application 用例或 UI action policy 路由到对应业务域，由最外层用例编排账务与业务状态更新。

### 反例三：跨域用例套用另一个完整 application use case

- 形式：`application/credit/createScheduledRepayment` 直接调用 `application/accounting/createRepayment`，把账务用例当作领域能力复用。
- 为什么不取：用例套用例会让事务边界、错误处理、事实加载职责变模糊。
- 替代：跨域用例组合 `domain/credit`、`domain/accounting` 与各自 ports。

### 反例四：调用方复制账务事实加载规则

- 形式：credit / import / UI 自己查询父交易、已退款额、账户角色、系统科目后再拼账务分录。
- 为什么不取：账务规则需要哪些事实本身是账务领域知识，复制后会漂移。
- 替代：由 accounting domain service 通过 accounting ports 获取其所需账务事实。

### 反例五：业务域代码组织形态错误

- 形式 1：把所有 service 平铺在 `domain/services/`。
- 形式 2：在 `features/credit/` 下重建 `domain/`、`data/`、`usecases/`。
- 为什么不取：前者无法表达业务边界，后者让 UI feature 承担领域代码。
- 替代：顶层分层，层内按业务域组织。

## 演进规则

- 新增账务流图原语：补充领域规则、detail 类型、系统科目键和 application 用例。
- 新增独立业务域：先定义 domain 模型 / ports，再按复杂度补 application / infrastructure。
- 流图原语演化出独立状态机时：保留原账务规则在 accounting，新增独立业务域管理状态机。
- 何时拆 package：边界稳定、API 稳定、出现复用诉求或团队隔离需要后再考虑；当前不拆。
