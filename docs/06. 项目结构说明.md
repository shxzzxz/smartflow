# 项目结构说明

本文档定义 SmartFlow Flutter 工程的目录组织与分层边界。业务模型见《03. 业务领域设计》，视觉规范见《05. 设计系统》，业务域划分与依赖边界的决策依据见《08.1 业务域划分与账务核心独立性》。

## 1. 总体原则

SmartFlow 采用**顶层分层 + 层内按业务域组织**：

- `application/`：用例编排层，负责用户操作、事务边界、跨领域协调、查询投影。
- `domain/`：领域层，负责领域模型、领域服务、领域不变量与 ports。
- `infrastructure/`：基础设施实现层，负责 Drift / SQL / mapper / repository 实现 / RPC 等技术细节。
- `features/`：UI 页面与用户工作流，不按 DDD 业务域强行归属。

写侧依赖方向：

```text
features / widgets / app
        ↓
application/<域或用例组>
        ↓
domain/<域>
        ↑
infrastructure/<域>  实现 domain ports
```

纯读侧可以绕过 domain：

```text
features / widgets / app
        ↓
application/<域>/queries + read_models
        ↓
infrastructure/<域> query implementation
        ↓
database
```

application 定义查询接口、查询参数和 read model；infrastructure 提供 Drift / SQL 实现并由装配层注入。纯 UI 展示、报表、响应式投影不强制经过 domain ports。

约束：

- `domain/` 不依赖 Flutter、Riverpod、Drift、`application/`、`infrastructure/`、`features/`、`app/`。
- `application/` 可以编排一个或多个 `domain/`，并通过 ports 调用写侧持久化能力；事务边界属于 application 用例。
- `application/queries` 可以定义纯读侧查询接口、查询参数、scope filter 与 read model；查询实现位于 infrastructure。
- `infrastructure/` 实现 domain ports 和 application query interfaces，可以依赖 Drift / SQL / RPC 等技术细节。
- `features/` 通过 Riverpod provider 使用 application 用例和查询，不直接 new DAO / repository 实现。
- `features/` 内不要新建 `data/`、`domain/`、`repositories/`、`usecases/`。
- 主题、token、基础组件放 `design_system/`，不放进 `core/`。

## 2. 分层职责

### 2.1 application

application 是**用例编排层**，不是某个业务域的附属实现细节。

职责：

- 表达一个具体用户用例。
- 编排一个或多个领域。
- 控制事务边界。
- 调用 domain service / aggregate / ports。
- 定义并组装查询 read model、query scope 与响应式查询投影。
- 返回 UI 或其它调用方需要的结果 DTO。

排除：

- 不承载领域不变量。
- 不把另一个 application use case 当成可复用领域能力。
- 不直接依赖 Drift / SQL 实现；纯读侧通过 application query interface 由 infrastructure 提供实现。

### 2.2 domain

domain 负责领域规则与不变量。判断标准：

```text
如果规则被破坏会让记账数学错、借贷不平、余额错算、状态机非法跃迁，归 domain。
如果只是流程编排、事务控制、数据刷新、页面展示、调用顺序，归 application 或 features。
```

domain service / aggregate 可以依赖**本领域定义的 ports** 获取领域事实。不要把“domain 不依赖 infrastructure 实现”误解为“domain 不能获取领域事实”。

例如复杂账务原语所需事实属于账务领域知识：

- 退款需要父交易、原分录结构、已退款总额。
- 报销结案需要垫付交易、已到账总额、剩余应收、原支出分类。
- 还款需要负债账户、付款账户、利息 / 手续费 / 优惠系统科目与账户角色。
- 更正 / 冲销需要原交易详情和分录结构。

这些事实应由 `domain/accounting` 的领域服务通过 `domain/accounting/ports` 获取，或由账务领域明确声明为上下文对象；不要让 `credit` / import / UI 等调用方复制账务事实加载规则。

### 2.3 infrastructure

infrastructure 实现 ports 与 query interfaces，不承载业务决策。

职责：

- Drift repository / query source 实现。
- SQL 表达式与 mapper。
- application query interface 的 Drift / SQL 实现。
- RPC / 文件 / 平台能力实现。
- 数据库事务执行器实现。

排除：

- 不解释业务原语。
- 不编码业务流程字面量。
- 不让兄弟业务域直接调用自己的实现类。

### 2.4 features

`features/` 按页面与用户工作流组织。UI 不强行归属到 DDD 业务域。

例如：

- `home` 可能消费账务、预算、信贷摘要。
- `calendar` 可能消费交易、还款计划和预算。
- `transactions` 是账务入口，但详情页可能通过 action policy 接入其它业务域。

## 3. 业务域与角色

业务域按领域语言命名，主要出现在 `domain/`、`application/`、`infrastructure/` 的层内目录。

| 业务域 | 角色 | 说明 |
| :--- | :--- | :--- |
| `accounting`（账务核心） | Shared Kernel | 账户、交易、分录、过账规则、账务流图原语；查询投影位于 application query side |
| `credit`（信贷） | 独立业务域 | 分期合同 / 计划 / 还款状态机；调用账务核心完成入账 |
| `budgeting`（预算） | 薄业务域 | 预算配置与预算查询，当前不强制完整三层 |
| `preset`（预设记账） | 独立业务域候选 | 周期记账、模板记账，待业务复杂度明确后落地 |
| `analytics`（分析） | 薄业务域 / 查询域 | 趋势、洞察、预测、报告投影 |

重域使用完整分层：

```text
application/accounting + domain/accounting + infrastructure/accounting
application/credit + domain/credit + infrastructure/credit
```

薄域允许先保持轻量结构；当长出复杂不变量、状态机或跨用例规则，再拆完整分层。

## 4. 目录结构

目标结构：

```text
lib/
├── main.dart
├── app/                                  # MaterialApp、router、顶层 provider、bootstrap、依赖装配

├── application/                          # 用例编排层
│   ├── accounting/
│   │   ├── commands/                     # 用例输入模型
│   │   ├── queries/                      # 查询参数与查询用例
│   │   ├── read_models/                  # 查询投影 / read model
│   │   └── use_cases/                    # 账务用例编排
│   ├── credit/
│   │   ├── commands/
│   │   ├── queries/
│   │   ├── read_models/
│   │   └── use_cases/
│   └── shared/                           # 事务执行抽象等 application 共享能力
├── domain/                               # 领域层：按业务域分子目录
│   ├── accounting/
│   │   ├── entities/
│   │   ├── value_objects/
│   │   ├── ledger/                       # 账务核心特有领域规则
│   │   ├── services/                     # 领域服务
│   │   └── ports/                        # 本领域 ports，仅接口
│   ├── credit/
│   │   ├── entities/
│   │   ├── value_objects/
│   │   ├── services/
│   │   └── ports/
│   └── ...
├── infrastructure/                       # ports 实现与技术细节
│   ├── accounting/
│   │   ├── repositories/
│   │   ├── mappers/
│   │   └── sql/
│   ├── credit/
│   │   ├── repositories/
│   │   └── mappers/
│   └── database/                         # 长期目标：Drift 单库装配与迁移
├── data/                                 # 过渡期保留：现有 Drift 单库装配 / tables / migrations
├── features/                             # 页面与 UI 状态编排

```

过渡期允许 `lib/data/` 与 `lib/infrastructure/` 并存。`data/` 当前仍承载应用级 Drift 单库装配、schema 注册、tables 与 migrations；迁移完成后可逐步收敛到 `infrastructure/database/`。

feature 内部按需使用：

```text
features/<feature>/
├── pages/
├── widgets/
├── providers/
├── view_models/
└── action_policy/                        # 可选；目前主要用于 transactions feature
```

## 5. 事务与 Drift 单库

### 5.1 事务边界

事务边界属于 application 用例。domain 不知道事务，infrastructure 只实现事务机制。

当前 `TransactionRunner` 可以作为 application 与 infrastructure 之间的事务抽象。目标规则：

```text
一个 application use case 拥有一个顶层事务边界。
application use case 不应通过调用另一个完整 application use case 来复用领域能力。
跨域用例在自己的事务内组合多个 domain service / ports。
```

跨域用例由最外层 application use case 拥有提交 / 回滚权。

过渡期代码中可能仍存在 repository / store 内部自行开启数据库事务的情况；这属于历史实现细节，不是目标边界。重构时应逐步收敛为 application 用例控制事务，infrastructure 写入方法参与当前调用链，不自行表达完整用例事务。

### 5.2 Drift 单库集中

模块化不等于 Drift schema 分散化。以下能力必须保持应用级集中管理：

- `AppDatabase`
- `schemaVersion`
- migration strategy
- 表注册
- 内置数据初始化

过渡期保留：

```text
lib/data/app_database.dart
lib/data/database_provider.dart
lib/data/migrations/*
lib/data/builtin_data.dart
lib/data/*/tables/*
```

禁止把迁移版本号和 schema 管理拆进各业务域，避免迁移撞号和装配混乱。

## 6. Import 边界

- `domain/*` 不依赖 `application/`、`infrastructure/`、`features/`、`app/`、Drift、Riverpod。
- `domain/*` 不依赖 application query DTO / read model / scope filter。
- `application/*` 可以依赖一个或多个 `domain/*`；`application/*/queries` 可定义纯读侧查询接口、查询参数与 read model。
- `infrastructure/*` 实现 `domain/*/ports` 和 application query interfaces，可以依赖对应接口和模型。
- `features/*` 不直接依赖 `domain/*` 或 `infrastructure/*`，通过 application provider / use case / query 使用业务能力。
- `domain/accounting` 不依赖 `domain/credit`、`domain/budgeting` 等兄弟业务域。
- 兄弟业务域之间如需组合，由 application 用例编排。

## 7. 测试规则

测试目录随结构演进逐步镜像：

```text
test/application/
test/domain/
test/infrastructure/
test/features/
```

现有 `test/data/` 可在基础设施迁移期间保留。

测试原则：

- `domain/` 测试用纯 Dart unit test。
- `application/` 测试验证用例编排、事务失败传播和跨领域协调。
- `infrastructure/` 测试用 Drift in-memory 或对应技术替身。
- `features/` 测试优先 mock provider / application 用例。

## 8. 命名约定

- 文件与目录：`snake_case`；类名：`UpperCamelCase`。
- 数据库列名：`snake_case`，与《03.1 数据模型》一致。
- 金额字段：数据库层用 `_minor` 后缀，领域 / UI 层使用 `Money`。
- Riverpod provider：`<scope>Provider`。
- 业务域目录名用领域语言（`accounting / credit / budgeting / analytics`），不用技术词替代领域词。

## 9. 演进规则

- **新增字段**：先改《03.1 数据模型》，再改 Drift table 与迁移，同步领域模型、application DTO 与 UI。
- **新增账务核心场景（流图原语）**：先改《03.2 核心业务规则》和《03.3 业务场景流程示例》；扩展 `BusinessPurpose` / `TransactionDetailType` / `SystemKey`；落地账务领域规则；按需补 application 用例和查询投影。
- **新增独立业务域**：按 08.1 的归类判断；先建 domain 规则和 ports，再按业务复杂度决定是否补 application / infrastructure 完整结构。
- **新增跨域用例**：放 application 层，由最外层用例编排多个领域；不要把一个领域的 application use case 当作另一个用例的领域能力复用。
- **新增 feature**：优先只建 `pages / widgets / providers / view_models`；领域规则不得放入 feature。
- **新增纯读侧查询**：优先在 application query side 定义 query / scope / read model，由 infrastructure 实现 Drift / SQL；不要为了 UI 查询把 read model 或 `TransactionScopeFilter` 放进 domain。
- **新增领域规则事实加载**：如果查询结果参与退款、报销、更正、取消等领域判定，应定义 domain port 和领域上下文，不复用 application read model。
- **性能优化**：优先在 infrastructure 查询、application projection 或索引上处理，不在页面层堆业务缓存。
