# 业务域领域文档

本文是 SmartFlow 业务域领域文档的总入口，统一 `docs/domains/` 下文档的内容边界与编写规则。阅读、创建或修改领域文档时，先阅读本文，再按索引进入相关业务域。

**领域文档记录当前有效的业务最终状态，表达“是什么”；以主要思想为主，补充必要的边界情况和易混淆点。**

## 只记录最终状态

“最终状态”指当前已经确定并生效的业务定义，不是未来规划，也不是业务对象生命周期的终点。正文直接陈述现行规则、适用条件与结果。

- 规则或模型变化时，重写对应段落，移除被替代的表述；不追加新旧方案对比、版本变更清单或“从某模型演变为某模型”的过程。
- 领域正文不解释为什么选择该方案、不记录讨论和权衡过程。需要追溯时链接相应 ADR 或 Issue，当前规则本身应能独立读懂。
- 业务对象的状态转换、交易修改与删除、分类迁移、外部数据导入等，只要属于现行能力，就应描述其业务行为；数据库版本升级、旧字段回填和兼容切换属于实现演进。
- 尚未确定的方案、待办和未来扩展放入需求或讨论记录，确定并生效后再更新领域正文。

## 控制抽象与细节

按“主要思想 → 适用条件与结果 → 必要边界或示例”组织内容。

- **概览讲职责与关系。** 说明领域负责什么、核心概念如何关联，以及跨域协作各自承担的业务责任。
- **模型讲业务含义。** 保留业务对象、身份、关系、关键属性及约束。确有必要时使用稳定字段标识澄清含义，避免照搬完整表结构、技术字段与索引清单。
- **规则讲条件与结果。** 保留业务不变量、状态转换、金额与时间口径；决定结果的公式、舍入规则和判定表可以直接表达，不展开为代码执行步骤。
- **边界澄清歧义。** 补充会改变业务判断的例外、冲突条件或易混淆概念。场景使用“前提、业务动作、预期结果”，以少量代表性案例澄清规则，避免穷举测试用例。
- **表述独立于实现。** 源码目录、具体文件与行号、类或方法清单、调用链、框架机制和具体代码逻辑不进入领域正文。文档导航链接用于定位说明，业务规则用领域语言表达。

判断细节是否必要：删去它是否会让读者误解业务结果？若只是帮助定位或修改代码，应回到源码或工程文档；若影响金额、时间、状态或责任边界，应保留其业务语义。

## 维护要求

1. 修改前确认术语、规则归属与受影响的文档；文档、已确认需求或实现相互冲突时，先澄清有效规则。
2. 按本规范整理本次涉及的章节，同步模型、规则与场景中受影响的表述。去掉失效内容、重复规则和实现细节，保留仍有业务意义的边界。
3. 新增或拆分领域文档时更新本页索引。完成时检查：正文只陈述当前规则，主要思想清楚，必要边界完整，引用有效，演变记录与实现信息已归位。
