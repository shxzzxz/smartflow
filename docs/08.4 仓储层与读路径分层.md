# 08.4 仓储层与读路径分层

## 适用范围

本决策约束账务核心(及其它业务域)的**读路径**(查询、聚合、响应式刷新)如何分层:

- 哪些信息允许出现在 SQL / repository 实现中,哪些必须留在 service 与 view model 层;
- repository / service / read model / view model 各自的职责边界;
- 响应式 Stream 的组装路径与 domain 层是否允许直接依赖持久化技术的事件流。

不约束:写路径的 voucher / runner 设计(见议题 2);单层内部的细分(repository 内是否抽 mapper / SQL fragment 等)。

## 背景

账务核心读路径在快速演进期形成了三种层级耦合:

1. **业务流程语义下沉到 SQL**:`watchTransactions` 的 200 行 CTE 内散布 `purpose='refund'` / `purpose IN (reimbursementReceipt, reimbursementClose)` / `is_excluded_from_stats=0` 这类业务流程字面量。新增 purpose 或调整口径需改 6+ 处 SQL,变更点散乱,且 repository 与业务流程的耦合形状不显性。

2. **UI 装饰下沉到 read model**:`accountName` / `categoryIconKey` / `flowOut/InAccountId` / `accountBalanceDelta` 直接出现在 `TransactionListItem`,SQL 必须 LEFT JOIN accounts 并 GROUP BY;account 名称变更要刷一次列表;UI 派生改动会推到 SQL 层。

3. **数据编排藏在 repository**:repository 内 `if (purpose == dailyExpense) {...} else if (purpose == reimbursementAdvance) {...}` 的 if 链做"哪种 purpose 该查哪些子树"判断,业务规则与数据访问混在一处。

4. **read model 形态混乱**:常规列表与更正链共用 `TransactionListItem`,后者大量字段在前一场景永远为 0,反之亦然。

5. **重复实现**:list-item projection 在多处各写一遍;余额累计 CASE WHEN 公式在 6 处 SQL 各微调一遍,易漂移。

6. **domain 层依赖持久化响应式原语**:metrics service 直接 `_db.tableUpdates(...)` 监听变化,把 drift 表事件流穿透到 domain 层。

## 决策

读路径分为三层,每层职责清晰互不越界。

### 1. 三层结构

| 层 | 路径示例 | 面向 | 包含 | 排除 |
| :--- | :--- | :--- | :--- | :--- |
| 能力(repository / service) | `domain/accounting/repositories/`、`domain/accounting/services/` | 业务概念 | 原子读 / 写 / 聚合方法;按 purpose 分桶 → 并行切片 → 拼装的数据编排 | 业务流程字面量(在 repository 实现内);UI 装饰 |
| 领域 read model | `domain/accounting/read_models/` | 业务场景 | 会计事实(entries / details)、业务派生标量(`refundedTotal` / `outstanding` / `isClosed` 等);一个场景一个 read model | UI 装饰;场景外的字段 |
| UI 层 view model | `features/<域>/view_models/`、`widgets/business/*` | 页面状态 | UI 派生(`flowOut/InAccountId` / `accountBalanceDelta` / 名称查找)、字段格式化;公共 lookup(`accountsById`) | 业务规则派生 |

### 2. 数据编排归属 service

repository 仅提供**原子能力**(单表查询 / 切片 / 单维度聚合);多步查询的编排(分桶 rootId → 并行查切片 → 拼装 read model)、业务规则派生(`outstanding` / `isClosed` 等)归 service。理由:每一步都要碰业务字面量(哪些 purpose 算 refund 等),把它们留在同一层(service)更易审计。

### 3. 业务字面量隔离

`BusinessPurpose.refund` / `purpose IN ('reimbursementReceipt', 'reimbursementClose')` / `is_excluded_from_stats=0` 等业务流程字面量的出现位置仅限:

- service 调能力时传入的参数 Set;
- read model 投影代码;
- scope filter 预设定义(`TransactionScopeFilter.stats` 等);
- UI 层 view model 派生代码。

repository 实现(无论 typed query 还是 customSelect)**不出现**业务流程字面量。具体值通过参数 `Set<BusinessPurpose>` / `Set<BusinessState>` / `TransactionScopeFilter` 传入,repository 只把它们翻译成 `equalsValue` / `isInValues` / where 片段。新增 purpose 类型或调整口径,改 service 端调用参数,不改 repository。

### 4. 响应式策略

- 优先 typed query + `.watch()`,自动追踪 select 涉及的表(`readsFrom` 自动)。
- 复杂多桶场景:repository 提供 `Stream` 入口,service 用 `asyncMap` 组合异步切片调用:
  ```dart
  return _txRead.watchPage(query).asyncMap((page) async {
    // 按 purpose 分桶 → Future.wait 并行查切片 → 投影 read model
  });
  ```
- 与底层数据无关的"表变化"事件(仅作为重新聚合的触发信号)通过 repository 暴露 `watchChanges()` Stream,domain 层不直接依赖 drift 的 `tableUpdates`。

### 5. SQL 公式收敛

跨场景共享的复合 SQL 表达式(余额累计公式、scope 过滤翻译等)通过 `data/accounting/sql/` 内的 `Expression<T>` 工厂收敛,所有需要的地方共用同一份;Dart 等价公式留在 `domain/accounting/ledger/`,语义对称由 integration 测试保证。

## 含义

- repository 接口签名只含会计枚举(`AccountType` / `BusinessState` 等)、`Set<>` 参数与 scope 抽象;**不**含"场景标识"枚举或"是否查 refund"这类语义参数。
- read model 字段集中在"会计事实 + 业务派生";新增 UI 派生(余额变动符号、账户名等)应当落在 view model 层。
- service 是唯一允许"用业务字面量调能力"的层;每个 service 方法明确自己的口径(scope lens / purpose 集合)。
- 复合 SQL 公式必须通过 `data/accounting/sql/` 工厂调用,**不**允许在 repository 实现内手抄 CASE WHEN。
- domain 层不依赖 drift / sqflite 等持久化技术的 API;响应式事件通过 repository `watchChanges()` 抽象暴露。

## 适用案例

### 仓储能力分桶

- `TransactionReadRepository`:交易直读、分页 `watchPage`、子树聚合 `aggregateChildren / aggregateChildDetailAmounts`(参数化的 purposes / states / detailTypes,不含字面量)。
- `EntryReadRepository` / `TransactionDetailReadRepository`:各自负责单表切片(`findByTransactionIds`),不跨表 JOIN。
- `BalanceAggregateRepository`:按账户类型分桶累计,JOIN accounts 是该场景本分;暴露 `watchChanges()` 给上层 service 编排响应式 Stream。

### scope lens

`domain/accounting/queries/transaction_scope.dart`:`TransactionScopeFilter` 把"业务态白名单 + 排除标志"抽成结构化 lens,预设(`stats / budget / assetLiability / actual / all`)以静态 const 字段表达常用口径。

### SQL 公式工厂

`data/accounting/sql/balance_expressions.dart`:`balanceDeltaExpr`(余额累计表达式)与 `applyTransactionScope`(scope 翻译 where 片段),所有需要这两类公式的 repository 调用同一份。Dart 等价公式(`balanceDeltaMinor`)在 `domain/accounting/ledger/ledger_rules.dart`。

### service 编排

`TransactionQueryServiceImpl.watchTransactions`:`_txRead.watchPage(query).asyncMap(page => 5 步编排)`,业务字面量集中出现在分桶代码与子树聚合调用参数;`FinancialMetricsServiceImpl.watchCashflowComparison`:`_aggregate.watchChanges().asyncMap((_) async => 3 次 aggregateByAccountType 调用 + 拼装)`。

### read model 形态

`TransactionListItem`(常规列表)、`TransactionHistorySnapshot`(更正链,无子树聚合)、`TransactionDetail`(详情场景)各自字段集合不同,共享 `entries: List<Entry>` / `details: List<TransactionDetailRecord>` 但其余字段按场景剪裁。

### UI 层 view model

`widgets/business/account_lookup.dart`(`Entry.resolveType / resolveAccount` extension + `balanceDeltaForAccount` 等纯函数 helper),`features/home/view_models/transaction_row_presentation.dart`(签名接收 `accountsById` map,内部派生 categoryName / iconKey / flowOut/InAccountName),`accountsByIdProvider`(Riverpod stream,UI widget `ref.watch` 即可)。

## 反例

### 反例一:repository 实现内编码业务流程字面量

- **形式**:SQL CTE 写 `WHERE purpose IN ('reimbursementReceipt', 'reimbursementClose')` 或 `WHERE business_state = 'current' AND is_excluded_from_stats = 0`,把"哪些 purpose 算报销链子节点"固化在 repository 内。
- **为什么不取**:口径调整(新增 purpose / 改 state 语义)需要改多处 SQL,变更点散乱;repository 与业务流程的耦合形状不显性。
- **替代**:caller 显式传 `purposes: {BusinessPurpose.reimbursementReceipt, BusinessPurpose.reimbursementClose}` 与 `scope: TransactionScopeFilter.stats`,repository 只翻译为 `.isInValues({...})` / `applyTransactionScope(...)`。

### 反例二:read model 持有 UI 装饰

- **形式**:`TransactionListItem` 直接持 `accountName` / `categoryIconKey` / `flowOut/InAccountId` / `accountBalanceDelta`,SQL 必须 LEFT JOIN accounts 并 GROUP BY。
- **为什么不取**:UI 装饰随渲染需求频繁变化,sql 与 read model 因此频繁调整;account 名称变更要刷一次列表(读路径不应持有这类瞬时数据);列表 SQL 复杂度被推高。
- **替代**:read model 只暴露 `accountId`,UI 层通过 `accountsByIdProvider` 查名字 / icon;`balanceDeltaForAccount` 等 UI 派生由 view model 层函数计算。

### 反例三:数据编排藏在 repository

- **形式**:repository 的某个方法内部 `if (purpose == dailyExpense) { ...查 refund... } else if (purpose == reimbursementAdvance) { ...查 reimbursement... }`。
- **为什么不取**:repository 同时承担数据访问与业务判断;新增业务流程或调整判断条件要改 repository,违反"repository 仅提供原子能力"的边界。
- **替代**:service 端按 purpose 预分桶 rootId,分别调用具体参数的 `aggregateChildren(rootIds: ..., purposes: {...})`;repository 只负责按参数累计。

### 反例四:业务规则两份实现

- **形式**:`outstanding = parent - sum(receipts)` 这类业务派生既出现在 service 的纯函数派生,又出现在某个 repository 方法的 SQL CTE 中。
- **为什么不取**:同一业务规则两份实现,迟早漂移。
- **替代**:业务派生只出现在 service / read model 投影代码;repository 只提供原子聚合,业务规则按需在 service 用聚合结果派生。

### 反例五:domain 层直接依赖 drift 的响应式原语

- **形式**:`FinancialMetricsServiceImpl` 直接 `_db.tableUpdates(...)` 监听变化。
- **为什么不取**:domain 层依赖具体持久化技术,无法替换;违反"账务引擎对外只暴露能力,内部规则不可见"的边界。
- **替代**:`BalanceAggregateRepository.watchChanges()` 把"相关表变化"作为抽象事件暴露,drift 实现层把它翻译为 `tableUpdates`。

### 反例六:为方便而合并 read model

- **形式**:常规列表与更正链共用 `TransactionListItem`,在 history 场景把 `refundedTotal` / `reimbursementChildCount` 等字段设为 0;在列表场景把 `mutationKind` / `mutationPreviousTransactionId` 等字段设为 null。
- **为什么不取**:每个场景都有大量"永远为空"字段,读者需要逐场景理解哪些字段在当前场景才有意义;字段集合膨胀;增删字段时要考虑跨场景影响。
- **替代**:一个场景一个 read model,字段集合按场景剪裁。共享部分用 Dart 组合(嵌套对象或抽公共部分到子类型),不强求大一统。

## 演进规则

- **新增业务场景** → 多半新增 read model + service 方法,通常**不**需要新增 repository 能力;若需要新的原子聚合(如按业务标签维度分桶),在 repository 上加参数化方法,**不**让业务标签字面量进入 repository 实现。
- **新增 UI 派生**(余额变动符号、名称查找等) → 在 `widgets/business/` 或 `features/<域>/view_models/` 加 helper,不修改 read model 字段集合。
- **新增 scope lens** → 在 `TransactionScopeFilter` 增加预设静态字段,service 按需选用,**不**在 repository 加 if-branch。
- **新增"按 X 维度分桶聚合"接口** → 在 `BalanceAggregateRepository` 或同类接口加方法,采用与现有方法相同的(account types + currency + scope + window)参数风格;**不**新建一个"为某场景定制"的查询接口。
- **新增响应式 Stream**(基于已有表事件触发重新聚合的场景) → 复用 `watchChanges()`,service 端用 `asyncMap` 拼装;**不**让 service 直接依赖 drift 的 `tableUpdates`。
- **新增复合 SQL 公式**(余额、scope、currency 兑换等) → 落 `data/accounting/sql/`,以 `Expression<T>` 工厂形式提供,多处共用。
