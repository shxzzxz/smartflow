# 08.4 仓储层与读路径分层

## 适用范围

本决策约束账务核心及其它业务域的读路径如何分层：

- SQL / repository / query source 中允许出现哪些信息；
- application query service 与 read model 的职责；
- UI view model 的职责；
- 响应式 Stream 的归属；
- domain 是否允许依赖持久化响应式原语；
- 纯 UI / 报表查询与领域规则事实加载的边界。

不约束写路径的最终接口形态；写路径边界应在重构时单独审计。

## 背景

账务核心读路径在快速演进期形成了几类耦合：

1. **业务流程语义下沉到 SQL**：复杂 CTE 中散布 `purpose='refund'`、`purpose IN (...)`、`is_excluded_from_stats=0` 等业务流程字面量。
2. **UI 装饰下沉到 read model**：`accountName`、`categoryIconKey`、`flowOut/InAccountId` 等字段进入查询模型，导致 SQL 绑定 UI 展示。
3. **数据编排藏在 repository**：repository 内用 if 链判断哪种 purpose 该查哪些子树。
4. **read model 形态混乱**：常规列表、详情、更正链复用同一模型，字段大量“只在某场景有意义”。
5. **domain 层依赖响应式持久化原语**：domain service 直接监听 Drift table updates。

## 决策

纯 UI / 报表读路径可以绕过 domain：

```text
features
  -> application query interface / query service
      -> infrastructure query implementation
          -> database
```

查询接口、查询参数、scope filter 与 read model 定义在 application query side；infrastructure query service 实现这些查询并把参数翻译成 Drift / SQL。domain 不参与纯展示投影。

读路径分为三层：

| 层 | 路径示例 | 职责 | 排除 |
| :--- | :--- | :--- | :--- |
| application query interface / service / read model | `application/accounting/queries/`、`application/accounting/read_models/` | 定义查询接口、查询参数、scope filter、read model；按业务场景编排查询、分桶、聚合、投影、暴露响应式查询 | UI 装饰、领域不变量 |
| infrastructure query implementation / source | `infrastructure/accounting/...` 或过渡期 `data/accounting/...` | 实现 application query interface、原子查询、参数化聚合、SQL 表达式、Drift watch 实现 | UI 装饰、领域规则判定 |
| UI view model / presentation | `features/<feature>/view_models/`、`widgets/business/*` | 名称查找、图标、账户展示方向、格式化、页面状态 | 账务规则、统计口径 |

### 1. read model 属于 application

`TransactionListItem`、`TransactionHistorySnapshot`、详情页 read model、`CashflowSummary` 等是查询投影，不是领域模型。

它们应放在 application query side，表达“某个场景要读取什么”，不负责维护账务不变量。

`TransactionScopeFilter` 这类查询口径也属于 application query side。它描述 stats / budget / asset-liability / actual / all 等读侧 scope，用于投影和报表，不作为 domain port 入参。

### 2. 响应式查询属于 application + infrastructure

Drift `.watch()`、table update 监听等是 infrastructure 机制。

application query service 可以组合这些 Stream，并投影 read model：

```dart
return querySource.watchPage(query).asyncMap((page) async {
  // application 侧按业务场景编排切片、聚合、投影
});
```

domain 不直接依赖 `Stream`、Drift table updates、`TransactionScopeFilter` 或具体数据库响应式 API。

### 3. infrastructure query implementation 只提供读侧实现

infrastructure query implementation / source 只做参数化数据访问：

- 按 transaction ids 查 entries。
- 按 root ids 聚合 child detail amounts。
- 按 account type / scope / window 聚合余额。
- 暴露底层变化 Stream 作为重新投影触发信号。

它不判断“哪个业务场景需要查哪些子树”，也不把业务流程规则写死在 SQL 中。业务场景由 application query service 通过查询参数表达，infrastructure 只负责把参数翻译成 where / join / aggregate。

### 4. 业务字面量隔离

`BusinessPurpose.refund`、`reimbursementReceipt`、`BusinessState.current`、统计排除口径等业务字面量只能出现在：

- application query service 调用 query source 时传入的参数；
- application read model 投影代码；
- scope filter 预设定义；
- UI view model 的展示派生。

infrastructure 实现只把参数翻译成 where 条件，不直接编码具体业务场景。

### 5. 领域规则事实加载不走 application read model

如果查询结果会参与领域规则判定，它不是纯读侧投影，应由 domain port 表达领域事实加载需求。

例如：

- 退款规则需要父交易、原分录结构、已退款总额、可退款余额。
- 报销结案需要垫付交易、已到账总额、剩余应收。
- 更正 / 取消需要原交易状态、原分录结构、mutation 链事实。

这些查询返回的是领域上下文，不复用 `TransactionListItem`、详情页 read model 或 `TransactionScopeFilter`。application 不应自己拼这些事实后替 accounting domain 做规则判断。

### 6. UI 装饰留在 UI 层

read model 保留会计事实和业务派生标量，不持有 UI 装饰。

例如：

- read model 可以持有 `accountId`、`entries`、`details`、`refundedTotal`。
- UI view model 负责 `accountName`、`iconKey`、`flowOut/InAccountId`、格式化文本。

### 7. SQL 公式收敛

跨场景共享的 SQL 表达式（余额累计公式、scope 过滤翻译等）通过 infrastructure SQL helper 收敛，避免手写多份 CASE WHEN。

Dart 等价公式留在 domain ledger 规则中，语义对称由测试保证。

## 含义

- domain 不放响应式查询服务，不直接依赖 Drift。
- application query service 是读路径编排者。
- read model 是 application projection，不是领域聚合。
- infrastructure query implementation 是读侧实现，不承载领域规则判定。
- `TransactionScopeFilter` 是 application query scope，不属于 domain。
- 会参与领域规则判定的事实加载通过 domain ports 和领域上下文表达。
- UI view model 做展示派生，不承载统计口径。

## 适用案例

### 仓储能力分桶

- application query interface：定义交易列表、详情、历史、统计等查询能力与 read model。
- infrastructure query source：交易直读、分页、参数化子树聚合。
- `EntryReadRepository`：按 transaction ids 查 entries。
- `TransactionDetailReadRepository`：按 transaction ids 查 details。
- `BalanceAggregateRepository`：按账户类型、时间窗口、scope 聚合。

这些能力可以仍在过渡期位于 `data/accounting/`，但职责上属于 infrastructure。

### application query service

`TransactionQueryService.watchTransactions`：

```text
watch page
-> 按 purpose / rootId 分桶
-> 并行查询 entries/details/child aggregates
-> 投影 TransactionListItem
```

`FinancialMetricsService.watchCashflowComparison`：

```text
watch accounting changes
-> 调用聚合 query source
-> 投影 CashflowSummary / comparison read model
```

### read model

一个场景一个 read model：

- 常规列表：`TransactionListItem`
- 更正链：`TransactionHistorySnapshot`
- 详情页：详情 read model，含 children / history / entries / details / 派生汇总

不要为了复用而把所有字段塞进一个大模型。

## 反例

### 反例一：repository 实现内编码业务流程字面量

- 形式：SQL 写死 `WHERE purpose IN ('reimbursementReceipt', 'reimbursementClose')`。
- 为什么不取：口径调整要改 SQL，变更点散乱。
- 替代：application query service 显式传 purpose / scope 参数。

### 反例二：read model 持有 UI 装饰

- 形式：`TransactionListItem` 直接持有 `accountName`、`categoryIconKey`、`flowOut/InAccountId`。
- 为什么不取：UI 变化推动 SQL 和 read model 变化。
- 替代：read model 暴露 id 和会计事实，UI view model 查 lookup 并格式化。

### 反例三：数据编排藏在 repository

- 形式：repository 内部按 purpose 分支决定是否查 refund / reimbursement 子树。
- 为什么不取：repository 同时承担数据访问与业务判断。
- 替代：application query service 分桶并调用参数化 repository 能力。

### 反例四：domain 层直接依赖 Drift 响应式原语

- 形式：domain service 直接 `_db.tableUpdates(...)`。
- 为什么不取：domain 依赖具体持久化技术。
- 替代：infrastructure 暴露变化触发，application query service 组合 Stream。

### 反例五：domain port 依赖 application query scope

- 形式：`domain/accounting/ports` 方法接收 `TransactionScopeFilter`。
- 为什么不取：`TransactionScopeFilter` 是读侧投影口径，会造成 domain -> application 的反向依赖。
- 替代：纯查询放 application query side；领域规则事实加载定义专用 domain port 和领域上下文。

### 反例六：application 自己拼领域事实

- 形式：退款用例在 application 查询父交易、已退款额、entries 后自行判断可退款金额。
- 为什么不取：领域规则需要哪些事实本身是 accounting domain 知识，放到 application 会复制并漂移。
- 替代：application 调 accounting domain service；domain service 通过本领域 ports 加载退款上下文并判断。

### 反例七：为方便而合并 read model

- 形式：列表、详情、历史链共用一个字段巨大的 read model。
- 为什么不取：字段语义按场景漂移，调用方难以判断哪些字段有效。
- 替代：一个场景一个 read model，共享部分用组合而非大一统。

## 演进规则

- 新增纯查询场景：优先在 application query side 新增 query / scope / read model，由 infrastructure 实现。
- 新增领域规则事实加载：在 domain 定义 port 与领域上下文，由 infrastructure 实现，不复用 application read model。
- 新增原子聚合：在 infrastructure query source / repository 加参数化方法，不写业务场景分支。
- 新增 UI 派生：放 `features/<feature>/view_models/` 或 `widgets/business/`。
- 新增响应式查询：由 infrastructure 提供 watch 能力，application 组合投影，domain 不直接依赖 Stream。
- 新增复合 SQL 公式：放 infrastructure SQL helper，Dart 等价公式放 domain 规则并补测试。
