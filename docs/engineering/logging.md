# 日志规范

本文档定义 SmartFlow 的诊断日志记录时机、级别、异常处理责任和数据边界。错误表达与传播见 [错误处理](error-handling.md)，验证范围见 [测试规则](testing.md)。

日志用于定位一次操作为何失败、关键流程执行到哪里，不作为账务事实或业务审计记录。财务状态仍以业务数据为准。

## 统一入口与命名

- 复用 `package:logging`，由 `core/logging` 统一配置级别、输出与文件保留，`app` 负责启动装配。
- Logger 使用稳定的点分模块名，例如 `app.bootstrap`、`app.error`、`app.provider`、`application.import`、`infra.database`、`feature.transaction.form`。实例 ID、用户输入和文件路径不进入 Logger 名称。
- 业务代码不使用 `print`、`debugPrint` 或直接写文件代替日志入口。`dart:developer` 仅用于统一输出和日志系统自身故障的兜底。
- `domain` 与纯 presentation 函数不记录日志；通过返回值或异常向调用边界提供结果和失败语义。

## 级别与记录时机

| 级别 | 记录内容 | 典型场景 |
| :--- | :--- | :--- |
| `FINE` | 开发排查所需的阶段或分支信息 | 导入阶段切换、可选数据加载、诊断耗时 |
| `INFO` | 关键流程的开始、完成与汇总结果 | 启动及版本、数据库迁移、导入提交、备份恢复、批量清理、后台任务完成 |
| `WARNING` | 已处理的业务拒绝、输入文件无效，或有明确降级路径的技术异常 | 合同状态不允许编辑、备份校验拒绝、可选配置读取失败后采用默认值 |
| `SEVERE` | 导致操作失败的基础设施异常、未知异常、编程错误或数据不变量破坏 | 保存失败、迁移失败、未处理异步异常、Flutter framework error |

级别根据实际影响确定，不仅根据异常类型确定：一次可选读取失败后能按既定规则继续，可记 `WARNING`；被包装进业务异常的数据库故障仍属技术失败，不能因包装而降级。

记录时机遵循以下规则：

- 耗时或会批量修改数据的关键流程记录开始与最终结果；中间阶段默认使用 `FINE`，必要的诊断阶段才提升到 `INFO`。
- 完成日志必须在操作实际完成后记录。事务用例须等待最外层事务成功提交；内层事务返回不代表跨域操作已提交。
- 失败日志只描述已经确认的事实。事务回滚尚未结束时，不声称“已回滚”；无法确认回滚结果时应保留失败语义。
- 批量流程优先记录成功数、跳过数、失败数等摘要，失败时可补充必要的组序号或阶段，不逐条输出业务数据。
- 普通页面加载成功、每次 rebuild、provider 状态变化、每次点击、每条 SQL 和普通 CRUD 成功不默认记录 `INFO`。
- 字段校验、正常空态、分支探测和用户取消不记错误日志。已记录开始的长流程可用 `INFO` 记录取消，以解释结束状态。

统一输出阈值为 Debug `FINE`、Profile / Release `INFO`，记录该级别及以上的消息。Debug 可镜像到开发控制台；所有输出遵守同一数据边界，不能以调试模式为由输出财务明细。

## 异常记录责任

一次失败沿调用链传播时，由最终处理它的边界记录一条完整异常日志。下层需要补充定位信息时，优先通过异常的稳定 code、cause、原始堆栈和必要上下文传递，不采用“记录后再抛出”的默认模式。

| 场景 | 负责记录的边界 | 其它层的职责 |
| :--- | :--- | :--- |
| 用户命令转换成 UI outcome | ViewModel 的动作处理边界；已使用共享 action guard 时由 guard 记录 | application / repository 转换已知失败或继续抛出，View 只展示结果 |
| provider 加载失败进入 error state | 应用级 `ProviderObserver` | 页面展示加载错误，不因 rebuild 或再次读取 error state 重复记录 |
| 后台任务失败后继续其它任务或等待重试 | 任务调度入口 | 任务内部继续抛出，入口记录失败及重试语义 |
| 局部捕获并采用既定降级结果 | 执行降级的局部边界 | 记录失败与降级结果，外层不再补记同一失败 |
| 未处理异常、`Error`、framework error | 全局异常边界 | 普通 ViewModel 不捕获 `Error`，不为记录日志而吞掉错误 |

provider observer 负责记录，不负责全局提示。若同一失败已由 observer 记录，随后传播到全局边界，应避免重复记录；这不改变错误传播和 UI 兜底责任。只消除同一次失败的重复上报，后续重试的新失败仍须记录。

application 可以记录关键业务流程摘要，infrastructure 可以记录迁移、文件处理等技术阶段；这些阶段日志不能重复承担同一次异常的最终记录责任。

### 异常信息

- `AppException` 必须保留稳定错误码。以固定操作描述加 `[code]` 表达，例如 `Transaction submit failed [ledger.account.not_found].`，不依赖可变的用户文案搜索和归类。
- 命令边界处理业务拒绝时记录 `WARNING`；处理导致命令失败的 `InfrastructureException` 或普通 `Exception` 时记录 `SEVERE`。已知的文件格式或校验拒绝按 `WARNING` 处理。
- 技术失败使用捕获到的异常原因和堆栈；包装异常时保留 `cause` / 原始 `stackTrace`，最终记录优先使用原始原因与堆栈，同时保留外层 code 和操作上下文。
- 异常与堆栈通过日志 API 的独立参数传递，不直接插值进 message。不得用记录位置新建的堆栈代替失败位置堆栈。
- 不将未知技术失败伪装成业务拒绝，不为日志新增包住每个 repository 方法的通用 guard。清理或日志记录自身失败也不能覆盖原始业务异常。

## 内容与数据边界

沿用 JSONL 格式，每条记录包含 `time`、`level`、`logger`、`message`，按需包含 `error`、`stackTrace`。时间使用 UTC ISO 8601。操作、结果、稳定错误码和必要上下文先通过固定描述表达，不为所有日志强制引入新的事件模型或追踪框架。

允许记录定位问题所需的应用版本、schema 版本、操作类型、阶段、数量、耗时和必要的内部 ID。内部 ID 必须是项目生成的标识，不得用账户名称、外部账号或原始文件内容代替；无定位用途时也不记录。

默认不记录：

- 金额、余额、账户名称、交易备注、用户自定义分类或标签名称等财务明细。
- 原始导入行、完整备份内容、完整 command / entity / state 的字符串化结果。
- 完整 SQL 参数、文件完整路径、用户提供的文件名、凭证或令牌。

该边界同样适用于异常的 `toString()`、嵌套 cause、provider 描述、堆栈路径以及开发控制台输出。记录前应移除或替换其中的敏感值；原始异常文本不安全时，保留异常类型、稳定 code、安全摘要及去除敏感路径后的调用位置，不直接输出原始文本。不要通过丢弃全部异常原因和堆栈来规避处理。

日志保存在本地应用支持目录，不纳入业务备份。沿用现有按日期和大小轮转、按天数和文件数清理的能力：默认轮转阈值 1 MiB、保留 14 天且最多 100 个文件，保留天数与文件数可由现有设置调整。

日志目录初始化、写入、轮转或清理失败时，应采用不依赖文件日志的最小诊断兜底；不得使正常业务操作失败，也不得向同一日志入口递归报告写入失败。兜底输出仍需遵守数据边界。
